# 2.0 — Preflight

**Parent:** new · **Depends on:** Phase 1 · **Unblocks:** everything
**Estimate:** 0.5 d · **Risk:** low, but skipping it moves the risk into 2.3

## Goal

Close the five platform gaps Phase 2's tasks assume are already there. Each is
small; each would otherwise be discovered halfway through the state machine,
where the cost of a detour is highest.

## Work items

### 2.0.1 Clock abstraction

Session expiry (45 s / 25 s), due-date computation, the idempotency minute
bucket and `ResolveHistorical` all read the current time. Tests must control it,
and `time.Now()` scattered through modules makes that impossible.

- [x] `internal/platform/clock/clock.go`
      ```go
      type Clock interface{ Now() time.Time }
      type System struct{}                    // time.Now().UTC()
      type Fake struct{ mu sync.Mutex; t time.Time }  // Set, Advance
      ```
- [x] `Fake.Now()` returns UTC and is safe under `-race` (the concurrency tests
      in 2.8 call it from several goroutines)
- [ ] Every Phase 2 service takes a `clock.Clock` in its constructor; nothing in
      `lending` or `checkout` calls `time.Now()` directly — N/A until those
      services exist (2.1, 2.3a); the package itself is ready for them
- [x] Leave Phase 1 modules alone — retrofitting them is not this phase's job
- [x] **Revised after review**: `internal/platform/auth` was the one Phase 1
      module worth retrofitting after all — it owns pairing-code expiry, a
      Phase 2 feature, and its `time.Now()` meant that expiry could not be
      driven by `clock.Fake` (the existing test back-dates the column by hand
      instead). `auth.New` now takes optional `auth.WithClock(c)`, defaulting
      to `clock.System{}`, and every `time.Now()` in the package reads through
      it — admin-session expiry included, since leaving one caller on the wall
      clock would be the same trap again

### 2.0.2 `test/fixtures`

`docs/10-testing-strategy.md` writes its example tests against a `fixtures`
package that does not exist. Build it now so the ~80 integration tests of 2.8
are cheap to write.

- [x] `test/fixtures/fixtures.go`, `//go:build integration`, each helper taking
      `(t *testing.T, pool *db.Pool)` and calling `t.Helper()`:
      `Department`, `User`, `SuspendedUser`, `ArchivedUser`, `Category`,
      `AvailableDevice`, `DeviceInStatus`, `Kiosk` (returns id + plaintext
      token), `ActiveCredentialFor`, `UnboundCredential`, `RevokedCredential`
      — each of these builds state through the real module service, never
      raw SQL, so a fixture can't construct anything the app itself would
      reject. `ActiveCredentialFor` and `RevokedCredential` take
      `(subjectType, subjectID)` for an existing subject
- [x] Unique-per-call asset tags and employee numbers (a counter, not
      `rand`) so a helper called twice in one test cannot collide on
      `devices_asset_tag_live_uk`
- [x] `OpenLoan` and `ClosedLoan` helpers land with 2.1, not here

### 2.0.3 Kiosk registration

Nothing currently creates a `kiosks` row, so no integration test and no demo can
present a kiosk token.

- [x] `internal/platform/auth`: `RegisterKiosk(ctx, name, location) (id, plainToken string, err error)`
      and `RotateKioskToken(ctx, id)`, hashing with the same scheme
      `ValidateKioskToken` verifies
- [x] `hdms-cli kiosk register --name --location` and `hdms-cli kiosk rotate <id>`,
      printing the token exactly once, following the `admin bootstrap` pattern in
      `cmd/hdms-cli/main.go`
- [x] `IssuePairingCode(ctx, kioskID) (code string, expiresAt time.Time, err error)`
      and `RedeemPairingCode(ctx, code) (kioskID, name, plainToken string, err error)`
      — a 6–8 digit single-use code, 10-minute TTL, stored hashed on the kiosk row.
      Phase 3's iPad is paired with a code rather than a pasted token: the kiosk
      token is long-lived, and typing one on an iPad whose on-screen keyboard is
      suppressed by a paired scanner is the worst possible handling of a credential
      (see [phase-3/3.7](../phase-3/3.7-pwa-and-kiosk-mode.md)). Redeeming mints
      and reveals a *fresh* token (functionally a rotation) rather than
      recovering the one issued at registration — the plaintext from
      registration is never persisted, so there is nothing to recover
- [x] Redeeming consumes the code; a consumed code and an expired code are
      indistinguishable to the caller, so the endpoint cannot be used to probe
      kiosk ids
- [x] **Fixed after review**: "consumes the code" now holds under
      concurrency, not just sequentially. `RedeemPairingCode` was a `SELECT`
      followed by an unconditional `UPDATE`, so two simultaneous redemptions
      both read the row, both minted a token and both wrote — the second
      overwriting the first, leaving that caller holding a token that never
      authenticates, with no error. The `UPDATE` now re-checks
      `pairing_code_hash`, so the row lock serialises the two and the loser
      matches nothing and gets `ErrPairingCodeInvalid`
- [x] `migrations/0006_kiosk_pairing.sql` — `pairing_code_hash bytea`,
      `pairing_code_expires_at timestamptz` on `kiosks`, both nullable, with a
      `CHECK` that they are either both set or both null. The table from
      `0001_init.sql` has neither
- [x] `hdms-cli kiosk pairing-code <id>` for setting up a kiosk without the admin
      console, which does not exist until Phase 4
- [x] The HTTP endpoints (`/v1/kiosks…`, `/v1/kiosks/pair`) belong to
      [2.6](2.6-api-surface.md); this item is the service + CLI only

### 2.0.5 depguard rule for `checkout`

Every sibling is already forbidden from importing `checkout`. The reverse rule —
`checkout` may import the four sibling `…api` packages and nothing deeper — does
not exist, so the boundary the whole architecture rests on is unenforced in the
one module that matters.

- [x] Add a `checkout-orchestrator` rule in `hdms-backend/.golangci.yml` denying
      `…/modules/identity`, `…/modules/catalog`, `…/modules/credentials`,
      `…/modules/lending` (the implementation packages) from
      `**/internal/modules/checkout/**`, while leaving the four `…api` packages
      allowed — **already present**, added during Phase 1's admin-console work
      alongside the other module-isolation rules and `no-checkout-outside-cmd`.
      Nothing to add; this item is verification only
- [x] Remember the v2 `files` glob gotcha: patterns need a leading `**/` — the
      existing rule already does this correctly
- [x] Prove it: temporarily add `import ".../modules/lending"` to a checkout file,
      confirm `task lint:backend` fails, revert — confirmed
      (`depguard: import '.../modules/lending' is not allowed from list
      'checkout-orchestrator'`), then removed

## Exit criteria

- [x] `task lint`, `task test:backend`, `task test:integration` green (backend
      only — frontend is untouched by this sub-phase)
- [x] A pairing code minted by `hdms-cli kiosk pairing-code` redeems for a working
      token exactly once, and a second attempt fails indistinguishably from an
      expired one — proven in `test/integration/kiosk_test.go`
      (`TestKioskPairingCodeRedeemsExactlyOnce`,
      `TestKioskPairingCodeConsumedAndExpiredAreIndistinguishable`, the latter
      back-dating `pairing_code_expires_at` directly since 10 minutes is too
      long to sleep out in a test)
- [x] `sqlc generate` and `task generate` both produce no diff (verified by
      running each twice)
- [x] A kiosk token minted by `hdms-cli kiosk register` authenticates against a
      running API (`curl -H "Authorization: Bearer …" …/v1/devices` returns 200 —
      note that it *should* eventually be 403 for most routes; that is 2.6's job)
      — verified two ways: `hdms-cli kiosk register` against a real migrated
      Postgres, and `TestKioskTokenAuthenticatesAgainstAPI`, which drives the
      real `auth.Service.Middleware` (the same middleware `cmd/hdms-api` wires
      up) with the minted token over `httptest`. A literal `curl` against a
      TLS-served instance was not run — `certs/` requires an interactive
      `mkcert -install` this environment couldn't grant — so this is not
      re-verified with every dev's local HTTPS stack, only the code path it
      exercises
- [x] A deliberate `checkout → lending` import fails the lint
