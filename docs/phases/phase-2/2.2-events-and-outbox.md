# 2.2 — Events and the transactional outbox

**Parent:** [§2.2](../phase-2-lending-checkout.md) · **Depends on:** 2.0 ·
**Unblocks:** 2.3c (writes outbox rows), 2.6 (SSE reads them)
**Estimate:** 1 d · **Risk:** medium — the failure mode is silent

## Goal

A state change and the announcement of that state change must be the same
atomic fact. The `outbox` table already exists (`migrations/0001_init.sql`);
this sub-phase gives it a writer, a dispatcher and an in-process bus, so that
audit, notifications (Phase 5) and the SSE stream (2.6) all hang off one
mechanism rather than three ad-hoc call sites.

## Design notes

**Why an outbox at all, for a system doing ten transactions a day.** Not for
throughput. For the guarantee: publishing inside the transaction means a
rolled-back borrow cannot emit `loan.opened`, and a subscriber that panics
cannot roll back a borrow. Both directions of that isolation are the point, and
both get a test.

**Topics** are typed constants, not free strings:

| Topic | Emitted by | Payload |
|---|---|---|
| `loan.opened` | 2.1 via 2.3c | loanID, deviceID, userID, dueAt, origin |
| `loan.closed` | 2.1 via 2.3c | loanID, deviceID, userID, returnedAt, returnSource |
| `loan.overdue` | sweeper (2.3c) | loanID, deviceID, userID, dueAt |
| `device.status_changed` | catalog via 2.3c | deviceID, from, to, reason |
| `credential.revoked` | credentials (Phase 1 call site, wired here) | credentialID, subjectType, subjectID |
| `user.registered` | identity (Phase 1 call site, wired here) | userID, registeredBy |

Payloads are `jsonb` and must be **self-contained**: a subscriber may run after
the row it describes has changed again, so "go read the current state" is wrong.

**Delivery is at-least-once.** Subscribers must be idempotent; `audit` is
naturally so because it appends. Say this in the package doc so a future
subscriber author does not assume exactly-once.

## Work items

### 2.2.1 `internal/platform/events`

- [x] `Topic` string type and the six constants above
- [x] `Event{ID int64, Topic Topic, Payload json.RawMessage, CreatedAt time.Time}`
- [x] `Bus` — in-process, `Subscribe(topic, handler)` at wiring time only (no
      dynamic unsubscribe; the composition root registers everything at startup)
- [x] Handler signature `func(ctx context.Context, ev Event) error`; a returned
      error is logged and the event is retried on the next poll, never propagated
      to the producer
- [x] A handler panic is recovered, logged with the topic and event id, and
      treated as an error — one bad subscriber must not take the process down

### 2.2.2 Outbox writer

- [x] `events.Publish(ctx, pool, topic, payload)` — inserts into `outbox` using
      `db.Conn(ctx, pool)`, so it joins the ambient transaction automatically
- [x] Rejects being called outside a transaction in test builds (a guard that
      catches "I published from a handler" mistakes early) — implemented with
      the stdlib `testing.Testing()` (Go 1.21+): true whenever the binary is
      running under `go test`, false in the real `hdms-api`/`hdms-cli`
      binaries, so no custom build tag was needed. **Deviation**: panics
      rather than returning an error — a returned error from `Publish` is too
      easy to silently drop (`_ = events.Publish(...)`), which defeats the
      point of a guard meant to fail loud
- [x] **Not in the original list**: `sqlc.yaml` had no query directory for
      `outbox` at all (it isn't owned by any existing module). Added
      `queries/events/events.sql` → `eventsstore`, output
      `internal/platform/events/store`, matching the `internal/platform/auth/store`
      precedent for a platform package's own store

### 2.2.3 Dispatcher

- [x] `events.Dispatcher` polling every 500 ms (configurable; 1 s SSE latency is
      an exit criterion, so the poll interval must leave headroom)
- [x] `SELECT … FROM outbox WHERE published_at IS NULL ORDER BY id
      FOR UPDATE SKIP LOCKED LIMIT 100` inside its own transaction, dispatch,
      then stamp `published_at` — so two API replicas never double-dispatch.
      **Clarifying the transaction boundary**, since it's easy to misread:
      the claim transaction stays open for the whole batch (that's what makes
      `SKIP LOCKED` exclusive across replicas), but each row's dispatch is
      handled with a plain `context.Background()`, not this transaction — see
      2.2.4 below and the package doc for why that's deliberate. Only the
      rows whose dispatch succeeded get their `UPDATE published_at` issued
      before the batch commits; a row whose handler failed is simply skipped
      and stays unpublished when the transaction commits
- [x] Started and stopped by `cmd/hdms-api`; `Stop` drains in flight work and
      returns within the shutdown grace period
- [x] Structured log line per dispatch batch, with a `slog` counter of
      unpublished backlog for observability
- [x] **Also added, not in the original list**: an hourly sweep of
      `outbox` rows published more than 7 days ago, run from the same
      polling loop — the "Risks" table below already calls for this; it
      just wasn't in the checklist
- [x] **Added after review**: retry accounting
      (`migrations/0010_outbox_retry.sql` adds `attempts`,
      `next_attempt_at`, `last_error`, `failed_at`). The design above —
      "a row whose handler failed is simply skipped and stays unpublished"
      — is correct per row but wrong per queue: because a batch is claimed
      `ORDER BY id LIMIT 100`, a permanently failing row is re-dispatched
      every 500 ms forever, and a hundred of them at the head starve every
      newer event behind them. Each failure now backs the row off
      exponentially (1 s, 2 s, 4 s … capped at 5 min) and records the
      error; after `maxDispatchAttempts` (10, ~half an hour) the row is
      dead-lettered — `failed_at` set, never claimed again, never swept —
      and the crossing is logged at ERROR. `CountUnpublished` excludes
      dead-lettered rows so a permanent failure does not read as a forever
      growing backlog; `Dispatcher.DeadLetteredCount` is the number that
      does count them, for 2.6's health surface

### 2.2.4 Subscribers

- [x] `audit` subscribes to all six topics and writes an `audit_events` row
      (`internal/modules/audit/subscriptions.go`) — running with a plain,
      transaction-free context, so `Record` auto-commits independently of the
      dispatcher's claim transaction. **This is the load-bearing design
      decision for at-least-once delivery**: if a handler's write were inside
      the dispatcher's transaction instead, a crash before that transaction
      committed would roll back the handler's effect *too*, making delivery
      effectively exactly-once (until a crash lost data) rather than
      at-least-once (until a crash duplicates it) — the guarantee this
      sub-phase's design notes explicitly ask for
- [ ] The SSE hub of [2.6](2.6-api-surface.md) subscribes to `loan.*` and
      `device.status_changed`; this sub-phase only needs the bus to exist

## Exit criteria

- [x] A rolled-back transaction publishes nothing (asserted, not argued)
- [x] A failing subscriber never fails the originating transaction
- [x] Two dispatchers running concurrently deliver each event once
- [x] Backlog depth is visible in logs/metrics — logged (`slog`) per dispatch
      batch as planned; no Prometheus metric was added since the parent's
      own wording ("a `slog` counter") only asked for the log line

## Risks

| Risk | Mitigation |
|---|---|
| Outbox grows unbounded | A `DELETE FROM outbox WHERE published_at < now() - interval '7 days'` sweep in the same dispatcher loop; Phase 5 revisits retention |
| Someone publishes outside a transaction and the guarantee quietly weakens | The test-build guard in 2.2.2, plus review of every `Publish` call site |
| Poll interval tuned down for latency, burning CPU on an idle system | 500 ms with `SKIP LOCKED` on an indexed partial predicate is cheap; measured in the 2.8 load test rather than guessed |
| A permanently failing handler starves the queue behind it | Per-row backoff and dead-lettering (2.2.3); a dead-lettered row keeps its `last_error` forever, so the failure is diagnosable rather than merely quiet |
