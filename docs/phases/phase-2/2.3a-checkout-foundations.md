# 2.3a — `checkout` foundations: schema, `Deps`, session lifecycle

**Parent:** [§2.3](../phase-2-lending-checkout.md) · **Depends on:** 2.1 ·
**Unblocks:** 2.3b
**Estimate:** 1 d · **Risk:** medium

## Goal

Everything the state machine needs to stand on, and nothing that decides an
outcome: the two tables, the dependency interfaces `checkout` defines for
itself, and the session CRUD (`CreateSession`, `Get`, `Close`, `Cancel`). After
this sub-phase a session can be created, fetched and closed; scanning still
returns "not implemented".

## Design notes

**`checkout` defines its own dependency interfaces.** They live in
`internal/modules/checkout/deps.go` and are *satisfied* by `identityapi`,
`catalogapi`, `credentialsapi` and `lendingapi` — not copied from them. This is
what lets the machine be unit-tested against fakes with no database and no
sibling module, which is the difference between the 2.3b matrix taking a day and
taking a week.

```go
type UserLookup interface {
    LookupUser(ctx context.Context, id string) (identityapi.UserSummary, error)
}
type DeviceLookup interface {
    LookupDevice(ctx context.Context, id string) (catalogapi.DeviceSummary, error)
    CategoryOf(ctx context.Context, categoryID string) (catalogapi.Category, error)
    SetStatus(ctx context.Context, id string, status catalogapi.DeviceStatus, reason, actor string) (catalogapi.DeviceSummary, error)
}
type TokenResolver interface {
    Resolve(ctx context.Context, token string) (credentialsapi.SubjectRef, error)
}
type Loans interface {
    OpenLoan(...) (lendingapi.Loan, error)
    CloseLoan(...) (lendingapi.Loan, error)
    OpenLoansFor(ctx context.Context, userID string) ([]lendingapi.Loan, error)
    HolderOf(ctx context.Context, deviceID string) (lendingapi.Loan, error)
}
```

Referencing sibling *types* in these signatures is allowed and intended — the
depguard rule permits the four `…api` packages. What it forbids is reaching into
a sibling's implementation.

**Sessions are persisted, not in-memory** ([ADR-0004](../../adr/0004-scan-session-state-machine.md)):
a kiosk reload mid-flow must resume rather than strand a scan, and the admin
console must be able to watch live activity.

**One kiosk, one live session.** Not stated in the parent docs, and it needs
deciding here rather than being discovered in 2.3c: creating a session at a
kiosk that already has an open one closes the old one with outcome
`superseded`. The alternative — two live sessions at one physical counter —
cannot be reconciled with a single screen.

### 2.3a.4 Service skeleton

- [ ] `checkout.New(pool, clock, deps Deps, audit auditapi.Recorder, bus *events.Bus)`
- [ ] `CreateSession(ctx, kioskID, actor)` — closes any live session for that
      kiosk with outcome `superseded`, inserts a fresh `idle` session with
      `expires_at = now + idleTTL`
- [ ] `GetSession(ctx, id)` — returns `ErrSessionExpired` for a session past
      `expires_at` that the sweeper has not reached yet, so behaviour does not
      depend on sweeper timing
- [ ] `Close(ctx, id, actor)` → `completed`; `Cancel(ctx, id, actor)` → `cancelled`;
      both idempotent (closing a closed session is a no-op, not an error)
- [ ] `Scan` and `ReturnLoan` present but returning `errNotImplemented` — they
      land in [2.3c](2.3c-scan-orchestration.md)
- [ ] Timeout constants in one place: `idleTTL = 45s` when a device is pending,
      `activeTTL = 25s` once a user is known, `sweepInterval = 30s`

## Exit criteria

- [ ] A session can be created, fetched, closed and cancelled over the service
      API, with state persisted across a process restart
- [ ] `checkout` imports only the four `…api` packages, `platform/*` and the
      standard library (depguard green)
- [ ] `scan_events` provably never contains a raw token
- [ ] The one-live-session-per-kiosk rule is enforced by an index, not by a read

## Risks

| Risk | Mitigation |
|---|---|
| `Deps` drifts into a copy of the sibling APIs | Keep each interface to the methods the machine actually calls; a method with no call site is deleted |
| The one-live-session rule surprises Phase 3 | Documented here and in the OpenAPI description of `POST /v1/sessions`; the kiosk's recovery path relies on it |
