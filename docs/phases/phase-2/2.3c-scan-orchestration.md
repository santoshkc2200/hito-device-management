# 2.3c — Scan orchestration: transactions, duplicates, expiry

**Parent:** [§2.3](../phase-2-lending-checkout.md) · **Depends on:** 2.3b, 2.2 ·
**Unblocks:** 2.4, 2.6
**Estimate:** 1.5 d · **Risk:** highest in the phase

## Goal

Execute what [2.3b](2.3b-transition-table.md) decided, atomically across three
modules, correctly under two kiosks scanning the same device at the same
millisecond. This is the sub-phase where the custody record can be corrupted, so
it is the one with the least room for cleverness.

## Design notes

**Shape of `Scan`:**

```
Scan(ctx, sessionID, token, source, scannedAt):
  1. tokens.Parse(token)                     → invalid-token-format (400), no session touched
  2. TxManager.Do:
       a. GetSessionForUpdate(sessionID)     → row lock: the serialisation point
       b. expired? → close as expired, return an expired outcome (not a 410 mid-session)
       c. Resolve token → SubjectRef         (credentials)
       d. Load subject: user or device + its category  (identity / catalog)
       e. Build Input, classify, Decide      (pure, 2.3b)
       f. Execute the Decision               (lending + catalog + outbox)
       g. Persist session state, touch expiry, insert scan_event
  3. Render message, assemble ScanResult
```

Steps (c)–(d) inside the transaction keep the read consistent with the write;
they are indexed single-row lookups, so the lock is held for well under a
millisecond in normal operation.

**The row lock is the concurrency answer within a session; the database
constraint is the answer across sessions.** `GetSessionForUpdate` serialises two
scans on *one* session. Two different sessions racing for one device are
serialised by `loans_one_open_per_device_uk` — the loser gets `23505` →
`ErrDeviceAlreadyOnLoan`, which the machine turns into a normal `rejected`
outcome naming the holder. Never a read-then-write check; never an advisory lock
on the device.

**Constraint violations abort the transaction.** Postgres marks the transaction
failed on `23505`, so the "who holds it now?" re-read cannot happen on the same
connection afterwards. Two workable options — pick one and state it in the code:

- wrap the `OpenLoan` insert in a `SAVEPOINT` so the outer transaction survives
  and the holder can be read in the same transaction (preferred: one round trip,
  one consistent view), or
- let the transaction roll back and re-read the holder on the pool before
  rendering the message (simpler, but the holder may have changed in between —
  acceptable for a display message, not for a decision).

**Borrow is three writes plus an event, or none:**

```go
err := txm.Do(ctx, func(ctx context.Context) error {
    loan, err := deps.Loans.OpenLoan(ctx, deviceID, userID, dueAt, meta)   // lending
    if err != nil { return err }
    if _, err := deps.Devices.SetStatus(ctx, deviceID, "on_loan", "", actor); err != nil { return err }  // catalog
    if err := events.Publish(ctx, pool, events.LoanOpened, payload(loan)); err != nil { return err }
    return persistSession(ctx, …)
})
```

INV-3 (`devices.status = 'on_loan'` ⟺ an open loan exists) holds because these
are one commit. The injected-failure test in 2.8 is what proves it.

**Duplicate detection is server-side and stateful.** The client debounce (Phase
3) is lost on reload; the server compares the incoming token's hash against the
session's last scan and timestamp. Store `last_token_hash` + `last_scan_at` on
`scan_sessions` — never the token itself — added in 2.3a's migration or a small
`0007b`. Within 3 s and equal ⇒ `duplicate`, no state change, `scan_events` row
with `result = 'duplicate'`.

**`scannedAt` from the client is advisory.** It is recorded on the scan event
for diagnostics; every timestamp that matters (`borrowed_at`, `returned_at`,
`expires_at`) comes from the server clock. A client-supplied past `borrowedAt`
on any live endpoint is rejected with `backdated-not-permitted` ([2.6](2.6-api-surface.md)).

## Work items

### 2.3c.1 Execution layer

- [ ] `execute(ctx, tx, session, decision, input) (checkoutapi.Outcome, error)`
      — a switch over `Action` only; it may not re-inspect `Input` to change
      course (review rule: if execution needs a new fact, the fact belongs in
      `Decision`)
- [ ] `borrow` — due date from the device's category default (nil period ⇒ no
      due date), `origin = kiosk`, `borrow_source` from the scan source,
      `session_id` recorded, `condition_out` from the device
- [ ] `return` — `CloseLoan` with `return_source = 'scanner'|'camera'|'manual'`,
      condition-in capture, device back to `available`
- [ ] `hold_device` / `replace_pending` / `set_user` / `switch_user` — session
      mutations only; `switch_user` closes the current session (outcome
      `user_switched`) and opens a new one, returning the new session's id
- [ ] `reject` / `duplicate` — no domain write, `scan_events` row always written

### 2.3c.2 `ReturnLoan` — the no-device path (FR-30)

- [ ] `ReturnLoan(ctx, sessionID, loanID, actor)` — only for a loan belonging to
      the session's identified user; anything else is `ErrSessionConflict`
- [ ] `return_source = 'manual'`, so the audit log distinguishes it from a
      scanned return — an unscanned return is a weaker claim that the item is
      physically back
- [ ] Same transaction shape as a scanned return, same event

### 2.3c.3 Expiry

- [ ] Per-state TTL applied on every touch, from the 2.3b table
- [ ] `Sweeper` goroutine every 30 s: `ExpireSessions` in one statement, closing
      `expires_at < now() AND closed_at IS NULL` as `expired`; releases any
      pending device (which is a session field, so nothing to undo in `lending`)
- [ ] Started/stopped by `cmd/hdms-api` alongside the outbox dispatcher
- [ ] Expiry during a scan is handled inline (see step 2b) so behaviour never
      depends on sweeper timing

### 2.3c.4 Wiring

- [ ] `cmd/hdms-api` and `internal/apiserver` construct `checkout` with the four
      sibling services as `Deps`, the clock, the bus and the audit recorder
- [ ] `internal/apiserver/server.go` gains the `checkout` service field (the
      HTTP handlers themselves are [2.6](2.6-api-surface.md))

## Exit criteria

- [ ] All seven scenarios from [04](../../04-scanning-and-checkout-flows.md)
      reproducible end to end at the service level, in both scan orders
- [ ] A borrow either writes loan + device status + outbox row, or writes none of
      them — proven by injected failure
- [ ] The execution layer contains no business branching that is not driven by a
      `Decision`
- [ ] No `time.Now()` in `checkout`; the fake clock drives every expiry test
- [ ] p95 scan latency < 100 ms locally (measured in 2.8, but instrumented here)

## Risks

| Risk | Mitigation |
|---|---|
| Cross-module SQL leaks past the boundary | `db.Conn(ctx, pool)` is the only mechanism; depguard + review; no module opens its own transaction when called from `checkout` |
| The failed-transaction re-read for the holder returns a stale or missing row | Decide savepoint vs. post-rollback re-read explicitly, document the choice, and test the concurrent-borrow message content |
| Sweeper and inline expiry disagree | Inline expiry is authoritative; the sweeper only reaps sessions nobody touched. One test per path |
| Row lock held across a slow sibling call | Only indexed single-row lookups happen inside the lock; the load test in 2.8 watches for lock waits |
