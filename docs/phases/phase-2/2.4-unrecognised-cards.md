# 2.4 — Unrecognised cards: refusing well

**Parent:** [§2.4](../phase-2-lending-checkout.md) · **Depends on:** 2.3c ·
**Unblocks:** 2.6 (the scope enforcement it tests), E7/E8 in Phase 3
**Estimate:** 0.5 d · **Risk:** low technically, high in product terms

## Goal

There is no kiosk enrollment and there never will be (FR-40, FR-45, INV-11).
Every unrecognised card therefore ends in a refusal — and a refusal that only
says "no" sends a person away holding a device they need, which makes the system
worse than the paper register it replaces. This sub-phase is about the three
distinct refusals, each naming the paper fallback, each logged so the
administrator can see how many people are being turned away.

## The three cases

| Case | `SubjectRef` | Message (from the catalogue, keyed) |
|---|---|---|
| **unbound** | `RefUnbound`, status active | "This card has not been registered yet. The attendant can write your item in the register — please see them to get your card." |
| **unknown** | `ErrCredentialUnknown` from `Resolve` | "Card not recognised. You can still take the item — the attendant will record it. Please see them to register." |
| **revoked** | `RefUser`/`RefDevice`, status `revoked`/`lost` | "This card was replaced on {{.RevokedAt}}. Please use your current card." |

All three are `200` with `outcome.kind = "rejected"`, never an HTTP error
([06](../../06-api-contract.md)): they are ordinary outcomes of a working
system. The matching problem types (`credential-unknown`, `credential-unbound`,
`credential-revoked`) exist for the *admin* API, where the same conditions are
genuine faults.

## Work items

### 2.4.1 Outcomes

- [ ] `credentials.Resolve` already distinguishes the three (`RefUnbound`,
      `ErrCredentialUnknown`, `CredentialStatus`); map each to its own
      `InputClass` and `MessageKey` — no shared "rejected" bucket
- [ ] Each releases any pending device and returns the session to `idle`
      (the [2.3b](2.3b-transition-table.md) table already says so; this is the
      assertion that it is true at run time)
- [ ] Each writes a `scan_events` row with `resolved_type` set to `unbound` /
      `unknown` / `revoked`, `result = 'rejected'` and a `reason`
- [ ] A revoked card's message includes the revocation date, which means
      `Resolve` must surface `RevokedAt` — extend `credentialsapi.SubjectRef` if
      it does not, and regenerate nothing else

### 2.4.2 The turned-away count

- [ ] `CountScanRejectionsSince(ctx, since)` grouped by `resolved_type`, feeding
      `GET /v1/dashboard` in [2.6](2.6-api-surface.md)
- [ ] The number the administrator actually needs is "distinct unknown tokens in
      the last 7 days" — the same person re-scanning three times is one person to
      go and register. Group by `token_preview` as a proxy and label it honestly
      in the API description

### 2.4.3 Kiosk scope — the test that must exist ★

`internal/platform/auth/middleware.go` currently authenticates a kiosk token and
then passes it to **every** route. FR-45 and INV-11 are unenforced today. The
enforcement lands in [2.6](2.6-api-surface.md); the *proof* is specified here
because this is the sub-phase about what a kiosk may not do.

- [ ] `test/integration/kiosk_scope_test.go` enumerates every path+method from
      the embedded OpenAPI spec (`gen.GetSwagger()`, already generated with
      `embedded-spec: true`) — not a hand-written list, so a newly added endpoint
      cannot silently escape the check
- [ ] Each operation is called with a valid kiosk bearer token; the test asserts
      the response is `401`/`403` unless the operation is on the kiosk allowlist
      (`POST /v1/sessions`, `GET /v1/sessions/{id}`, `POST /v1/sessions/{id}/scan`,
      `POST /v1/sessions/{id}/return-loan`, `POST /v1/sessions/{id}/close`,
      `DELETE /v1/sessions/{id}`, `GET /v1/healthz`, `GET /v1/readyz`)
- [ ] The allowlist lives in one exported place shared by the middleware and the
      test, so they cannot drift — but the test asserts *coverage of the spec*,
      not agreement with the list
- [ ] Explicit named cases for the two the requirement calls out:
      `TestINV11_KioskCannotCreateUser`, `TestINV11_KioskCannotListUsers`
- [ ] `TestINV11_RegisteredByNeverKiosk` — no code path writes a `kiosk:` actor
      into `users.registered_by`

## Tests

- [ ] `TestUnboundCardRejectedWithGuidance` — message names the paper fallback
- [ ] `TestUnknownTokenRejectedAndLogged` — `scan_events` row written, no user
      created anywhere in the process
- [ ] `TestRevokedCardRejectedWithDate`
- [ ] `TestRefusalReleasesPendingDevice` — parameterised over all three, from
      `awaiting_user`, asserting the session lands in `idle` and the device is
      untouched (`available`, no loan)
- [ ] `TestRejectionMessagesAllNamePaperFallback` — a content assertion over the
      catalogue: each of the three templates mentions the attendant/register.
      Blunt, and exactly the product rule that must not be silently edited away
- [ ] The spec-driven scope suite above

## Exit criteria

- [ ] Three distinct refusals with three distinct server-authored messages, each
      naming the paper fallback
- [ ] Each refusal releases the pending device and logs a `scan_events` row
- [ ] The kiosk token provably cannot create or list users — one test per
      endpoint, generated from the spec (FR-45, INV-11)
- [ ] The administrator can see how many people were turned away, by case, in
      the last 7 days

## Risks

| Risk | Mitigation |
|---|---|
| A future endpoint is added without a scope decision | The scope test enumerates the spec; a new operation fails until it is classified |
| Messages get "tightened" into pure refusals during copy review | `TestRejectionMessagesAllNamePaperFallback` fails, and the failure message says why the rule exists |
| The turned-away count is read as "attacks" rather than "people needing cards" | Wording in the dashboard field description and in [08](../../08-admin-console.md) |
