# 2.4b — The paper backfill engine

**Parent:** [§2.4b](../phase-2-lending-checkout.md) · **Depends on:** 2.1, 2.3b ·
**Unblocks:** the Phase 4 backfill screen, E16–E19
**Estimate:** 2 d · **Risk:** high — the only path that can write history

## Goal

An administrator types in a page of the paper register, days after the fact, and
the system either records it faithfully or tells them exactly where paper and
system disagree. This is the only code path allowed to supply a past
`borrowed_at`, which makes it the only path that can corrupt history — hence
the database-level custody constraint rather than an application check.

Backfill deliberately does **not** run through the scan session machine: there
is no kiosk, no session, no timeout, and the administrator is describing
something that already happened. What it reuses is the *resolution* logic, so
the backfill screen's auto-detection and the kiosk cannot disagree.

## Design notes

**`ResolveHistorical` asks about custody as it stood at an instant**, not as it
stands now. A device borrowed on the 15th and returned on the 18th must resolve
correctly even though it is on the shelf today — which is exactly why it is a
separate call rather than a flag on the live path.

```go
func (c *Checkout) ResolveHistorical(ctx, deviceID, userID string, at time.Time) (Action, error)
// custody at `at` is: no covering loan            → borrow
//                     covering loan, same user    → return   (closes it at `at`)
//                     covering loan, other user   → conflict
```
It calls the same `resolveAction` helper the live machine uses
([2.3b](2.3b-transition-table.md)), over `lending.CustodyAt(deviceID, at)`.

**A batch is one transaction — all rows or none.** A page of twelve rows where
row seven conflicts writes nothing. The administrator fixes row seven and saves
the page again; a half-saved page is worse than an unsaved one, because they
cannot tell which half.

**Conflicts are structured, not strings.** Each conflicting row returns the
conflicting loan (id, holder display, department, dates, origin) and the list of
resolutions the UI may offer: `truncate-existing`, `change-device`,
`discard-row`, `record-as-disputed`. The application never picks one.

**Preview is a convenience, never a grant.** `POST /v1/backfill` re-runs the
identical validation server-side. A stale preview must not be able to commit
something the current state forbids.

### Disputed entries

Some conflicts cannot be truthfully resolved: the paper says one thing, the
scanned record says another, and the administrator does not know which is right.
Discarding the row loses information; forcing it corrupts custody. So a disputed
row is stored **outside** the exclusion constraint and badged permanently:

- a `disputed boolean NOT NULL DEFAULT false` column on `loans`, added in
  [2.1](2.1-lending-module.md)'s migration
- the exclusion constraint's predicate becomes
  `WHERE (status <> 'written_off' AND NOT disputed)`
- a disputed loan **never** makes a device `on_loan` and is excluded from
  `HolderOf`, `OpenLoansFor` and the dashboard — it is a recorded claim, not a
  custody fact
- `GET /v1/reports/disputed` lists them so they are visibly unresolved rather
  than quietly absorbed

Deciding this in 2.1's migration rather than altering the constraint later is
the whole reason 2.1 lands first.

## Work items

### 2.4b.1 Resolution

- [x] `lending.CustodyAt(ctx, deviceID, at)` — landed in 2.1 together with
      `RecordHistorical`; nothing new needed here
- [x] `checkout.ResolveHistorical(ctx, deviceID, userID, at)` → `borrow` /
      `return` / `conflict`, sharing the live path's `machine.ResolveAction`
      (exported from `internal/machine` for exactly this caller — the helper
      itself is unchanged, so the kiosk and the backfill screen still decide
      in one place)
- [x] Explicit handling of the awkward inputs: `at` in the future (rejected
      per-row as an unresolved `borrowedAt`/`returnedAt`, plus the
      `ErrHistoricalTimeInFuture` sentinel on `ResolveHistorical` itself),
      `at` before the device existed (allowed, with a warning on the row),
      a row whose `returnedAt` precedes its `borrowedAt` (unresolved row
      naming `returnedAt`)

### 2.4b.2 Reference resolution

- [x] `deviceRef` accepts an asset tag **or** a scanned credential token — one
      field, so a USB scanner on the admin PC fills it with one trigger pull
      (a token-shaped ref goes through `credentials.Resolve`; anything else is
      an asset tag — asset tags never carry a valid token checksum)
- [x] `userRef` is a discriminated union: `userId`, `employeeNo`, scanned
      `token`, or `newUser{fullName, employeeNo, departmentId}` — exactly one
      discriminator set; two is rejected as ambiguous rather than guessed
- [x] Unresolvable refs come back as a per-row `status: "unresolved"` with the
      field named (and a reason), never as a batch-level failure — the
      administrator must be able to see all twelve rows' problems at once

### 2.4b.3 `RecordPaperBatch`

- [x] `RecordPaperBatch(ctx, batch PaperBatch, actor string) (PaperBatchResult,
      error)` — one transaction: create inline users, then insert loans in
      `borrowed_at` order, then publish one outbox event per loan
- [x] Inline user creation goes through `identityapi.CreateUser` with
      `registered_by = admin:<id>` (never `kiosk:`, INV-11) and is idempotent
      under retry via the batch's `Idempotency-Key` ([2.5](2.5-idempotency.md));
      an `ErrEmployeeNoTaken` during a batch re-uses the existing person rather
      than failing the page
- [x] Every row written with `origin='paper'`, `paper_ref`, `recorded_at`,
      `recorded_by` (INV-14); `origin` never rewritten afterwards (INV-15 —
      a paper return closing a kiosk-origin loan keeps `origin='kiosk'` and
      only adds `return_source='paper'`)
- [x] A row with only an OUT time creates an **open** loan, which sets the device
      `on_loan` — so the kiosk offers a normal return next time it is scanned
      (FR-79). A row with both times creates a `returned` loan and leaves the
      device alone (a device touched only by a status *change* — truncated
      open loan, closed open row — is reconciled at the end of the batch: on
      loan iff an undisputed open loan holds it)
- [x] `23P01` → `ErrOverlappingCustody`, caught per row (inside that row's
      SAVEPOINT, so the batch transaction survives) and re-presented as a
      structured conflict with the existing loan attached; a rejected batch
      rolls back entirely
- [x] Audit: one `backfill.batch_recorded` event with the row count and paper
      ref, plus the per-loan events the outbox already emits

### 2.4b.4 Preview

- [x] `PreviewPaperBatch` — the same validation (`applyPaperBatch` is the one
      code path both call), in a transaction that is always rolled back, so
      preview and commit cannot diverge in logic
- [x] Response keyed by `clientRowId` so the UI updates rows in place without
      reordering the administrator's work
- [x] `summary{ok, conflicts, newUsers}`

### 2.4b.5 Endpoints

- [x] `POST /v1/backfill/preview`, `POST /v1/backfill`, `GET /v1/backfill/last-entry`
      in `api/openapi.yaml`, admin-only, denied to kiosk tokens by the
      deny-by-default scope middleware (proven by the spec-driven suite from
      2.4 and the named test below)
- [x] Request/response schemas exactly as in
      [06](../../06-api-contract.md#paper-backfill), plus two additive fields
      the contract freeze has room for: `reason` on an unresolved row (the
      doc's example shows only `field`-free conflicts) and `committed` on the
      result envelope
- [x] `backfill.last-entry` returns when a page was last recorded, for the
      dashboard nag (204 when no paper page exists yet)

### 2.4b.6 Backdating is refused everywhere else

- [x] Every *live* write rejects a supplied past `borrowedAt` with
      `ErrBackdatedNotPermitted` at the module boundary
      (`lending.OpenLoan`, tolerance 5 s for scan-capture skew — landed in
      2.1, proven by `TestOpenLoanRejectsBackdatedBorrowedAt`), so only
      `RecordHistorical` can write history
- [ ] A test enumerating live mutating HTTP endpoints asserts this, so a new

## Deviations and discoveries

- **Migration `0011_disputed_open_loan_index.sql` is new.** 2.1's migration
  excluded disputed rows from the *exclusion* constraint but not from
  `loans_one_open_per_device_uk` — an open disputed row would have sat in the
  unique index and blocked every future real borrow of that device, the exact
  opposite of "recorded outside the constraint". The index is rebuilt with
  `WHERE status = 'open' AND NOT disputed`, matching the exclusion
  constraint's notion of custody.
- **Rebuilding that index exposed a latent fragility, now fixed.** With the
  index's OID now *later* than the exclusion constraint's, Postgres reports a
  second open loan as `23P01` (exclusion) rather than `23505` (unique) — error
  identity had silently depended on index creation order. `lending.translateLoanErr`
  now decides *semantically*: a custody violation with an existing open loan
  is `ErrDeviceAlreadyOnLoan` regardless of which constraint reported.
- **`machine.resolveAction` is now exported as `machine.ResolveAction`.** The
  helper itself is unchanged — exporting it is what lets
  `checkout.ResolveHistorical` share it with the live table literally rather
  than by re-implementation.
- **A "return" row closes the covering loan rather than inserting a second
  loan** (`lending.CloseHistoricalAt`): it moves `returned_at` earlier when
  already set (the `truncate-existing` resolution) or sets it for an open
  loan, fills paper provenance only where the loan carries none, and refuses
  to touch disputed rows. `ErrAlreadyEndedBefore` — the paper claims a return
  the system already recorded earlier — is a per-row warning, not an error:
  the system was already right, or righter.
- **`change-device` is a client-side resolution**: by save-time the asset tag
  has been edited, so a committed row still carrying it is rejected as
  unresolved with that instruction, rather than the server guessing at a
  different device.
- **The commit's rejection is deliberately lean** (409/422 + `clientRowIds`
  in extensions): the structured per-row comparison is what the preview is
  for, and the admin screen re-previews on any rejection.

## Risks

| Risk | Mitigation |
|---|---|
| An administrator resolves conflicts by forcing everything through | `record-as-disputed` exists precisely so forcing is not the easy path, and disputed rows are permanently visible in a report |
| Preview and commit drift | Both call one validation function; `TestPreviewAndCommitAgree` |
| Inline user creation duplicates people on retry | Idempotency key covers the batch; live-uniqueness index on `employee_no` catches the rest |
| The feature is too slow to use and paper piles up | NFR-9b (a row in under 20 s) is a Phase 4 UI concern, but the API shape here — batch preview keyed by client row id — is what makes it reachable |
