# 2.5 — Idempotency

**Parent:** [§2.5](../phase-2-lending-checkout.md) · **Depends on:** 2.0 ·
**Unblocks:** 2.6, and the Phase 5 offline queue
**Estimate:** 0.5 d · **Risk:** low

## Goal

A network blip must never duplicate or lose a transaction (NFR-5). The client
debounce cannot help — it is lost on reload and on retry — so the server stores
the response for every keyed `POST` for 24 h and replays it verbatim.

## Design notes

**Key derivation for the kiosk** is documented and shared:
`sha256(session_id | device_id | action | minute_bucket)`. The minute bucket is
what makes a *deliberate* re-borrow of the same device a minute later a new
transaction rather than a replay. It is documented in the OpenAPI description of
the header and duplicated in `packages/domain` for the kiosk to compute
identically.

**Scope of a key** is `(key, actor)` — a kiosk's key never collides with an
admin's. Store the actor with the record.

**A replay returns the stored response, including its status code**, with
`Idempotency-Replayed: true`. Same key + different body ⇒ `idempotency-mismatch`
(422), compared on a hash of the canonical request body, not the raw bytes
(whitespace differences from a retrying client must not be a mismatch).

**In-flight requests.** A retry that arrives while the first is still running
must not execute twice. Insert the key row first, inside the request's own
transaction, with the unique constraint doing the work: the second insert gets
`23505` and returns `409 session-conflict` with `Retry-After: 1`. Simpler and
more honest than a lock table.

## Work items

### 2.5.1 Migration — `migrations/0009_idempotency.sql`

Numbered `0009`, not `0008`: the phase-2 README's own migration table reserves
`0008` for checkout ([2.3a](2.3a-checkout-foundations.md)), which hadn't landed
yet when this sub-phase was built. Goose tolerates the gap fine (verified with
the `goose` CLI directly) as long as `0008` is added and applied before `0009`
on any real database — true here since nothing is deployed yet.

- [x] ```sql
      CREATE TABLE idempotency_keys (
          key           text NOT NULL,
          actor         text NOT NULL,
          request_hash  bytea NOT NULL,
          status_code   integer,
          response_body jsonb,
          created_at    timestamptz NOT NULL DEFAULT now(),
          completed_at  timestamptz,
          PRIMARY KEY (key, actor)
      );
      CREATE INDEX idempotency_keys_created_idx ON idempotency_keys (created_at);
      ```
- [x] Goose down — verified with the `goose` CLI directly (up then down)

### 2.5.2 Middleware

- [x] `internal/platform/httpx/idempotency.go`, wrapping mutating handlers
- [x] No header on a `POST` ⇒ pass through (the admin console will not always
      send one); the kiosk's session endpoints **require** it, enforced in the
      handler, so a missing key on the hot path is a `validation-failed` —
      **not built yet**: there is no kiosk session endpoint until
      [2.6](2.6-api-surface.md), so this requirement has nowhere to live. Noted
      as a 2.6 follow-up rather than invented here
- [x] Response capture via a recording `http.ResponseWriter`, persisted only for
      2xx; a 5xx is not stored, so a retry after a server fault genuinely retries.
      Mechanically this means the placeholder `idempotency_keys` row inserted at
      the start is *deleted* for a non-2xx response — the doc doesn't spell out
      the delete, but it's required: without it, a retry's own INSERT would hit
      the same still-present PK and get 409 forever instead of ever retrying
- [x] `Idempotency-Replayed: true` on replay, original status code preserved
- [x] Bodies larger than 64 KB are not stored (none of ours approach it); log and
      pass through rather than truncating
- [x] **Not in the original list**: the concurrency guard itself. "Insert first,
      let the unique constraint decide" (this file's own design notes) needed a
      concrete implementation: `INSERT` succeeds ⇒ this request owns the key,
      run the handler, then `UPDATE`/`DELETE` the row depending on the outcome;
      `INSERT` fails `23505` ⇒ `SELECT` the existing row — `completed_at NULL`
      is "still in flight" (409), `completed_at` set is a genuine replay
      (compare the hash)
- [x] **Deviation**: response equality on replay is JSON-*semantic*, not
      byte-identical — `response_body` is `jsonb` per this file's own schema
      above, and Postgres reformats whitespace on that column's round trip.
      Caught by `TestReplayReturnsStoredResponse` initially failing on a raw
      byte comparison; fixed by comparing parsed JSON, which is the same
      canonical-rather-than-raw principle this file already applies to
      request-body comparison

### 2.5.3 Retention

- [x] A 24 h sweep, folded into the outbox dispatcher's loop from
      [2.2](2.2-events-and-outbox.md) rather than a second goroutine — added
      `Dispatcher.AddSweep(fn)` to 2.2's `events` package (not in that
      sub-phase's own list either, since nothing needed it yet) so this sub-phase
      could register `httpx.SweepExpiredIdempotencyKeys` on the existing loop
      instead of either duplicating it or reaching into `events`'s internals

## Tests

Integration (`test/integration/idempotency_test.go`):
- [x] `TestReplayReturnsStoredResponse` — one loan row, second call carries the
      replay header and the identical (JSON-equivalent) body. Uses a real
      `lending.OpenLoan` call as the wrapped handler — checkout's own HTTP
      endpoints don't exist until 2.6, but "one loan row" doesn't need them;
      2.1's lending module is enough to make the assertion literal rather than
      simulated
- [x] `TestSameKeyDifferentBodyIsMismatch` — 422 `idempotency-mismatch`
- [x] `TestWhitespaceOnlyBodyDifferenceIsNotAMismatch`
- [x] `TestConcurrentSameKeyOneWins` — two simultaneous identical requests: one
      executes, one gets 409, exactly one loan row. Made deterministic (not
      merely probable) with a channel barrier: the first request's handler
      signals it has started — and therefore that its row is inserted with
      `completed_at NULL` — before the second request is sent
- [x] `TestErrorResponsesAreNotStored` — force a 500, retry, the handler runs again
- [x] `TestKeysAreScopedByActor`
- [ ] `TestDeliberateReborrowInNextMinuteIsNewTransaction` — **deferred to 2.6**.
      This test is about the *kiosk's specific key-derivation algorithm*
      (`sha256(session_id|device_id|action|minute_bucket)`), not about the
      generic middleware built here — there is no kiosk scan handler yet to
      compute that key, and the algorithm itself is meant to live in the
      OpenAPI header description plus `packages/domain` (frontend TypeScript),
      not in `internal/platform/httpx`. Writing a hollow version of this test
      against a fake key-deriver would prove nothing beyond "subtraction
      works"; the real test belongs with the code that computes the key

## Risks

| Risk | Mitigation |
|---|---|
| Storing responses that contain a plaintext token | The credential endpoints marked `x-sensitive` are excluded from the store, same allowlist the logging middleware uses |
| Table growth | 24 h sweep; at ten transactions a day this is decorative, but it is the right default |
