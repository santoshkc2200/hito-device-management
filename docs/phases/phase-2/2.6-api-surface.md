# 2.6 — API surface: sessions, loans, dashboard, SSE, kiosk scope

**Parent:** [§2.6](../phase-2-lending-checkout.md) · **Depends on:** 2.3c, 2.5 ·
**Unblocks:** Phases 3 and 4 (both start from this contract)
**Estimate:** 1.5 d · **Risk:** medium — the contract freezes at the end of it

## Goal

Put everything built so far behind HTTP, exactly as
[06](../../06-api-contract.md) specifies, and close the kiosk scope gap. After
this sub-phase the whole product is demonstrable with `curl`, and Phases 3 and 4
can proceed in parallel against a frozen contract.

## Design notes

**Spec first, always.** Edit `api/openapi.yaml`, run `task generate`, let the Go
compiler fail on unimplemented handlers, then implement. Generated code is
committed; CI fails on a diff.

**Rejections are `200`.** `outcome.kind = "rejected"` with a server-authored
message. HTTP errors are reserved for genuine faults — bad token format, expired
session, auth failure, server error. This is not a stylistic choice: modelling
"held by someone else" as a `4xx` would force the kiosk to parse errors to drive
its main screen.

**The scan response is complete.** Session + outcome + open loans + message, so
the kiosk never reconstructs anything and never needs a second call.

**Kiosk scope, at last.** The middleware today authenticates a kiosk token and
lets it reach every route. Fix it here: an allowlist of `(method, path-pattern)`
pairs, everything else `403 forbidden`. The allowlist lives in
`internal/platform/auth/scope.go` and is exercised by the spec-driven test from
[2.4](2.4-unrecognised-cards.md).

## Work items

### 2.6.1 Spec

- [ ] Session endpoints: `POST /v1/sessions`, `GET /v1/sessions/{id}`,
      `POST /v1/sessions/{id}/scan`, `POST /v1/sessions/{id}/return-loan`,
      `POST /v1/sessions/{id}/close`, `DELETE /v1/sessions/{id}`
- [ ] Loans: `GET /v1/loans` (filters: status, origin, userId, deviceId, from,
      to, cursor), `GET /v1/loans/{id}`, `POST /v1/loans/{id}/force-return`,
      `POST /v1/loans/{id}/write-off`, `GET /v1/devices/{id}/loans`,
      `GET /v1/users/{id}/loans`
- [ ] `GET /v1/dashboard` — on loan now, overdue, availability by category,
      turned-away counts from [2.4](2.4-unrecognised-cards.md), last backfill entry
- [ ] `GET /v1/events/stream` — `text/event-stream`
- [ ] Backfill endpoints from [2.4b](2.4b-paper-backfill.md)
- [ ] Kiosks: `GET /v1/kiosks`, `POST /v1/kiosks`, `POST /v1/kiosks/{id}/rotate-token`,
      `POST /v1/kiosks/{id}/disable` — token returned exactly once, `x-sensitive`
- [ ] Pairing, for Phase 3's iPad: `POST /v1/kiosks/{id}/pairing-code` (admin) →
      `{ code, expiresAt }`, and `POST /v1/kiosks/pair` (**unauthenticated**,
      rate-limited to five attempts per minute per IP) → `{ code }` →
      `{ kioskId, name, token }`. Both `x-sensitive`, both `Cache-Control: no-store`;
      an invalid, consumed or expired code answers the same `404 pairing-code-invalid`.
      They are specified here, while the contract is still open, rather than as an
      additive change after [2.9](2.9-contract-freeze-and-demo.md)'s freeze
- [ ] `Idempotency-Key` request header documented on every `POST`, with the
      kiosk's derivation formula in its description
- [ ] Every new error type from [06](../../06-api-contract.md#error-format)
      registered in the `Problem` documentation: `device-on-loan`,
      `overlapping-custody`, `backdated-not-permitted`, `device-unavailable`,
      `user-suspended`, `session-expired`, `session-conflict`,
      `idempotency-mismatch`, `credential-*`
- [ ] `security` per operation: `kioskToken` on the six session operations,
      `adminSession` everywhere else
- [ ] `task generate` → commit spec + generated Go + generated TS together

### 2.6.2 Handlers

- [ ] `internal/apiserver/sessions.go`, `loans.go`, `dashboard.go`, `backfill.go`,
      `kiosks.go`, `events_stream.go` — following the existing file-per-resource
      convention
- [ ] `Server` gains `checkout`, `lending` and the event bus; `cmd/hdms-api`
      updated to construct them
- [ ] One error-mapping function from module sentinels to RFC 9457 problems,
      shared by every handler, so `ErrDeviceAlreadyOnLoan` cannot map to two
      different types in two places
- [ ] `extensions` on `device-on-loan` carries `deviceId` and
      `holderDepartment` — **never** the holder's name (the name appears only in
      the in-session `message`, where the borrower is standing at the kiosk)
- [ ] `Cache-Control: no-store` on every response carrying a token

### 2.6.3 Kiosk scope enforcement

- [ ] `internal/platform/auth/scope.go`: `KioskAllowed(method, routePattern) bool`
      over an explicit allowlist
- [ ] `auth.Middleware` consults it after validating the kiosk token; denials are
      `403 forbidden` and produce an audit row (docs/09: every check failure
      produces an audit row)
- [ ] Route patterns come from the router, not from string matching on the raw
      path, so `/v1/users/{id}` and `/v1/users` are distinguishable
- [ ] `kiosks.last_seen_at` stamped on every authenticated kiosk request (FR-57)

### 2.6.4 SSE

- [ ] `GET /v1/events/stream`: subscribes to the bus, writes `id:`, `event:`,
      `data:` frames, flushes per event
- [ ] Heartbeat comment (`: ping`) every 15 s so proxies do not idle out the
      connection
- [ ] `Last-Event-ID` resume: replay from `outbox` where `id > lastEventID` and
      `published_at IS NOT NULL`, then attach to the live bus — the outbox is the
      log that makes resume possible without a second store
- [ ] Per-connection bounded buffer; a slow consumer is dropped with a logged
      warning rather than growing memory
- [ ] Admin-only; the kiosk does not need it and is not allowed it
- [ ] Graceful close on client disconnect (`r.Context().Done()`) and on shutdown

### 2.6.5 Rate limiting

- [ ] 60 requests/minute per kiosk token and per admin session, `429` with
      `Retry-After` — generous enough that a stuck scanner trigger cannot generate
      load, low enough not to interfere with real use

## Exit criteria

- [ ] Every scenario in [04](../../04-scanning-and-checkout-flows.md) is
      reproducible over `curl`/HTTP in both scan orders
- [ ] SSE delivers a loan event within 1 s of the transaction, and resumes
- [ ] The kiosk token reaches exactly six operations and no others; `/v1/kiosks/pair`
      is reachable with no token at all and nothing else is
- [ ] A pairing code exchanges for a working kiosk token exactly once
- [ ] `task generate` produces no diff; the TS client compiles against the spec
- [ ] Every registered error type in [06](../../06-api-contract.md) is produced
      by at least one test

## Risks

| Risk | Mitigation |
|---|---|
| Contract churn blocks Phases 3 and 4 | The freeze is [2.9](2.9-contract-freeze-and-demo.md)'s explicit gate; changes after it need a version bump |
| SSE connections leak goroutines | Bounded buffers, context cancellation, and the 24 h soak in Phase 5; a goroutine-count assertion in the load test |
| Scope allowlist drifts from the router | Patterns taken from the router; the spec-driven test enumerates every operation |
