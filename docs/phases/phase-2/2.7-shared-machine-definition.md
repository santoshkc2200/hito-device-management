# 2.7 — The shared machine definition

**Parent:** [§2.7](../phase-2-lending-checkout.md) · **Depends on:** 2.3b ·
**Unblocks:** Phase 3's kiosk machine and the parity test
**Estimate:** 0.5 d · **Risk:** low now, high if skipped

## Goal

The machine is specified once and implemented twice — authoritatively in Go,
mirrored in XState v5 on the kiosk for instant visual feedback. The only thing
making that duplication safe is a single definition both sides consume, plus a
scenario fixture replayed through both. Both artefacts are produced here, in
Phase 2, so Phase 3 starts from them rather than inventing a second opinion.

## Design notes

**Generated, not hand-written.** `session-machine.json` is emitted from the Go
table (`machine.Table()`) by a small generator, and CI asserts the committed file
matches a fresh generation. A hand-maintained JSON file would drift from the Go
table within a fortnight, which is exactly the failure ADR-0004 lists as the
cost of the mirrored design.

**The frontend never decides an outcome.** The JSON gives the kiosk states,
transitions and timeouts — enough to know which screen to paint and when to show
the countdown ring. It deliberately does **not** encode borrow-vs-return
resolution, which requires custody knowledge the kiosk does not have and must
not guess.

## Work items

### 2.7.1 `packages/domain/session-machine.json`

- [x] `cmd/hdms-cli export machine` (or `go run ./cmd/hdms-cli`) writing the file
      from `machine.Table()`
- [x] Shape: `{ version, states: { <state>: { on: { <inputClass>: { action, target, clearsPending } }, after: { <ms>: { target } } } } }`
- [x] Stable key ordering so the file diffs cleanly
- [x] Timeouts included (45 s / 25 s), from the same table, so the kiosk's
      countdown cannot disagree with the server's expiry
- [x] A `version` field bumped whenever the table changes, which Phase 3's kiosk
      logs at startup — a kiosk running an old build against a new server is then
      diagnosable from one log line
- [x] `packages/domain/src/session-machine.ts` re-exporting the JSON with types,
      alongside the existing `token.ts`

### 2.7.2 `packages/domain/scenarios.json`

- [x] The full scenario fixture: an array of
      `{ name, initialState, inputs: [{ class, …fields }], expected: [{ action, state }] }`
- [x] Covers all seven worked scenarios of
      [04](../../04-scanning-and-checkout-flows.md) plus every matrix cell,
      generated from the same Go table test so the two cannot diverge
- [x] Includes the timeout and duplicate cases, which are the ones a
      hand-written fixture always forgets

### 2.7.3 Go side

- [x] A Go test drives the transition table **from the JSON file**, not from the
      Go map, so the exported artefact is proven to be a faithful description of
      the implementation rather than a well-intentioned summary
- [x] `task generate` (or a `task export:machine`) regenerates both files; CI
      fails on a diff, the same guarantee the OpenAPI pipeline has

## Tests

- [x] `TestMachineJSONMatchesTable` — regenerate in-memory, compare byte for byte
- [x] `TestScenariosReplayThroughGoMachine` — every scenario produces its
      expected action/state sequence
- [x] `TestScenariosCoverEveryMatrixCell` — a coverage assertion over the fixture,
      so the Phase 3 parity test is known to be exhaustive before anyone relies
      on it

## Exit criteria

- [x] `packages/domain/session-machine.json` and `scenarios.json` committed and
      regenerable
- [x] The Go tests drive the transition table from the JSON
- [x] CI fails if either file is stale
- [x] Phase 3 can build the XState config with no further questions about the
      rules

## Risks

| Risk | Mitigation |
|---|---|
| The JSON becomes a second, subtly different source of truth | It is generated, and CI diffs it |
| The fixture is too thin to catch drift | Generated from the matrix test, with a coverage assertion |
