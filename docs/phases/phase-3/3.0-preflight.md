# 3.0 — Preflight

**Parent:** new · **Depends on:** Phase 2 ([2.6](../phase-2/2.6-api-surface.md),
[2.7](../phase-2/2.7-shared-machine-definition.md)) · **Unblocks:** everything
**Estimate:** 0.5 d · **Risk:** low — the contract risk that used to live here
was moved into Phase 2, where the spec is still open

## Goal

Settle the three things Phase 3 assumes exist: an authenticated API client, a
test harness, and a decision about where shared UI lives. Then verify the pairing
flow Phase 2 built actually works from a browser.

## Design notes

**Pairing is Phase 2's now.** The two endpoints — `POST /v1/kiosks/{id}/pairing-code`
and `POST /v1/kiosks/pair` — are specified in [2.6](../phase-2/2.6-api-surface.md)
and implemented alongside kiosk registration in
[2.0](../phase-2/2.0-preflight.md), because doing it there costs one line in an
open spec and doing it here costs an amendment to a frozen one. This sub-phase
consumes them; it does not define them.

**Why a pairing code rather than pasting the token.** The kiosk token is
long-lived; typing one on an iPad on-screen keyboard, in a corridor, with a paired
scanner suppressing that keyboard, is the worst possible handling of a credential.
A short numeric code valid for ten minutes that exchanges *once* for the real
token keeps it out of human hands entirely.

## Work items

### 3.0.1 Verify the pairing flow from a browser

The endpoints and their integration tests belong to Phase 2. What is unproven is
the *browser* half — CORS, the unauthenticated route reaching through the proxy,
and the token surviving a standalone-mode reload.

- [ ] `hdms-cli kiosk register` + `hdms-cli kiosk pairing-code` produce a code
      that a fetch from the kiosk origin can redeem
- [ ] CORS and the Caddy config (`deploy/Caddyfile`) allow `POST /v1/kiosks/pair`
      unauthenticated from the kiosk origin, and nothing more
- [ ] The redeemed token persists in `localStorage` across a full reload
- [ ] Anything missing here is a Phase 2 defect, filed against
      [2.6](../phase-2/2.6-api-surface.md) rather than patched around in the client

### 3.0.2 Authenticated API client wiring

`apps/kiosk` currently sets a base URL and nothing else.

- [ ] `apps/kiosk/src/lib/api.ts`: configure the generated client with the base
      URL, the `Authorization: Bearer <kiosk token>` header from local storage, and
      `Cache-Control: no-store` on requests carrying one
- [ ] `Idempotency-Key` on every POST, derived deterministically so a retry of the
      *same* user action reuses it and a new action does not:
      `<kioskId>:<sessionId>:<monotonic scan sequence>`. The formula is documented
      in the spec ([2.6](../phase-2/2.6-api-surface.md)); implement *that* formula,
      do not invent a second one
- [ ] `problem.ts`: parse `application/problem+json` into a discriminated union
      keyed on `type`, with an `unknown-problem` fallback that carries a support
      code — the kiosk branches on `type`, never on a message string
- [ ] Unauthenticated / unpaired state is a first-class result, not a thrown
      error: it drives the pairing screen in [3.7](3.7-pwa-and-kiosk-mode.md)
- [ ] A single `QueryClient` with the retry policy [3.8](3.8-resilience.md)
      tightens later; the mutation for `scan` is created here so every screen uses
      one code path

### 3.0.3 Test harness

- [ ] `@axe-core/playwright` and `vitest-axe` installed; one worked example of
      each committed, so 3.3 onward has a pattern to copy rather than a decision
      to make
- [ ] `playwright.config.ts` gains an `api` project fixture: `docker compose up -d db api caddy`,
      `hdms-cli migrate`, `hdms-cli seed`, and a kiosk registered + paired, with the
      resulting token injected into `localStorage` by a `storageState` setup project
- [ ] A deterministic fake camera: a script that renders a known device QR to PNG
      and converts it to Y4M, plus the Chromium flags
      `--use-fake-device-for-media-stream --use-file-for-fake-video-capture=…`.
      Generated by a task, not committed as a binary blob
- [ ] `test/scan.ts` Playwright helper that dispatches a token as scanner-speed
      `keydown` events (8 ms gaps, trailing `Enter`) — the same thing the hardware
      produces, and the only way E1–E13 stay honest
- [ ] `pnpm --filter kiosk test` picks up `src/test/setup.ts` with
      `@testing-library/jest-dom` (already present) plus fake-timer defaults

### 3.0.4 Two decisions, written down

- [ ] **Shared UI:** `packages/ui` keeps design tokens and `cn` only; components
      stay app-local. The kiosk's primary button is ≥ 64 px tall with a press
      animation the admin console must not inherit. Record it in
      `packages/ui/README.md` so Phase 4 does not merge the two sets "for
      consistency"
- [ ] **Kiosk config:** what lives in local storage (kiosk id, kiosk name, token,
      mute flag, enabled sources, attendant PIN hash) versus `sessionStorage`
      (the current session id only). Written as one typed module,
      `apps/kiosk/src/lib/kiosk-config.ts`, with a schema version field — an iPad
      that has been in a corridor for a year will be running a stale shape one day

## Tests

- [ ] `TestPairing*` integration tests above (Go)
- [ ] `api.test.ts` — the idempotency key is stable across a retry of the same
      scan and different across two scans
- [ ] `problem.test.ts` — a known type maps to its variant; an unknown type maps
      to `unknown-problem` with a support code and never throws
- [ ] `kiosk-config.test.ts` — a stale schema version is discarded, not crashed on
- [ ] The Phase 0 smoke e2e still passes against the new client wiring

## Exit criteria

- [ ] A browser at the kiosk origin can exchange a pairing code for a kiosk token
      and make an authenticated `POST /v1/sessions`
- [ ] `task generate` produces no diff
- [ ] Playwright can start the API stack, seed it, and drive a simulated scan
      through the helper
- [ ] The two decisions in 3.0.4 exist as committed prose, not as folklore

## Risks

| Risk | Mitigation |
|---|---|
| A pairing gap is discovered here and patched client-side | Anything missing is filed as a Phase 2 defect against 2.6; the client does not grow a workaround for a contract hole |
| The e2e stack is slow enough that nobody runs it locally | Compose stack reused between runs (`reuseExistingServer`), seeding idempotent, and the whole suite budgeted at under three minutes in [3.11](3.11-e2e.md) |
| The pairing token ends up in a log or a URL | It is a POST body, `no-store`, redacted in the client's error path; asserted by a test that greps captured logs |
