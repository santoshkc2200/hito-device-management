# 3.11 — End-to-end tests and the CI stage

**Parent:** [§3.11](../phase-3-kiosk-app.md) · **Depends on:** 3.3b, 3.8 ·
**Unblocks:** 3.12
**Estimate:** 1.5 d · **Risk:** medium — flaky e2e is worse than no e2e, because
it teaches everyone to ignore a red build

## Goal

Scenarios E1–E13 from [10](../../10-testing-strategy.md) running against a real
API and a real Postgres, with scans delivered as keyboard events, plus the CI
stage that does not currently exist.

## Design notes

**Keyboard events are not a simulation.** A Bluetooth imager types. Dispatching
`keydown` sequences at 8 ms gaps is exactly what the hardware produces, so these
tests exercise the real wedge interpreter and the real suppression logic — this is
high fidelity, not an approximation. (The one thing it cannot cover is the
scanner's own configuration and physics, which is [3.10](3.10-hardware-validation.md)'s
job.)

**Assert against the database, not only the screen.** "Borrowed" on screen with no
loan row is the failure this suite exists to catch. Each scenario checks the API's
view of the world after the fact — `GET /v1/loans` with the seeded ids — as well as
what the borrower saw.

**Determinism or delete it.** Every scenario seeds its own users and devices with
unique tags; nothing depends on ordering or on leftovers. Time-dependent scenarios
(E10's timeout) use short server-side TTLs supplied by test configuration rather
than by waiting 45 real seconds. A test that needs a `waitForTimeout` to pass is
rewritten, not retried.

**E13 is the awkward one.** Playwright's fake-device flags plus a generated Y4M
containing a rendered device QR, from [3.0](3.0-preflight.md). It stays in the
suite rather than being manually verified, because the camera path is the one
nobody exercises by hand until it is already needed.

**E14–E19 belong to Phase 4.** They are admin-console journeys; the file layout
here leaves room for them rather than pretending they are out of scope.

### 3.11.3 CI stage

- [ ] A new `e2e` job in `.github/workflows/ci.yml`: build the frontend, bring up
      the compose stack, run Playwright, upload traces on failure
- [ ] `axe` assertions from [3.9](3.9-visual-design.md) run in the same job over
      every screen
- [ ] Job budgeted under 5 minutes; if it exceeds that, scenarios are parallelised,
      not deleted
- [ ] Flake policy written into the job's README section: a flaky test is quarantined
      *with an issue* within a day, or fixed; it is never left retrying quietly

## Exit criteria

- [ ] E1–E13 green locally and in CI, three consecutive runs with no retries
- [ ] Every scenario asserts both the screen and the API's view of the data
- [ ] E7 additionally asserts, via the API, that the user count is unchanged
- [ ] No `waitForTimeout` anywhere in the suite
- [ ] CI fails on an axe violation
- [ ] `task e2e` runs the same suite locally with one command

## Risks

| Risk | Mitigation |
|---|---|
| Flaky suite trains everyone to ignore red | No arbitrary waits, per-test seeding, an explicit flake policy, three-clean-runs exit criterion |
| The compose stack makes CI slow enough to skip | Under-5-minute budget, cached images, and the stack reused locally |
| E13's fake camera breaks on a Chromium upgrade | The Y4M is generated by a task, and the failure mode is loud and specific rather than mysterious |
| E2E becomes the place every rule gets tested | The pyramid in [10](../../10-testing-strategy.md) is deliberate: rules belong in the Go integration tests, journeys belong here |
