# 3.1b — `HidWedgeSource`

**Parent:** [§3.1](../phase-3-kiosk-app.md) · **Depends on:** 3.1a ·
**Unblocks:** 3.10, 3.11
**Estimate:** 1 d · **Risk:** high — timing-dependent, and the primary input path
for every transaction the product will ever record

## Goal

Turn a keystroke stream into scans, reliably, on a device that also has a person
tapping it. This is the one piece of the kiosk where "works on my laptop" is worth
very little: [3.10](3.10-hardware-validation.md) is where it is actually judged.

## Design notes

**Timing is the only signal.** A Bluetooth imager pairs as a keyboard and types
2–20 ms apart; a human types 80–300 ms apart. `MAX_INTERVAL_MS = 35` and
`MIN_LENGTH = 6` separate them. Both constants are exported and covered by tests
at the boundaries, because the next scanner model will be the reason to move them.

**Listen on `window`, in the capture phase.** A kiosk whose scans depend on which
element has focus is one stray tap away from silently dropping transactions. The
capture phase also lets the terminating `Enter` be suppressed before it activates
a focused button — otherwise the last scan of a session cheerfully presses
"Done".

**Everything about the buffer is a failure mode.** A partial read (the trigger
released mid-barcode) must not poison the next scan: a 100 ms idle timer clears
it. A long buffer that never sees `Enter` must not grow without bound: cap it and
drop. `keydown` with `e.key.length === 1` ignores modifiers and dead keys; an
`Escape` clears immediately.

**Scanner sleep is a real-world defect, not an edge case.** A Bluetooth scanner
that has idled overnight takes about a second to reconnect and the first trigger
pull is lost. The kiosk cannot fix that, but it can *say* so: a "Scanner ready"
heartbeat derived from recent keystroke activity, and after a long idle a "press
the trigger once to wake it" hint. The alternative is a nurse concluding the
system is broken at 07:00 on day one.

**Availability is inferred, never queried.** There is no API that says "a scanner
is paired". `isAvailable()` returns true always; the heartbeat reports *observed*
activity — last successful scan within the freshness window — and the idle state
is a hint, not a claim.

## Work items

### 3.1b.1 The interpreter

- [ ] `packages/scan/src/hid-wedge.ts` — a pure function/class over
      `{ key, timeStamp }` events, so it is testable without a DOM
- [ ] Inter-key threshold, minimum length, `Enter` termination, `Escape` clear
- [ ] 100 ms idle-buffer reset on a timer, cancelled on each keystroke
- [ ] Buffer cap (say 64 chars) after which the buffer is dropped and a
      `source-state` warning is emitted
- [ ] Lowercase and stray-hyphen tolerance is `parseToken`'s job, not the wedge's —
      the wedge emits exactly what was typed

### 3.1b.2 The DOM source

- [ ] `HidWedgeSource implements ScanSource` — `window.addEventListener('keydown', h, { capture: true })`
      on `start()`, removed on `stop()`
- [ ] `preventDefault()` + `stopPropagation()` on the terminating `Enter` **only
      when a scan was emitted**, so a genuine keyboard Enter (the attendant's
      keypad) still works
- [ ] Keystrokes are ignored while a text input is focused *and* the sequence is
      human-speed — the attendant typing in the keypad must not emit scans
- [ ] Heartbeat: `lastActivityAt`, an `isFresh` flag over a configurable window
      (default 60 s), exposed through `source-state` events for the idle screen's
      indicator

### 3.1b.3 Diagnostics

- [ ] A hidden diagnostics view (five taps on the kiosk name, PIN-gated) showing
      the last ten raw sequences with their inter-key timings — the only realistic
      way to debug "the scanner sometimes doesn't work" from a corridor, and the
      first thing 3.10 will want
- [ ] Raw sequences are held in memory only, capped at ten, and never logged or
      sent anywhere — they are credential tokens

## Exit criteria

- [ ] Every test above green, with no real `sleep` anywhere in the file
- [ ] A scan emitted while a button has focus does not activate that button
- [ ] The attendant keypad ([3.4](3.4-attendant-manual-entry.md)) can be typed in
      with the wedge attached without emitting a scan
- [ ] The heartbeat indicator reflects reality on the real device — deferred to
      [3.10](3.10-hardware-validation.md), and explicitly *not* claimed done here
- [ ] `MAX_INTERVAL_MS` and `MIN_LENGTH` carry a comment saying they are
      **untuned** and derived from the literature, not from this hospital's
      scanner — the imager is not available yet ([3.10](3.10-hardware-validation.md)),
      and a constant that looks measured but is not is worse than one that admits it

## Risks

| Risk | Mitigation |
|---|---|
| The timing heuristic is right in jsdom and wrong on iPadOS | 3.10 runs the real checklist; the diagnostics view records actual inter-key timings from the real scanner so the constants are tuned from data, not from taste |
| Scanner sleep drops the first scan of the morning | Heartbeat + wake hint here; documented in the runbook; retested in 3.10's "slept 30+ minutes" item |
| A scan lands while the keypad is open and corrupts the entry | Focus-aware suppression, plus a dedicated test |
| The terminating Enter activates a focused control | Capture-phase `preventDefault` on emit, plus a test |
