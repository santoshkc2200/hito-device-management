# 3.1c — `CameraSource`

**Parent:** [§3.1](../phase-3-kiosk-app.md) · **Depends on:** 3.1a ·
**Unblocks:** 3.10, 3.11 (E13)
**Estimate:** 1 d · **Risk:** medium — it is the fallback nobody exercises until
the scanner has already failed, which is the worst moment to discover it is broken

## Goal

When the scanner is flat, unpaired or missing, the iPad's own camera must decode a
device label at arm's length in corridor lighting. Toggled from a persistent
button — **"Scanner not working? Use camera"** — and back off automatically after
a successful read.

## Design notes

**Safari has no `BarcodeDetector`.** The `barcode-detector` ponyfill (already a
dependency of `packages/scan`) uses the native implementation where it exists and
a zxing WASM build (~400 KB) elsewhere, which on the iPad is always. That bundle
must be precached by the service worker ([3.7](3.7-pwa-and-kiosk-mode.md)) — a
fallback that needs a good network to load is not a fallback.

**Narrow the format list.** `qr_code`, `data_matrix`, `code_128` and nothing else.
Every extra format is CPU spent on a decode that will never match, on a device
whose thermal budget is already being shared with a video stream.

**Decode small, crop large.** Downscale frames to roughly 640 px on the long edge
and decode at ~10 fps; only the crop of a candidate region goes through at full
resolution. Decoding every full-resolution frame heats the iPad, drains the
battery the mount is supposed to be charging, and does not improve the read rate.

**HTTPS is not optional.** `getUserMedia` is unavailable on plain HTTP outside
`localhost`. Dev already serves the kiosk over mkcert-issued TLS
(`apps/kiosk/vite.config.ts`); production needs a real certificate on the internal
hostname, which [09](../../09-security-privacy-ops.md) flags as a common late
surprise. Nothing here works around it.

**Permission is granted once per origin** and survives in standalone mode. A
denied permission is a *state*, not an error: the button explains what to do
rather than the app looking broken.

**Stopping means stopping.** Every track released, the timer cleared, the video
element detached. A camera left running is a privacy incident with an LED on it.

## Work items

### 3.1c.1 The source

- [ ] `packages/scan/src/camera.ts` — `CameraSource implements ScanSource`
- [ ] `isAvailable()`: `navigator.mediaDevices?.getUserMedia` present **and**
      permission not `denied` (via `navigator.permissions.query` where supported,
      falling back to an attempt)
- [ ] `start()`: `getUserMedia({ video: { facingMode: 'environment', width: { ideal: 1280 } } })`,
      a detached `<video>` playing inline (`playsinline` and `muted` are both
      required on iOS or the stream will not start)
- [ ] Decode loop on `requestAnimationFrame` throttled to ~10 fps, drawing to an
      `OffscreenCanvas` where available
- [ ] `stop()`: stop every track, cancel the loop, null the `srcObject`
- [ ] Emit through the router like any other source; the debounce and the token
      pre-check are inherited, not reimplemented

### 3.1c.2 Viewfinder UI

- [ ] `CameraOverlay` in `apps/kiosk`: live preview, a target frame, a "point at
      the barcode" hint, and a large Cancel
- [ ] Torch toggle where `track.getCapabilities().torch` exists; hidden, not
      disabled, where it does not
- [ ] Auto-exit back to scanner mode on a successful read, with the normal scan
      feedback ([3.6](3.6-feedback.md)) rather than a separate camera-specific one
- [ ] Denied-permission state: what to tap in iOS Settings, plus the attendant
      manual-entry route ([3.4](3.4-attendant-manual-entry.md)) as the way out
- [ ] Toggle button is present on every screen where a scan is expected, not only
      on idle — the scanner can die mid-session

### 3.1c.3 Bundle and lifecycle

- [ ] The zxing WASM chunk is lazily imported on first camera use and precached by
      the service worker; the idle path must not pay for it
- [ ] The camera stops on `visibilitychange` to hidden, on session end, and on the
      3-minute watchdog ([3.8](3.8-resilience.md))
- [ ] A camera in use for more than 60 s with no decode returns to scanner mode
      with a gentle message — an abandoned viewfinder is a hot iPad pointed at a
      corridor

## Tests

Vitest with a stubbed `mediaDevices` and a stubbed detector:
- [ ] `unavailableWhenGetUserMediaMissing`
- [ ] `deniedPermissionReportsUnavailableWithoutThrowing`
- [ ] `emitsScanOnDetectedBarcode`
- [ ] `stopReleasesEveryTrack` — asserted on the fake tracks
- [ ] `hiddenTabStopsTheCamera`
- [ ] `restrictsFormatsToTheThreeConfigured`
- [ ] `idleTimeoutReturnsToScannerMode`

E2E (E13, in [3.11](3.11-e2e.md)) uses the fake-camera Y4M from
[3.0](3.0-preflight.md); real-lighting behaviour is [3.10](3.10-hardware-validation.md)'s
job and is not claimed here.

## Exit criteria

- [ ] Camera mode decodes a device label from a laptop screen in desktop Chrome
      with the fake stream, end to end into a real API call
- [ ] Toggling in and out ten times leaves no running track and no growing memory
- [ ] The WASM bundle loads with the network throttled to "offline" after one warm
      load (proving the precache), verified once [3.7](3.7-pwa-and-kiosk-mode.md)
      lands
- [ ] No camera-specific branch exists anywhere in the state machine or screens

## Risks

| Risk | Mitigation |
|---|---|
| Decode too slow or unreliable in corridor lighting | Restricted formats, downscaled frames, torch toggle; tested in the actual corridor in 3.10, not only under a desk lamp |
| iOS refuses to start the stream (missing `playsinline`/`muted`, or a gesture requirement) | Camera only ever starts from a user tap; both attributes set; verified on the device early in 3.10 |
| The WASM chunk is not precached and the fallback fails exactly when the network does | An explicit offline test after 3.7; the chunk is named in the service worker's glob, not assumed |
| A camera left running silently | `stop()` on visibility change, session end and watchdog, each with a test |
