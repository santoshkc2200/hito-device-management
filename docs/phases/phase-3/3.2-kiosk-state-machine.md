# 3.2 — The kiosk state machine

**Parent:** [§3.2](../phase-3-kiosk-app.md) · **Depends on:** 3.0,
[2.7](../phase-2/2.7-shared-machine-definition.md) · **Unblocks:** 3.3a, 3.3b,
3.8
**Estimate:** 1.5 d · **Risk:** medium — the risk is not that it breaks, it is
that it starts having opinions

## Goal

A presentation machine that decides **which screen to paint and when to time out**,
generated from the definition Phase 2 exported, and proven identical to the Go
machine by replaying a shared fixture through both.

## Design notes

**Two implementations, one definition.** `packages/domain/session-machine.json`
and `scenarios.json` were generated in [2.7](../phase-2/2.7-shared-machine-definition.md)
from the Go transition table. The XState config is *built from the JSON at
module load*, not transcribed by hand. A hand-written mirror drifts within a
fortnight — that is precisely the cost [ADR-0004](../../adr/0004-scan-session-state-machine.md)
accepts and mitigates.

**The machine never decides an outcome.** It sends a scan, receives
`outcome.kind`, and moves. It does not know what a borrow is, whether a device is
available, or why a card was refused. Every attempt to "help" by predicting the
outcome for a snappier UI is a second opinion about custody, and the wrong one
eventually.

**Optimistic feedback without optimistic truth.** The submitting state paints an
immediate neutral acknowledgement (the soft click, the pending card) so the kiosk
feels instant. It never paints "Borrowed" before the server says so. Perceived
speed comes from the acknowledgement and from the ≤ 200 ms transitions, not from
guessing.

**`expiresAt` is the clock.** The `after` transitions from the JSON drive the
countdown ring; the *authoritative* deadline is the `expiresAt` in each response.
On every response the machine reconciles: if the server's deadline is nearer, it
wins. A backgrounded iPad whose timers were throttled must not believe a session
is alive that the server has already reaped.

**Recovery is a request, not a guess.** On load, if `sessionStorage` holds a
session id, `GET /v1/sessions/{id}` decides everything: alive → resume in the
right state with the right screen; expired or missing → start clean. The kiosk
never reconstructs a session from cached fragments.

**The watchdog is unconditional.** Three minutes in any non-idle state returns to
`idle` and clears the screen, whatever the machine believes. A kiosk stuck on one
person's name and open loans all afternoon is a privacy incident and an outage at
the same time.

## Work items

### 3.2.1 Machine construction

- [x] `apps/kiosk/src/machine/session-machine.ts` — `setup()` + `createMachine`
      with states and transitions built from `@hdms/domain`'s
      `session-machine.json`, including its `after` timeouts
- [x] The machine's `version` is logged once at startup alongside the app build id
      — a kiosk running an old bundle against a new server is then diagnosable from
      one log line
- [x] A startup assertion that every state in the JSON has a screen mapped, so an
      added server state fails loudly in CI rather than rendering blank on an iPad
- [x] Context: `sessionId`, `kioskId`, `user`, `pendingDevice`, `openLoans`,
      `lastOutcome`, `lastMessage`, `expiresAt`, `supportCode`

### 3.2.2 API actor

- [x] `scanActor` — `fromPromise` invoking `POST /v1/sessions/{id}/scan` with the
      idempotency key from [3.0](3.0-preflight.md); creates the session first if
      there is none
- [x] `closeActor` (Done), `cancelActor`, `returnLoanActor` (tap-to-return,
      including its confirmation tap — FR-30)
- [x] Every response replaces context wholesale from `session` + `openLoans`;
      nothing is merged, because the server response is complete by design
      ([06](../../06-api-contract.md))
- [x] `outcome.kind === 'duplicate'` is a no-op transition that does not disturb
      the countdown or re-announce feedback
- [x] Problem responses are routed to the failure states, never thrown into React

### 3.2.3 Lifecycle

- [x] Session id persisted to `sessionStorage` on creation, cleared on close,
      cancel and expiry
- [x] Recovery on load via `GET /v1/sessions/{id}`; storage that is missing or
      corrupt (iOS can evict it) starts clean rather than erroring
- [x] 3-minute watchdog from any non-idle state → `idle`, clearing all
      person-identifying context
- [x] `expiresAt` reconciliation on every response and on `visibilitychange` back
      to visible

### 3.2.4 Parity test

- [x] `apps/kiosk/src/machine/contract.test.ts` replays
      `packages/domain/scenarios.json` through the XState machine with a stubbed
      API returning each scenario's scripted outcomes, asserting the state
      sequence matches the fixture's expectation exactly
- [x] The test fails if the fixture contains a scenario the machine cannot run —
      no skipping, no filtering; a scenario the kiosk cannot express is a defect in
      the kiosk

- [x] Parity green over every scenario in the fixture, including the timeout and
      duplicate cases
- [x] The machine contains no branch on device status, user status, or any reason
      code — grep for the enum names as part of review
- [x] A reload mid-session resumes on the correct screen against a live API
- [x] Deleting a state from the JSON fails CI rather than the iPad

## Risks

| Risk | Mitigation |
|---|---|
| The XState machine drifts into its own opinions | Built from the generated JSON; parity replayed in CI; a review rule against status branches |
| iOS throttles timers in the background and the countdown lies | `expiresAt` reconciliation on visibility change and on every response |
| `sessionStorage` evicted by iOS in standalone mode | Recovery treats missing storage as "start clean", with a test |
| A new server state renders a blank screen | Startup assertion that every state maps to a screen |
