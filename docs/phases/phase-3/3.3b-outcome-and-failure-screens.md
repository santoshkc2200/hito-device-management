# 3.3b — Outcome and failure screens

**Parent:** [§3.3](../phase-3-kiosk-app.md) · **Depends on:** 3.2 ·
**Unblocks:** 3.6, 3.8, 3.9, 3.11
**Estimate:** 1 d · **Risk:** medium — NFR-4 ("the kiosk never shows a raw
error") is proven or lost here

## Goal

`SuccessScreen`, `BlockedScreen`, `OfflineScreen` and the `ErrorBoundary`: the
screens that decide whether a refused borrower leaves informed or leaves angry,
and whether a crash looks like a message or like a broken product.

## Design notes

**The server wrote the words.** `message.title`, `message.detail` and
`message.tone` come from the API ([06](../../06-api-contract.md)) so wording can be
corrected — or translated — without shipping a build to every iPad. These screens
choose layout, colour and icon from `tone` and `outcome.kind`; they do not author
sentences about custody. The only text these screens own is chrome: "OK",
"Done", "Scan another device".

**Every dead end names the paper fallback.** Design constraint 7 in
[07](../../07-kiosk-app.md): a screen that says only "no" sends a nurse away
without the equipment they came for, and the system has then made the hospital
worse than the register it replaced. The server's message already says it; the
layout must give it room rather than truncating it under a large red icon.

**The three unrecognised-card cases are distinct** ([2.4](../phase-2/2.4-unrecognised-cards.md)):
unbound, unknown, revoked. Same screen, different server message, all directing to
the equipment administrator. The kiosk renders whichever it is told; it must not
collapse them into "card error", which is exactly the flattening that makes the
turned-away counts in the dashboard useless.

**An unhandled render error is a product failure, not an exception.** The
`ErrorBoundary` is the last line: a calm full-screen message, the kiosk name, a
support code, and an automatic return to idle. It cannot itself depend on anything
that might be broken — no API call, no store read, no lazy chunk.

**Offline is a state with advice.** "Reconnecting… the attendant can record your
item on the register in the meantime" — naming the fallback rather than asking
someone holding a device to wait indefinitely.

## Work items

### 3.3b.1 `SuccessScreen`

- [ ] Borrowed and returned variants, distinguished by icon, colour *and* word
- [ ] Device name and asset tag; due date rendered as human relative time
      ("Please return by tomorrow, 9:00"), from the server's `dueAt`
- [ ] A nil due date renders no due line at all — not "no due date", which reads
      as a defect
- [ ] "Scan another device, or tap Done"; auto-returns after 4 s
- [ ] Multi-item context: the second borrow in a session says so ("2 items")

### 3.3b.2 `BlockedScreen`

- [ ] Reason and guidance straight from `message`, laid out so the *guidance* is
      readable, not squeezed under the icon
- [ ] Covers device conflicts (`device-on-loan`, unavailable statuses) and all
      three unrecognised-card cases
- [ ] OK button plus an 8 s auto-dismiss, returning to whatever state the machine
      says follows — after a rejection from `awaiting_user`, that is `idle` with
      the pending device released
- [ ] Amber/blue-grey per `tone` — never the red reserved for system failure. A
      refused borrow is a normal outcome and must not look like a crash

### 3.3b.3 `OfflineScreen`

- [ ] Full-screen, non-technical, with the kiosk name and support code
- [ ] Names the paper-register fallback explicitly
- [ ] Retries in the background ([3.8](3.8-resilience.md)) and disappears on its
      own when connectivity returns; no "retry" button that a borrower must think
      about
- [ ] Never shows an HTTP status, a URL, or a stack

### 3.3b.4 `ErrorBoundary`

- [ ] Wraps the entire app, above the router
- [ ] Renders with zero dependencies: no API, no config read, no lazy import
- [ ] Support code = kiosk name + a short random incident id, also written to the
      local diagnostics ring buffer for [3.10](3.10-hardware-validation.md)
- [ ] Auto-reloads the app after 15 s — an unattended kiosk must heal itself
- [ ] A `renderError` test double proves it catches a throwing child

## Tests

- [ ] Snapshot guard: **no screen can render a raw error object, an `Error`
      message, a URL, or an empty state** — a test that renders every screen with
      hostile props (nulls, an `Error`, an unknown `tone`, an unknown
      `outcome.kind`) and asserts the output is still a human message
- [ ] `blockedScreenRendersServerGuidanceVerbatim` for each of the three
      unrecognised-card messages
- [ ] `unknownOutcomeKindFallsBackToSafeMessage` — forward compatibility with a
      server that learns a new kind
- [ ] `errorBoundaryCatchesAndShowsSupportCode`
- [ ] `offlineScreenHasNoTechnicalStrings` (regex over the rendered text)
- [ ] `successWithoutDueDateOmitsTheDueLine`
- [ ] axe clean on all four

## Exit criteria

- [ ] Killing the API mid-session shows the offline screen and never a browser
      error (E12 proves it end to end in [3.11](3.11-e2e.md))
- [ ] Each of the three unrecognised-card cases shows its own guidance, naming the
      equipment administrator and the paper register
- [ ] A deliberately thrown render error produces the boundary screen with a
      support code and self-heals
- [ ] The hostile-props test covers every screen in the app, including 3.3a's

## Risks

| Risk | Mitigation |
|---|---|
| A future refactor lets a raw error reach the screen | The hostile-props snapshot guard runs over every screen, and new screens are added to its table by construction |
| Blocked screens read as a system failure and borrowers stop trusting the kiosk | Tone-driven palette, guidance given layout priority, and 3.12's observation of real staff |
| The three refusal cases get collapsed into one message during a "cleanup" | A test per case, named for the case |
