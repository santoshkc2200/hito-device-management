# 3.4 — Attendant manual entry

**Parent:** [§3.4](../phase-3-kiosk-app.md) (plus `ManualSource`, moved here from
§3.1) · **Depends on:** 3.1a, 3.3a · **Unblocks:** 3.10
**Estimate:** 0.5 d · **Risk:** low, and it removes a high one

## Goal

The last resort (FR-62): a PIN-gated keypad the attendant uses when a label is
unreadable and the camera cannot help either. It exists because of one hardware
fact — **iPadOS hides its on-screen keyboard while a hardware keyboard is
connected**, and the paired scanner *is* a hardware keyboard.

## Design notes

**No borrower ever types.** Registration is administrator-only (FR-40), so the
entire on-screen QWERTY the original plan carried is gone. What is left is one
attendant entering one token — which is why this is a keypad, not a keyboard.

**The alphabet is the validation.** Tokens are Crockford Base32
([05](../../05-credentials-and-labeling.md)): 32 characters with I, L, O and U
excluded. A keypad that only offers those characters makes an invalid character
*impossible to enter*, which is a better guarantee than any error message. It is
also far fewer, larger keys than QWERTY — faster and more accurate for a person in
a hurry at a counter.

**Checksum before network.** `parseToken` validates the mod-37 check character
locally, so a mistyped token is caught at the keypad rather than as a rejection
screen ten seconds later. The keypad's own error is quiet and inline: "That code
doesn't look right — check the last character."

**Every use is audited and counted.** `source: 'manual'` flows to the server on
the scan, lands in `scan_events`, and shows on the dashboard. Manual entry that is
climbing means labels are wearing out or a scanner is failing — the count is a
maintenance signal, not a suspicion.

**The PIN protects a capability, not a secret.** It stops a curious borrower from
typing someone else's token. It is stored hashed in kiosk config, is settable only
by an administrator, and locks out for 60 s after five failures. It is not a
security boundary against a determined attacker who has the iPad in hand — the
kiosk token's narrow scope is what limits that ([06](../../06-api-contract.md)).

## Work items

### 3.4.1 `ManualSource`

- [ ] `packages/scan/src/manual.ts` — `ManualSource implements ScanSource`, with a
      `submit(token)` method the UI calls; no DOM of its own
- [ ] Emits through the router like every other source, inheriting the debounce
      and the token pre-check
- [ ] `id: 'manual'`, forwarded to the API as the scan source

### 3.4.2 PIN gate

- [ ] Entry point: a small, deliberately unobvious control in the screen chrome
      (long-press the kiosk name) — reachable by an attendant who knows, invisible
      to a borrower who does not
- [ ] 4–6 digit numeric PIN, hashed in kiosk config; five failures → 60 s lockout,
      with the attempt counted in diagnostics
- [ ] The gate closes on session end, on the watchdog, and on 60 s idle

### 3.4.3 Keypad

- [ ] Keys for the 32 Crockford characters plus the hyphen, backspace and clear;
      no other character is reachable
- [ ] Keys ≥ 56 px with press feedback; the display shows the entry in the
      canonical `HD-U-XXXXXXXXXX-C` shape as it is typed
- [ ] Crockford substitution applied as typed (I/L → 1, O → 0) so a person reading
      a smudged label cannot go wrong
- [ ] Submit is disabled until `validateToken` passes; the inline hint names the
      failing part (length, character, checksum)
- [ ] Cancel returns to the underlying screen with the session untouched
- [ ] Verified with the scanner paired — the case this whole sub-phase exists for
      ([3.10](3.10-hardware-validation.md))

## Tests

- [ ] `keypadCannotProduceAnInvalidCharacter` — iterate every key, assert the
      result is always in the alphabet

- [ ] `submitDisabledUntilChecksumValid`

- [ ] `gateClosesOnWatchdog`
- [ ] `manualSubmissionFlowsThroughTheRouterWithSourceManual`

      [3.1b](3.1b-hid-wedge-source.md)'s focus rule)
- [ ] axe clean; keys reachable and labelled for screen readers

## Exit criteria

- [ ] A valid token typed on the keypad completes a borrow end to end
- [ ] An invalid checksum is caught locally, with no API call made
- [ ] The keypad is usable with the Bluetooth scanner connected on the real iPad
      (checked off in 3.10, not here)
- [ ] Manual scans appear in `scan_events` with `source = 'manual'` and are counted
      on the dashboard

## Risks

| Risk | Mitigation |
|---|---|
| iOS keyboard suppression leaves the attendant with no way to type | This keypad removes the dependency on the iOS keyboard entirely; 3.10 verifies it with the scanner paired |
| The PIN entry point is discovered and used by borrowers | Deliberately unobvious, lockout on failures, every use audited; the kiosk token's scope bounds the damage |
| A scan arrives mid-entry and corrupts the field | Focus-aware wedge suppression, with a test on both sides |
