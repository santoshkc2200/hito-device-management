# 3.7 — PWA, pairing and kiosk mode

**Parent:** [§3.7](../phase-3-kiosk-app.md) · **Depends on:** 3.0, 3.3a ·
**Unblocks:** 3.10
**Estimate:** 1 d · **Risk:** medium — most of it is iPadOS behaviour that cannot
be verified anywhere but on the iPad

## Goal

Turn the app into something that lives on a home screen, survives a reload, is
paired to a kiosk identity, and cannot be casually navigated away from.

## Design notes

**The manifest already exists** (`apps/kiosk/vite.config.ts` from Phase 0):
standalone display, icons, theme colour. What is missing is the service worker's
precache list, the pairing flow, and the lockdown behaviours.

**Precache what the fallback needs.** The shell, the fonts, and — critically —
the zxing WASM chunk ([3.1c](3.1c-camera-source.md)). The camera is the fallback
for a failed scanner; a fallback that needs a healthy network to download itself
will be unavailable in exactly the situations that produce it.

**Updates must not interrupt a transaction.** `registerType: 'autoUpdate'` is
already configured; gate the actual reload on the machine being in `idle`. A
service-worker refresh in the middle of someone's borrow is a lost transaction and
an inexplicable screen flash.

**Pairing is one-time and legible.** The kiosk shows "This iPad is not yet paired"
with a keypad for the code from [3.0](3.0-preflight.md). On success it stores the
token, the kiosk id and the kiosk name, and never shows the screen again unless
the token is rejected. A `401` from the API returns it to the pairing screen
rather than to an error — a rotated token is an expected event, not a fault.

**Kiosk mode is a stack of small refusals.** Pull-to-refresh off, overscroll off,
text selection off, long-press callouts off, double-tap zoom off, context menu
off. Each is a one-liner; together they are the difference between an appliance
and a browser someone can wander out of.

**Guided Access is the real lock**, and it is an iPad setting, not code. The app's
job is to not need it — to have nothing to navigate to — and the runbook's job is
to ensure it is on.

## Work items

### 3.7.1 Service worker and manifest

- [ ] Precache the shell, fonts, icons and the zxing WASM chunk explicitly by glob
- [ ] Runtime caching: nothing for `/v1/*` — API responses are never served from a
      cache, because a stale custody answer is worse than no answer
- [ ] Update flow: new worker activates, but reload is deferred until the machine
      is `idle`
- [ ] Verify `display: standalone`, orientation and theme colour on the device
- [ ] Offline start: a cold launch with no network reaches the offline screen,
      never a Safari error page

### 3.7.2 Pairing

- [ ] `PairingScreen`: kiosk name unknown yet, a numeric keypad for the code, a
      clear "ask an administrator for a pairing code" instruction
- [ ] Exchange via `POST /v1/kiosks/pair`; on success store token + id + name and
      enter `idle`
- [ ] `401`/`403` from any API call clears the token and returns to pairing, with
      a support code shown
- [ ] The token is written once and never logged, never rendered, never put in a
      URL
- [ ] An "unpair" action behind the attendant PIN ([3.4](3.4-attendant-manual-entry.md))
      for redeploying an iPad to another counter

### 3.7.3 Kiosk-mode behaviours

- [ ] `overscroll-behavior: none`, pull-to-refresh disabled, rubber-banding
      suppressed
- [ ] `user-select: none`, `-webkit-touch-callout: none`, context menu suppressed
- [ ] Double-tap zoom disabled; pinch zoom left alone (an accessibility need, not a
      leak)
- [ ] Screen Wake Lock where supported, re-acquired on `visibilitychange`;
      documented Auto-Lock = Never in the runbook where it is not
- [ ] The app has exactly one route — there is nothing to navigate to, which is the
      strongest lockdown available

### 3.7.4 Runbook (first draft)

- [ ] `docs/runbooks/kiosk-ipad-setup.md`, following the seven steps in
      [07](../../07-kiosk-app.md): pair scanner, configure suffix = CR and
      symbologies, Add to Home Screen, pair the kiosk, grant camera permission,
      Guided Access + Auto-Lock, physical mount and cradle
- [ ] Scanner setup barcodes recorded (photographed or referenced by manual page),
      including the show/hide-iOS-keyboard toggle barcode
- [ ] Completed and corrected during [3.10](3.10-hardware-validation.md) — the
      draft exists here so 3.10 is a *check*, not a writing exercise

## Tests

- [ ] `pairingExchangeStoresTokenAndEntersIdle`

- [ ] `tokenNeverAppearsInDomOrConsole` — a test that renders the app and greps the
      DOM and captured console output
- [ ] `serviceWorkerUpdateDeferredWhileSessionActive`
- [ ] `apiResponsesAreNotCached` (asserted on the SW config)
- [ ] Playwright: offline cold start reaches the offline screen, not a browser
      error (folded into E12 in [3.11](3.11-e2e.md))

## Exit criteria

- [ ] Installed to the iPad home screen and launching in standalone mode
- [ ] Paired with a code, borrowing successfully afterwards
- [ ] Rotating the kiosk token in the admin API returns the iPad to the pairing
      screen with a clear message
- [ ] Pull-to-refresh, text selection and long-press callouts all inert on the
      device
- [ ] A cold offline launch shows the offline screen
- [ ] Runbook draft committed

## Risks

| Risk | Mitigation |
|---|---|
| iPadOS Safari quirks in standalone mode (storage eviction, wake behaviour) | Test on the real device from the first week of the phase, never only in desktop Safari |
| A service-worker update reloads mid-transaction | Reload gated on `idle`, with a test |
| Storage eviction loses the kiosk token and the iPad goes dead overnight | Token in `localStorage` (not `sessionStorage`), pairing screen is a recoverable state, and the runbook tells the attendant what to do |
| The camera fallback's WASM is not actually precached | Explicit glob plus an offline verification step in the exit criteria |
