# 3.8 — Resilience

**Parent:** [§3.8](../phase-3-kiosk-app.md) · **Depends on:** 3.2, 3.3b ·
**Unblocks:** 3.11
**Estimate:** 0.5 d · **Risk:** medium — NFR-4 and NFR-5 both land here

## Goal

Every failure the kiosk can meet — a dropped connection, a slow API, a 500, an
expired session, a reload — resolves to a human message and a recoverable state.
No borrower ever sees a status code, and no retry ever creates a second loan.

## Design notes

**Idempotency is what makes retries safe.** The key is derived deterministically
in [3.0](3.0-preflight.md), so retrying *the same scan* is provably one
transaction server-side ([2.5](../phase-2/2.5-idempotency.md)). Retrying without
that guarantee is how a hospital ends up with two loans for one device — which is
why the retry policy is written here, next to the key derivation, and not in
whichever component happened to need it first.

**Retry writes, but narrowly.** Network errors and `5xx`: retry with backoff,
three attempts, jittered. `4xx` other than `408`/`429`: never — a rejected request
will be rejected again, and the delay is the borrower's. `409`/`422` from
idempotency conflicts are surfaced, not retried.

**Offline is detected from requests, not from `navigator.onLine`.** iPadOS reports
`onLine: true` for a Wi-Fi association that reaches no gateway — the single most
common corridor failure. `onLine` is a hint that speeds up detection; two
consecutive request failures are what actually flips the state.

**Recovery is quiet.** On reconnect the app resyncs via `GET /v1/sessions/{id}`
and drops back to the correct screen. No banner announcing recovery, no toast to
dismiss — the offline screen simply goes away.

**Phase 5 owns the queue.** An IndexedDB replay queue for transactions attempted
while offline is explicitly *not* built here. The API has been idempotent since
Phase 2 precisely so that this is a purely client-side addition later. What this
sub-phase must not do is make that addition harder — hence one mutation path,
keys derived in one place, and no assumption that a mutation resolves before the
next screen.

## Work items

### 3.8.1 Query and mutation policy

- [ ] TanStack Query defaults: retry 3 with exponential backoff + jitter for
      network/`5xx`, no retry for other `4xx`
- [ ] A single scan mutation used by every path, carrying the derived
      `Idempotency-Key`
- [ ] Request timeout (say 8 s) so a hung request cannot hold a screen forever;
      timeout is treated as a network failure
- [ ] `AbortController` on session end and watchdog, so a reply to an abandoned
      session never repaints a live screen

### 3.8.2 Connectivity state

- [ ] `useConnectivity()` — two consecutive failures → offline; one success →
      online; `navigator.onLine` transitions used only to check sooner
- [ ] Drives `OfflineScreen` ([3.3b](3.3b-outcome-and-failure-screens.md)) from
      any state, and suspends the countdown while offline (a session the kiosk
      cannot reach is not a session the borrower is wasting)
- [ ] Background probe of `/healthz` while offline, with backoff capped at 10 s

### 3.8.3 Resync

- [ ] On reconnect: `GET /v1/sessions/{id}` and reconcile — alive → resume,
      expired/absent → clean idle
- [ ] On `visibilitychange` to visible after more than 30 s hidden, the same
      reconcile (an iPad that has been asleep is a kiosk with stale beliefs)

### 3.8.4 Error mapping

- [ ] One `errorMessage(problem)` catalogue mapping every RFC 9457 `type` the API
      can produce ([06](../../06-api-contract.md)) to a human message and a tone
- [ ] An unknown `type` maps to a generic message plus a support code — and is
      logged locally so [3.10](3.10-hardware-validation.md) can find it
- [ ] The catalogue is exhaustive by construction: a table keyed on the generated
      problem-type union, so a new server error type fails the TypeScript build
      rather than shipping as "something went wrong"

## Tests

- [ ] `retriesNetworkErrorsThreeTimesWithBackoff` (fake timers)
- [ ] `doesNotRetryOn400`
- [ ] `retryReusesTheSameIdempotencyKey` — the test that stands between this
      product and duplicate loans
- [ ] `twoConsecutiveFailuresGoOffline`, `oneSuccessComesBackOnline`
- [ ] `onlineEventAloneDoesNotClearOfflineState`
- [ ] `countdownSuspendedWhileOffline`
- [ ] `resyncAfterReconnectRestoresCorrectScreen`
- [ ] `abortedRequestCannotRepaintANewSession`
- [ ] `everyProblemTypeHasACatalogueEntry` — exhaustiveness over the generated union

## Exit criteria

- [ ] Killing the API mid-session shows the offline screen within 3 s and recovers
      on its own when it returns (E12)
- [ ] A retried scan produces exactly one loan, asserted against the database in
      the e2e run
- [ ] No code path can render an HTTP status, a URL, or an exception message
- [ ] Adding a new problem type to the spec fails the build until the catalogue is
      updated

## Risks

| Risk | Mitigation |
|---|---|
| A retry creates a duplicate transaction | Deterministic idempotency keys, one mutation path, and a database-level assertion in e2e |
| `navigator.onLine` lies on hospital Wi-Fi | Detection is request-based; `onLine` is only an accelerator |
| A late response repaints a screen belonging to the next person | Abort on session end and watchdog, with a test |
| The offline screen flickers on a single slow request | Two-failure threshold plus the 8 s timeout |
