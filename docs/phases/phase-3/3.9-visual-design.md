# 3.9 — Visual design

**Parent:** [§3.9](../phase-3-kiosk-app.md) · **Depends on:** 3.3b, 3.6 ·
**Unblocks:** 3.12
**Estimate:** 1 d · **Risk:** low, and easy to skip — which is how kiosks end up
looking like admin panels

## Goal

One coherent visual direction across every screen, legible from a metre by
someone who has not slept, and accessible by measurement rather than by intent.

## Design notes

**Design once, at the end of the screen work, not at the start.** By this point
all seven screens exist with real content and real edge cases (a 40-character
device name, a five-item loan list, a three-line refusal message). Choosing type,
colour and spacing against real content is the difference between a design that
survives contact and one that has to be redone.

**Hospital-appropriate, not hospital-clichéd.** Restrained, high-contrast,
generous whitespace. This is a device people glance at while carrying things —
personality belongs in clarity, not in decoration.

**The type scale is a requirement, not a preference.** Body ≥ 20 px, headings
≥ 36 px ([07](../../07-kiosk-app.md)). The prompt on each screen outranks
everything except an outcome.

**Colour-vision deficiency is a design input.** Success/warning/error must be
distinguishable in deuteranopia and protanopia simulation. Since nothing is
conveyed by colour alone ([3.6](3.6-feedback.md)), this is a check rather than a
constraint — but it is a check that gets done here, with a simulator, not assumed.

**Both orientations, and 150% Dynamic Type.** The mount may end up portrait. A
layout that only works landscape is a layout that will be discovered wrong on
installation day.

## Work items

### 3.9.1 Direction

- [x] Use the `frontend-design` skill for the visual direction; use `shadcn` for
      component scaffolding where a primitive is needed
- [x] Tokens land in `packages/ui/src/tokens.css` (colour, spacing, radius,
      elevation, motion durations); components stay app-local per the decision in
      [3.0](3.0-preflight.md)
- [x] Type scale defined once as tokens and applied — no ad-hoc `text-[22px]`
      anywhere
- [x] Dark surfaces are a decision, not an accident: the counter's lighting is
      known by now from [3.10](3.10-hardware-validation.md)'s early visits

### 3.9.2 Application

- [x] Every screen from 3.3a and 3.3b reworked to the direction, with real content
      at its worst case (longest device name, longest server message, most loans)
- [x] Countdown ring, feedback colours and icons brought into the same system
- [x] Loading and transition states styled — a skeleton that flashes for 80 ms is
      worse than nothing; prefer instant acknowledgement

### 3.9.3 Verification

- [x] `axe-core` in CI over every screen, with no violations (the CI stage lands
      in [3.11](3.11-e2e.md); the assertions land here)
- [x] Contrast measured against WCAG 2.2 AA for every text/background pair,
      including on coloured outcome backgrounds
- [x] Deuteranopia/protanopia simulation pass over all outcome screens
- [x] Layout verified at 150% Dynamic Type and in both orientations, at the iPad's
      actual resolution
- [x] Touch targets re-audited after restyling (≥ 48 px, ≥ 64 px primary)

## Tests

- [x] `vitest-axe` on every screen component, in both light-content and
      outcome-coloured variants
- [x] A token-usage test: no hard-coded hex colours or px font sizes outside the
      token sheet (a lint rule is better than a test here if oxlint can express it)
- [x] Playwright screenshots at both orientations and both text scales, reviewed
      as artefacts rather than pixel-compared (a pixel-diff gate on a design that
      is still moving produces noise, not signal)

## Exit criteria

- [x] axe reports no violations on any screen
- [x] Every text/background pair meets AA, verified with a contrast tool
- [x] Screens legible from one metre on the actual iPad — checked with the actual
      mount, at the actual counter
- [x] Layout intact in portrait and landscape at 100% and 150% text
- [x] No hard-coded colours or font sizes outside the token sheet

## Risks

| Risk | Mitigation |
|---|---|
| Design work expands to fill the phase | Timeboxed to a day; the direction is applied to existing screens, not used as an excuse to redesign flows |
| A restyle breaks contrast or target sizes | axe and the touch-target audit re-run as exit criteria, not as a one-off |
| It looks right on a MacBook and wrong on the iPad | Verified on the device at the counter, in the counter's lighting |
