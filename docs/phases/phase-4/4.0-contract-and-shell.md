## Goal

Get the two foundations in place that every later task assumes: a contract that
already contains every operation Phase 4 needs, and a shell where every screen
has a route, a nav entry, and its three states before anyone builds the screen
itself.

Every new path Phase 4 needs, added in one deliberate pass so no later task edits
the spec ad hoc: admin account management and auth lifecycle, audit query and
export, reports, settings/policy, kiosk get/edit/enable, CSV import
preview/commit, CSV exports, registration support (`check-employee-no`,
`archive`, `hasCredential` filter), `correct-attribution`, and optional
`Dashboard` fields. Both generators regenerated and committed.

32 new operations, so 32 stub handlers in
`hdms-backend/internal/apiserver/phase4_stubs.go` answering 501 with the task
number that fills each one in — `gen.ServerInterface` is one interface, so the
spec could not land without them.

**Two things worth knowing before touching the spec again:**

- `ImportRowAction`'s member is `invalid`, not `error`, because oapi-codegen
  disambiguates colliding enum member names package-wide: an `error` member here
  silently renamed `MessageTone`'s constants (`gen.Error` → `gen.MessageToneError`)
  and broke unrelated tests. **Check the generated constant diff after adding any
  enum.**
- New `Dashboard` fields are optional, not required, so `dashboard.go` compiles
  untouched until [4.7](4.7-dashboard.md) fills them in.

**Was:** spec lints clean, both generators run in CI, no field removed or
narrowed vs v1.0.0, and a written note recording that v1.1.0 is additive-only
(`docs/06-api-contract.md` § Versions).

## 4.0b Admin shell

### Design notes

**The shell is where the "no unexplained empty table" rule is won.** Building
loading/empty/error primitives once, here, is the difference between eleven
screens that all handle failure and eleven screens that each handle it slightly
differently. [4.11a](4.11-quality-and-exit.md) then audits rather than retrofits.

**Role-aware nav is cosmetic and must be labelled as such.** Hiding a nav item is
a courtesy to the user, not a control. Every reviewer of a nav change should be
able to point at the corresponding `requireRole` in
[4.1a](4.1-auth-and-roles.md). A nav item hidden with no server check behind it
is the exact failure the parent's risk table names.

**Placeholder routes are better than absent routes.** A reachable route that says
"Reports — 4.9" is navigable, linkable and demoable on day one; it also means
every later task is a fill-in rather than a router change, so two people building
two screens never collide in `router.tsx`.

**The stub 501 is a first-class UI state.** The API answers unimplemented
operations with a problem carrying `task: "4.x"`. The error primitive renders
that as "Not built yet — task 4.9a" in development, which is far more useful than
a generic failure and disappears on its own as stubs are deleted.

### Work items

#### 4.0b.1 Route tree
- [ ] Routes for every Phase 4 screen: dashboard (`/`), devices, device detail,
      users, user detail, register, backfill, loans, loan detail, disputed,
      reports, audit, settings (categories, policy, kiosks, templates, admins),

#### 4.0b.2 Nav and layout
- [ ] Grouped nav replacing the flat five-item list in `components/app-shell.tsx`
      — Daily (dashboard, backfill, register), Records (devices, users, loans),
      Insight (reports, audit), Settings
- [ ] Role-aware rendering driven by `/auth/me`, marked in code as cosmetic
- [ ] Collapses correctly at admin-PC widths (1280 px and 1440 px); **not**
      mobile-responsive — out of scope by [08](../../08-admin-console.md)

#### 4.0b.3 State primitives
- [ ] `<LoadingState />`, `<EmptyState />`, `<ErrorState />` in
      `apps/admin/src/components/states/`
- [ ] `EmptyState` requires a title, an explanation and an optional action — the
      props make an unexplained empty table impossible to write by accident
- [ ] `ErrorState` renders a problem+json title/detail, the request ID for
      support, and the `task` extension when present
- [ ] Route-level error boundary so a render crash shows a recoverable panel and
      not a blank page

#### 4.0b.4 Feedback surface
- [ ] Toast surface (sonner is already present) with a single `notify` wrapper —
      success, failure-with-problem, and undo-less destructive confirmations
- [ ] Every mutation in the phase reports through it; no bare `alert`, no silent
      success

### Tests

- [ ] `states.test.tsx` — `EmptyState` renders its explanation; `ErrorState`
      surfaces detail, request ID and task number from a problem+json body
- [ ] `app-shell.test.tsx` — a `viewer` identity renders no settings nav entry;
      an `admin` identity renders all groups
- [ ] `router.test.tsx` — every declared route resolves to a component (guards
      against a route added to the tree with no element)

### Exit criteria

- [ ] Every Phase 4 screen has a reachable placeholder route with the three
      states wired
- [ ] Nav collapses correctly at admin-PC widths
- [ ] Navigating to a screen backed by a stub shows the "not built yet — task
      4.x" panel, not a spinner that never resolves
- [ ] No screen in the app renders an undesigned empty or error state (grep for
      bare `isLoading &&` returning `null` is part of review)

| Risk | Mitigation |
|---|---|
| Placeholder routes rot and ship to the pilot | 4.11d's exit run walks every nav item; a placeholder still present is a failed exit |
| Role-aware nav is mistaken for access control | Comment at the definition site, and 4.1a's matrix test is the actual proof |
| Later spec edits reopen the frozen contract per feature | Additive-only rule in the README; any change bumps the minor version and re-runs both generators |
