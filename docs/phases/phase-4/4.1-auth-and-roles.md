# 4.1 — Authentication and roles

**Parent:** [§4.1](../phase-4-admin-console.md) · **Depends on:** 4.0b ·
**Unblocks:** every screen that gates an action, and 4.11's role exit criterion
**Estimate:** 3.5 d · **Risk:** high — this is the sub-phase most likely to be
"done" in the UI and absent at the API

## Goal

Three roles that mean something at the API, and an account lifecycle an
administrator can operate without a developer and a `psql` prompt.

The exit criterion is written adversarially on purpose: *"`viewer` and
`technician` are provably blocked at the API, not just hidden in the UI."*
Everything below is arranged so that passing it is the default rather than an
afterthought.

## Design notes

**The role names change, and the migration is not a rename.** Today the enum is
`admin_role AS ENUM ('superadmin','admin','operator')` with a column default of
`'operator'`; the parent and [08](../../08-admin-console.md) specify
`admin`/`technician`/`viewer`, and the exit criteria are written against those
names. The docs win — they are the spec.

`ALTER TYPE ... RENAME VALUE` looks tempting and does not work here: renaming
`superadmin` → `admin` collides with the existing `admin` value, and there is no
transactional ordering that avoids it. Create a new type, migrate the column with
an explicit `USING` map, drop the old type:

| Old | New | Why |
|---|---|---|
| `superadmin` | `admin` | full access, unchanged in meaning |
| `admin` | `admin` | same — the two old top roles were never distinguished in code |
| `operator` | `technician` | closest existing meaning; devices yes, staff no |
| — | `viewer` | new; nobody is migrated into it |

No production data exists yet (the pilot is Phase 5), so this is safe now and
will not be later. The seeded bootstrap admin must land on `admin`, and the
column default becomes `viewer` — the least privilege, so a row created by a
future bug is harmless rather than dangerous.

**`auth.HasRoleAtLeast` exists and nothing calls it.** Keep the ranked helper
(`viewer` < `technician` < `admin` is a genuine total order for this product) but
do not let ranking be the interface. The interface is a **per-operation minimum
role table**, keyed by `"METHOD /v1/path/{template}"`, exactly mirroring
`auth.KioskAllowedOperations`. That shape is chosen deliberately: it already has
a test in this tree (`test/integration/kiosk_scope_test.go`) that enumerates the
*spec* and fails on any operation not classified. Reusing it means a Phase 5
endpoint cannot be added without someone deciding its role.

**Two roles are not simply "less admin".** `technician` may force-return and
reprint device labels but may not touch staff, kiosks or other admins. `viewer`
may read the dashboard, loans and reports and write nothing at all. Where the
table and the ranking disagree, the table is right — encode the exception, do not
bend the ranking to fit.

**Lockout must not become a denial-of-service on the only administrator.**
Counting failures per account lets anyone who knows an email address lock a real
admin out of a hospital's equipment desk. Count per account *and* record the
source, lock for a bounded window rather than permanently, and give every lockout
a recorded unlock path an `admin` can use — with the bootstrap admin unlockable
via the CLI so a single-admin hospital is never locked out of its own system.

**Recovery codes are single-use and stored hashed**, with the same Argon2id
parameters as passwords. They are shown exactly once, on generation. Redeeming
one consumes it and emits an audit event; the count remaining is visible so
"I have one left" is knowable before it is urgent.

## 4.1a Role model and server-side enforcement · 1 d

### Work items
- [ ] `migrations/0012_admin_roles.sql` — new enum, column migrated with the map
      above, default `viewer`, working Down
- [ ] Update `auth.roleRank` and the `AdminIdentity.Role` comment; the identity
      already carries `Role` from the session, so no session change is needed —
      verify that with a test rather than assuming it
- [ ] `auth.RequiredRoles` — `map[string]string` of `"METHOD /v1/template"` →
      minimum role, plus the deliberate exceptions list
- [ ] `auth.RequireRole(method, path) (string, bool)` and middleware application
      in the same place kiosk scope is enforced, before routing
- [ ] 403 responses are RFC 9457 problems with a stable type, never a bare status
- [ ] Every denial emits an audit event (actor, operation, role) — an attempted
      override is as interesting as a successful one

### Tests
- [ ] `test/integration/role_matrix_test.go` — table-driven over every operation
      in the spec × three roles, asserting the expected status class. **Fails on
      any operation not present in `RequiredRoles`**, mirroring the kiosk-scope
      suite
- [ ] `viewer` receives 403 on every mutating operation, including the ones whose
      UI it never sees
- [ ] `technician` receives 403 on `/users*`, `/admins*`, `/kiosks*`, `/settings`
      and 2xx on device status change and credential reprint
- [ ] `migrations_test.go` still green up and down; a fixture row per old value
      survives the migration with the mapped new value

### Exit criteria
- [ ] The role × operation matrix test is green and covers 100 % of spec
      operations
- [ ] No handler reads `AdminIdentity.Role` directly to make an authorisation
      decision — the middleware is the single choke point (grep is part of review)
- [ ] A new endpoint added without a `RequiredRoles` entry fails CI

## 4.1b Account lifecycle and hardening · 1.5 d

Deletes the eleven `4.1b` stubs from `phase4_stubs.go`.

### Work items
- [ ] `migrations/0013_auth_lifecycle.sql` — `admin_recovery_codes` (hashed,
      single-use, `used_at`), lockout columns (`failed_attempts`, `locked_until`,
      `last_failure_at`), `must_change_password`, `must_reenrol_totp`
- [ ] `/admins` CRUD — list, create, get, update (role and status)
- [ ] `/admins/{id}/reset-password`, `/reset-totp`, `/unlock` — admin-initiated
- [ ] `/auth/password`, `/auth/totp/reenrol`, `/auth/totp/confirm`,
      `/auth/recovery-codes` — self-service
- [ ] Recovery-code redemption path in login, consuming the code atomically
- [ ] Lockout after N failures within a window; bounded unlock; CLI unlock for
      the bootstrap admin
- [ ] `must_change_password` / `must_reenrol_totp` block every non-auth operation
      until satisfied, at the middleware, not in the UI

### Tests
- [ ] Integration: lockout triggers, blocks, expires, and unlocks via the endpoint
- [ ] Integration: a recovery code works once and never again; two concurrent
      redemptions of the same code produce exactly one success
- [ ] Integration: forced re-enrolment blocks a device list call and permits the
      TOTP endpoints
- [ ] Every auth event (login, failure, lockout, unlock, reset, re-enrolment,
      recovery-code use) emits an audit event with actor and, where applicable,
      reason

### Exit criteria
- [ ] Every auth lifecycle operation is reachable from the API with no `psql`
- [ ] Locking out an administrator is recoverable by another administrator, and
      a single-administrator installation is recoverable by CLI
- [ ] Recovery codes are never stored or logged in plaintext (grep the audit
      payloads in the test)

### Work items
- [x] Login with TOTP, plus a "use a recovery code" path

      in a dialog and resume, rather than redirecting a half-typed registration

      explicit "these will not be shown again" confirmation

### Tests
- [x] Component: expiry mid-form is recoverable and the form's values survive
- [x] Component: a `viewer` identity renders no destructive affordance on any

      (proven by 4.1a, referenced here — the UI test alone is not the proof)
- [x] axe clean on login, recovery, forced-change and admin-accounts screens

## Risks

| Risk | Mitigation |
|---|---|
| Role checks land in the UI only | The matrix test enumerates the spec and fails on an unclassified operation; 4.1a precedes every screen that gates an action |
| The enum migration is attempted as a rename and collides | Written down above with the mechanism; the migration test carries a fixture row per old value |
| Lockout becomes a DoS on a hospital's only administrator | Bounded window, admin unlock endpoint, CLI unlock for the bootstrap account |
| Recovery codes are treated as passwords and stored recoverably | Same Argon2id path as passwords, shown once, single-use, with a test asserting no plaintext in storage or audit |
| Renaming roles quietly downgrades the seeded admin | Explicit mapping table, default `viewer`, and a test asserting the bootstrap admin is `admin` after migration |
