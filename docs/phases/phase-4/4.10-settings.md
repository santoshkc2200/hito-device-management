# 4.10 — Settings

**Parent:** [§4.10](../phase-4-admin-console.md) · **Depends on:** 4.1a ·
**Unblocks:** 4.5c's low-stock threshold, 4.6e's backlog threshold, 4.7c's
warnings
**Estimate:** 1.75 d · **Risk:** low, with one real decision — where settings
live

## Goal

Everything the hospital will want to change without a developer: loan periods,
policy thresholds, kiosk registration, and the printed artefacts.

## Design notes

**There is no settings store today, and that is the actual work here.** Policy
values are currently constants, and label geometry lives in the browser's local
storage (`apps/admin/src/lib/label-settings.ts`), which does not survive a
different admin PC — the label sheet an administrator carefully calibrated is
gone the moment they use another machine. Settings move server-side.

**A typed single row beats a key/value bag.** `settings` as one row with typed
columns gives migrations, defaults and constraints for free; a `key text, value
jsonb` table gives none of them and turns every read into a parse with an
optional failure. The schema is small and it changes by migration, which is
exactly the audit trail a policy change deserves.

**Every settings change is audited with actor and before/after.** "Who turned off
block-on-overdue" is a question that gets asked after something goes wrong, and
[4.9d](4.9-reports-and-audit.md)'s diff view is where it gets answered.

**Reads are cached; writes invalidate.** Policy is read on nearly every checkout
and every dashboard load. Cache it in the process with an explicit invalidation
on write, rather than paying a query per scan or, worse, reading it once at boot
and requiring a restart to change a threshold.

**There is no self-registration toggle.** Registration is administrator-only by
design, not by configuration (FR-40). If a setting for it appears in a pull
request, the answer is no — a toggle would make the kiosk's most important
security property a runtime accident.

- [ ] Thresholds consumed by 4.5c, 4.6e and 4.7c come from here, not from

## Risks

| Risk | Mitigation |
|---|---|
| Settings become a key/value bag with no validation | Typed single row, changed by migration, with range checks and field-level problems |
| A setting is added that nothing reads | Every value's call site is a work item in 4.10a; a setting with no consumer fails review |
| Policy is cached at boot and a threshold change needs a restart | Explicit invalidation on write, with an integration test that changes policy and re-checks behaviour |
| Label calibration is lost when the admin uses a different PC | Migration out of local storage is a named work item with its own test |
| A self-registration toggle is added "for flexibility" | Stated as out of scope here and in [08](../../08-admin-console.md); registration is admin-only by design |
