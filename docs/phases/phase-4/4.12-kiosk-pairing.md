# 4.12 — Kiosk pairing in the admin console

**Parent:** [Phase 4 admin console](../phase-4-admin-console.md) ·
**Depends on:** [4.10b](4.10-settings.md), Phase 3 kiosk pairing ·
**Unblocks:** administrator-led kiosk provisioning without CLI access
**Estimate:** 1.5 d · **Risk:** medium — this workflow exchanges a short-lived
code for a long-lived kiosk credential

## Goal

An administrator can register and pair a kiosk entirely from the admin console.
The console issues the exact code accepted by the kiosk, explains its lifetime
and one-time use, and never exposes the resulting bearer token outside the
deliberate one-shot credential surface.

## Existing baseline and gaps

The API already supports kiosk registration, listing, editing, enable/disable,
token rotation, pairing-code issuance, and pairing-code redemption. The admin
Settings screen already calls those operations and displays issued codes.
Phase 4.12 hardens that existing path rather than building a second kiosk
management surface.

The gaps to close are:

- The backend previously issued an eight-digit code while the kiosk accepted
  exactly six digits. This made the documented pairing path impossible.
- Pairing is buried in a row action after registration instead of being offered
  as the natural next step in kiosk setup.
- The pairing dialog shows an expiry time but no live remaining time, copy
  confirmation, reissue semantics, or protection against duplicate issuance.
- Existing component tests prove only that the kiosk table renders; they do not
  prove the pairing workflow.
- There is no end-to-end proof that a code issued in the admin console takes an
  unpaired kiosk to its idle screen without using the CLI.

## Invariants

- Pairing codes are exactly six decimal digits.
- A code expires 10 minutes after issuance and succeeds exactly once.
- Issuing a new code for a kiosk invalidates its previous code.
- Wrong, expired, consumed, and superseded codes return the same public error.
- Pairing-code issuance remains an administrator-only operation enforced by the
  API. UI role checks are presentation, not authorization.
- Codes and bearer tokens never appear in URLs, browser history, analytics,
  application logs, or toast text.
- Pairing responses retain `Cache-Control: no-store`.
- Closing or replacing the pairing dialog removes the displayed code from
  component state.

## 4.12b Make pairing a guided admin workflow · 0.75 d

### Work items

- [ ] After kiosk registration, offer **Pair this kiosk now** as the primary
      next action; keep direct bearer-token setup as an explicitly labelled
      advanced fallback.
- [ ] Keep **Issue pairing code** on each active kiosk row for replacement
      devices and browsers with cleared storage.
- [ ] Disable pairing actions while issuance is pending and for disabled
      kiosks.
- [ ] Display the six digits in a readable grouped treatment, with kiosk name,
      location, absolute expiry, and a live remaining-time countdown.
- [ ] Add a copy button with accessible copied-state feedback. Do not include the
      code in toast text.
- [ ] Explain that the code is single-use and that issuing another code cancels
      the current one.
- [ ] When the countdown reaches zero, mark the code expired and offer **Issue
      new code** without requiring the dialog to close.
- [ ] Clear the code from component state when the dialog closes, expires, or is
      replaced.
- [ ] Preserve designed loading, empty, error, and permission states.

### Tests

- [ ] Component: registration can continue directly into pairing for the newly
      created kiosk ID.
- [ ] Component: row action requests a code for the selected kiosk and renders
      exactly six digits.
- [ ] Component: duplicate clicks issue only one request while pending.
- [ ] Component: countdown reaches expired state and reissue replaces the old
      code in memory.
- [ ] Component: closing the dialog removes the code from the DOM.
- [ ] Component: technician and viewer do not see mutation controls.
- [ ] Accessibility: dialog focus enters, remains trapped, and returns to its
      trigger; countdown updates do not create noisy live-region announcements.

### Exit criteria

- [ ] An administrator can register a kiosk and reach a usable pairing code
      without leaving the registration workflow or using a CLI.
- [ ] The dialog communicates which kiosk is being paired, how long remains,
      and what reissuing does.

## Risks

| Risk | Mitigation |
|---|---|
| Short numeric code is brute-forced | Ten-minute expiry, single use, five attempts per minute per IP, cryptographic generation |
| Administrator pairs the wrong physical kiosk | Dialog repeats kiosk name and location; kiosk idle screen confirms assigned name after redemption |
| Reissue leaves two valid codes | Database stores one pairing hash per kiosk; replacement and concurrency tests prove one winner |
| Secret leaks through UI convenience | No URL placement, no code-bearing toast, explicit state clearing, `no-store`, logging-redaction test |
| Existing bearer-token setup becomes confusing | Pairing is primary; direct token setup remains an advanced, one-shot fallback |
