# 4.2 — Shared list infrastructure

**Parent:** — (new; the parent asks for it eleven times in 4.11) ·
**Depends on:** 4.0b · **Unblocks:** 4.3a, 4.4a, 4.8a, 4.9c, 4.9d
**Estimate:** 2.5 d · **Risk:** medium — cheap to build once, expensive to
retrofit into six screens

## Goal

One filter/sort/pagination contract on the server and one table component on the
client, so that every list screen in the console gets URL-bound filters, column
visibility, keyboard navigation and designed empty states for free — and so that
the 5 000-loan performance criterion is met by a query that was designed for it
rather than tuned afterwards.

## Design notes

**Cursor pagination, not offset.** Offset pagination on an audit log or a loan
history disagrees with itself under concurrent writes: a row inserted while the
admin is on page 2 pushes a row from page 2 to page 3, which they then never see.
Keyset cursors are stable under insertion and get an index that actually helps.
The cursor is opaque to the client — base64 of the sort key plus id — so its
shape can change without a contract change.

**The sort key must always be unique.** `ORDER BY created_at DESC` on a table
where two rows share a timestamp will silently repeat or skip a row at the page
boundary. Every sort is `(<column>, id)`, and every supporting index carries `id`
as its last column. This is the single most common way keyset pagination is built
wrong.

**Filter parsing is shared with export.** [4.9c](4.9-reports-and-audit.md)'s CSV
export must return exactly what is on screen; the only way that stays true is if
the export handler parses the same query parameters with the same code. Build the
parser as a reusable piece from the start, not as handler-local argument
shuffling.

**The client table owns the memo boundary.** Unmemoized `columns` or `data` in
TanStack Table v8 produce a 100 % CPU render loop with no console error and no
failing test. This project has already lost time to it. `DataTable` accepts
column definitions through a hook that memoizes them, so a screen author cannot
reintroduce the bug by passing an inline array.

**URL search params are the state.** Not component state mirrored into the URL —
the URL is read as the source of truth and written on change. That makes back,
forward, reload and paste all work by construction, and it is why
[4.0b](4.0-contract-and-shell.md) declared search-param schemas on every route up
front.

## 4.2a Server-side list contract · 1 d

### Work items
- [ ] `internal/platform/httpx/listing` — parse and validate `limit`, `cursor`,
      `sort`, `order`, and a typed filter set per resource
- [ ] Whitelist sortable and filterable columns per resource; an unknown column
      is a 400 problem, never an interpolated string reaching SQL
- [ ] Cursor encode/decode with a version byte, so a stale cursor from a previous
      deploy is rejected cleanly rather than misread
- [ ] `limit` capped server-side (default 50, max 200) — an export is
      [4.9c](4.9-reports-and-audit.md)'s job, not a `limit=100000` call
- [ ] `migrations/0014_list_indexes.sql` — covering indexes for the four list
      surfaces, each ending in `id`:
      loans by `(status, due_at, id)` and `(user_id, borrowed_at, id)`,
      devices by `(status, asset_tag, id)`, users by `(department_id, full_name, id)`,
      audit by `(occurred_at, id)` and `(actor, occurred_at, id)`
- [ ] Apply the shape to the existing `/devices`, `/users`, `/loans` handlers
      without changing their responses incompatibly (additive: new params,
      existing behaviour when they are absent)

### Tests
- [ ] Unit: cursor round-trips; a tampered or stale cursor is rejected as a 400
- [ ] Unit: unknown sort column, unknown filter, over-max limit → 400 problems
- [ ] Integration: **paging is stable under concurrent writes** — page 1, insert
      rows, page 2, assert no duplicate and no skipped row
- [ ] Integration: ties on the sort column do not repeat or drop a row at the
      page boundary
- [ ] Integration/benchmark: the overdue query over 5 000 historical loans
      completes within the < 1 s budget with `EXPLAIN` showing an index scan —
      the assertion is on the plan as well as the wall clock, because a timing
      test on a fast laptop hides a sequential scan

### Exit criteria
- [ ] One parser serves devices, users, loans and audit
- [ ] Cursor paging is stable under concurrent writes
- [ ] The 5 000-loan overdue query is index-backed and inside budget

|---|---|

| Keyset pagination built without a unique tiebreaker | Every index ends in `id`; a tie test exists at the page boundary |
| Export drifts from what is on screen | 4.9c reuses this parser rather than reimplementing the filters |
