# 4.3 — Devices

**Parent:** [§4.3](../phase-4-admin-console.md) · **Depends on:** 4.2b, 4.5a ·
**Unblocks:** nothing on the critical path
**Estimate:** 2 d · **Risk:** low — the most conventional work in the phase, and
the first thing to slip if the schedule tightens

## Goal

The equipment catalogue an administrator can run without a developer: find a
device while someone waits on the phone, change its status with a reason, print
its label, and see its whole story on one page.

Phase 1 already shipped device list and forms; this sub-phase moves them onto
[4.2b](4.2-list-infrastructure.md)'s table and fills in what is missing —
detail, bulk actions, import.

## Design notes

**Search must be fast enough to use mid-conversation.** The scenario in
[08](../../08-admin-console.md) is explicit: someone is on the phone. Search
spans asset tag, name, model and serial number, runs server-side through
[4.2a](4.2-list-infrastructure.md)'s parser, and is index-backed — not a client
filter over a fetched page, which stops working at the first thousand devices.

**Validation mirrors the server, it does not replace it.** The forms use the same
rules the API enforces so the admin learns about a problem before the round trip.
The server remains the authority, and a 400 from it is rendered against the
offending field rather than as a toast.

**Status changes are custody-adjacent and take a reason.** Marking a device
`in_service` while it is on loan is a real situation with a real answer; the
reason is what makes the answer legible later. Same rule as every other override
in the phase.

**Bulk actions are where a console earns its keep — and where it can do the most
damage.** Selecting forty rows and printing labels is a Saturday morning
well spent; selecting forty rows and changing their category by accident is a
data-recovery afternoon. Bulk operations state the count in the confirmation, and
bulk status change is deliberately *not* offered.

**The import machinery is shared with users.** [4.4d](4.4-users-and-registration.md)
builds preview/commit, the `import_batches` table and the per-row classification
first; this unit supplies a device parser and reuses everything else. If it needs
a second CSV dialect, something has gone wrong.

## 4.3a Table and detail · 0.75 d

### Work items
- [ ] Device list on `DataTable`: filter by status and category, search across
      asset tag, name, model, serial; sort; cursor paging; column visibility
- [ ] Row actions: view, edit, change status, print label, force return
- [ ] Detail page: full attributes, current holder if on loan (linked), complete

## 4.3b Mutations · 0.75 d

### Work items
- [ ] Create and edit forms with validation mirroring the server, field-level
      error rendering from problem+json
- [ ] Status change with a **mandatory reason**, audited
- [ ] Bulk select → **print labels** (into the existing label sheet), **change
      category**, **export** (via [4.9c](4.9-reports-and-audit.md))

- [ ] Component: a server 400 renders against the offending field, not as a toast
- [ ] Component: status change is impossible without a reason
- [ ] Component: bulk category change confirms with the count before acting
- [ ] Integration: status change emits an audit event with actor and reason

## Risks

| Risk | Mitigation |
|---|---|
| Client-side search that stops scaling at a thousand devices | Server-side through 4.2a's parser, index-backed, with an integration test |
| A bulk action changes forty rows the admin did not mean to select | Count stated in the confirmation; no bulk status change; no bulk delete |
| A second CSV implementation diverges from the user importer | 4.4d lands first and owns the machinery; this unit supplies only a parser |
| This sub-phase absorbs time the starred screens need | It is explicitly slippable — see the README's track split |
