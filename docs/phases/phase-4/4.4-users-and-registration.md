# 4.4 — Users and registration ★

**Parent:** [§4.4](../phase-4-admin-console.md) · **Depends on:** 4.2b, 4.1a ·
**Unblocks:** 4.5, 4.6b, and Phase 3's pilot
**Estimate:** 3.75 d · **Risk:** high — this is the critical path for the whole
product, and its failure mode is "works, but takes six minutes"

## Goal

An administrator turns a person standing at the desk into a borrower holding a
working card, on one screen, in under three minutes (FR-41, FR-44, FR-59).

The kiosk cannot register anyone by design (FR-40). Until this sub-phase lands,
nobody new can ever borrow anything, no matter how well the kiosk works. It is
the single highest-priority item in Phase 4 and should be built by whoever has
the most uninterrupted time.

## Design notes

**"Under three minutes" is a design constraint, not a hope.** It rules out a
wizard, it rules out navigating to a separate card-assignment screen, and it
rules out validating the employee number on submit. Every interaction on the
registration screen is measured against a stopwatch that has a person standing
next to it.

**The atomic write already exists.** `/users/register-with-card` is in the frozen
v1.0.0 contract and creates the user and binds the credential in one transaction.
Use it. Do not build "create user, then bind card" from two calls in the client —
that is precisely how a half-registered person with no card, or a card bound to
nobody, gets into the database.

**The duplicate check is live, and it is advisory.** `/users/check-employee-no`
tells the admin about a collision while they are still on the field that caused
it. It is not the enforcement — the unique constraint in the database is. The
client check can be stale by definition (two admins, two desks); the screen must
therefore also handle the 409 gracefully rather than treating it as impossible.

**Three card options, one of which is honest about failure.** Scanning a blank
card is the fast path and needs a USB scanner on the admin PC (the same HID-wedge
input the kiosk uses — see [3.1b](../phase-3/3.1b-hid-wedge-source.md); the token
is also printed legibly on every blank card so it can be typed). Printing a card
on the spot is the fallback. "Register without a card" exists for roster
pre-loading, and those users carry a visible *no card issued* badge everywhere
they appear — a person who cannot borrow must never look like one who can.

**"Register another" is the roster-day feature.** On success, the screen offers
to keep going with the department pre-filled and focus back in the name field.
Batch registration by hand is a real workflow on distribution days and it should
not require re-navigating for each person.

**Provenance is not decoration.** `users.registered_by` records `admin:<id>` or
`import` today, and INV-11 forbids a `kiosk:` value. 4.4d extends this so an
imported user can be traced to *which* import, because "where did these 200
people come from" is a question that gets asked exactly once, six months later,
with nobody available who remembers.

- [x] The screen is completable keyboard-only, end to end

## Risks

| Risk | Mitigation |
|---|---|
| Registration is slow enough that admins avoid it and people go unregistered | The under-3-minute target is a measured exit criterion with a real admin, not a review opinion |
| The client composes create + bind and produces orphans | `/users/register-with-card` is the only path; an injected-failure integration test asserts no partial state |
| The live duplicate check is mistaken for enforcement | The unique constraint stays; the 409 race has its own test |
| "Register without a card" quietly produces people who cannot borrow and nobody notices | Visible badge everywhere, plus the `hasCredential=false` work queue on 4.4a |
| Import creates 200 people whose origin nobody can reconstruct | `import_batches` row, linked from every created user, surfaced on 4.4c |
