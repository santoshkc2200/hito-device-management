# 4.5 — Credentials ★

**Parent:** [§4.5](../phase-4-admin-console.md) · **Depends on:** 4.4a ·
**Unblocks:** 4.3a, 4.4c, 4.6e, 4.7c, and Phase 3's pilot (via 4.5c)
**Estimate:** 2.25 d · **Risk:** high — the one screen where a wrong click
destroys a working card

## Goal

The full credential lifecycle, on a panel that makes the difference between
*reprint* and *reissue* impossible to miss. This is the workflow the entire
project was originally asked for: someone lost their card, and it must stop
working while their history stays intact.

## Design notes

**Reprint and reissue are different actions with different consequences, and the
device/user split is not arbitrary.** A device token is stored recoverably, so
reprinting a device label reproduces the *same* token and the old label keeps
working — harmless. A user credential is stored hashed and cannot be recovered,
so "print it again" is impossible: the only thing the system can do is issue a
new one, which **kills the card in that person's pocket**. That is why the same
conceptual button reads **Print** on a device and **Reissue & print** on a user,
in a different colour, behind a dialog that says what is about to stop working.

**The confirmation dialog states consequences, not warnings.** "Are you sure?"
teaches nothing. The dialog says: the old card stops working immediately, open
loans and history are unaffected, a new card must be printed and handed over —
and requires a typed reason before the action is available. Six months later,
"why does Dr. Sharma have three revoked cards" has an answer.

**Every credential action is audited with its reason.** Revoke, reissue,
report-lost, bind, additional issue. The reason field is not optional and is not
free of consequence: it is the text that appears in the audit log and in the
credential history on this very panel.

**Blank card stock is an operational feature, not an admin toy.** Cards are
generated in batches, printed, and kept in a drawer at the desk; registration
binds one. The unbound count is shown on this screen, on the registration screen,
and on the dashboard when it drops below ten — because discovering the drawer is
empty at the moment a card is needed is the failure this exists to prevent.

**The card-reader test screen is built now and used in Phase 6.** When the
hospital's RFID/NFC ID cards are adopted, someone will hold an unknown card
against an unknown reader and need to see what comes out. Raw next to normalised,
with no interpretation, is the whole feature — and building it now, while the
normalisation code is fresh, costs a quarter of a day.

## 4.5b Destructive flows · 1 d

### Work items
- [x] **Print** (device credential) — reproduces the same token, no dialog beyond
      the print preview
- [x] **Reissue & print** (user credential) — distinct label, distinct colour,
      plain-language explanation on the button's own dialog
- [x] **Report lost & reissue** — consequences dialog (old card dead immediately,
      loans and history unaffected, new card must be printed and handed over),
      mandatory typed reason, and the new token revealed once for printing
- [x] **Revoke** with mandatory reason, no replacement issued
- [x] **Issue an additional credential** of a chosen kind — QR, Code 128, RFID
      (FR-16)
- [x] Every action goes through the existing frozen endpoints
      (`/credentials/{id}/reprint|revoke|reissue`), none through a new one
- [x] Token reveal uses the existing one-shot reveal surface; the token never
      enters a URL, a log line, or a toast

### Tests
- [x] Component per destructive path **including cancel** — cancel must leave the
      credential untouched and the dialog must not be dismissible by clicking
      away mid-reason
- [x] Component: the device panel never renders "Reissue & print"; the user panel
      never renders a plain "Print"
- [x] Integration **E14**: reissue kills the old token, the new token works, and
      the history shows both with the reason
- [x] Integration: every action emits an audit event carrying actor and reason

### Exit criteria
- [x] Reprint and reissue are visually and verbally distinct, and the consequence
      is stated before the confirmation, not after
- [x] Every destructive path has a component test including its cancel branch
- [x] No credential action is possible without a reason

## Risks

| Risk | Mitigation |
|---|---|
| Reprint vs reissue confuses the admin into killing a working card | Distinct labels, distinct colours, a consequences dialog with a mandatory reason, and a device/user split that matches the real risk |
| A destructive dialog is dismissible mid-reason and half-acts | Component tests cover the cancel branch of every path explicitly |
| Blank stock runs out unnoticed at the desk | Count on three screens plus a dashboard warning below the settings threshold |
| A token leaks into a log, a URL or a toast | One-shot reveal surface only; the no-secrets-in-the-DOM rule in the README, checked in review |
