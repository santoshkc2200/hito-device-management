# 4.6 — Paper backfill ★★

**Parent:** [§4.6](../phase-4-admin-console.md) · **Depends on:** 4.4b, 4.5c ·
**Unblocks:** 4.7c (backlog warning)
**Estimate:** 4.75 d · **Risk:** highest in the phase — and the risk is boredom,
not breakage

## Goal

The screen an administrator uses every morning: yesterday's paper register page,
typed in, keyboard only, in under four minutes for twelve rows (NFR-9b — under
20 s per row).

The engine already exists. Phase 2 built `/backfill/preview`, `/backfill` and
`/backfill/last-entry`, the resolution rules, the disputed-entry path and the
exclusion constraint ([2.4b](../phase-2/2.4b-paper-backfill.md)). **Everything in
this sub-phase is user interface**, and the failure mode is entirely
interaction design: an admin facing four clicks and a page reload per row will do
it once, let the slips pile up, and the system's data quality collapses.

Budget the time. This is the second most important UI in the system after the
kiosk idle screen and the one most likely to be built as a lazy CRUD form and
then quietly abandoned.

## Design notes

**The keyboard path is the feature.** Tab moves Device → Person → times; **Enter
commits the row and returns focus to a cleared Device field**. If the admin's
hand has to leave the keyboard once per row, the four-minute target is gone
regardless of how correct everything else is. Every subsequent decision in this
sub-phase defers to that sentence.

**Staging is client-side; truth is one atomic save.** Rows accumulate in the
browser and are submitted as one batch. A conflict on row 3 must not cost the
typing of rows 1, 2 and 4 — and neither must a closed laptop, which is why staged
rows live in local storage until saved or discarded.

**The client never decides borrow-vs-return.** The same rule the kiosk follows
([Phase 3](../phase-3/README.md)): once device and person are known, the *server*
resolves the action via `/backfill/preview`, which reuses `checkout`'s logic. The
radio shows the server's answer pre-selected; the admin overrides only when the
paper disagrees. Any client-side `if` that recomputes this is a defect, however
convenient.

**Conflicts are surfaced while the admin is still looking at the paper page.**
Preview runs as rows change, not on save. Discovering on save that row 3 is
impossible, after the page has been put back in the file, means the admin cannot
check what the paper actually says.

**Four resolutions, and the fourth one matters most.** Correct the existing
record, change the asset tag, discard the row — or **record it anyway as
disputed**. Sometimes the truth is genuinely unknown, and forcing a tidy answer
to satisfy a database constraint is how audit trails become fiction. A disputed
entry is stored outside the exclusion constraint, badged permanently, and listed
on [4.8a](4.8-loans.md)'s disputed view.

**The point of the screen is the follow-up step.** Paper rows exist mostly
because someone had no card. Saving the batch leads directly to *"2 new people
were created and have no card yet — issue cards to both"*. Paper in, cards out,
and next time those two people use the kiosk. Without that step, the feature
records history and changes nothing.

## 4.6a Entry bar · 0.75 d

### Work items
- [ ] Single-row entry bar: Device → Person → Action → Out/In → Note
- [ ] **Enter commits and refocuses** the cleared Device field, always — including
      after a validation failure elsewhere in the row
- [ ] `Ctrl+Enter` as the documented alternative; `Escape` clears the in-progress
      row without touching staged rows
- [ ] Forgiving time parser as a **separately unit-tested module** in
      `packages/domain`: accepts `9:15`, `0915`, `9.15am`, `915`, `21:05`, `9 15`
- [ ] Times are relative to the sticky page date, so `0915` alone is sufficient
- [ ] Ambiguous input (`115`, `1230am`) resolves by a documented rule and shows
      the interpreted value inline before commit

### Tests
- [ ] Parser table test covering every accepted form **and** every ambiguous one,
      with the resolved interpretation asserted
- [ ] Component: focus returns to the first field after commit, in every branch
- [ ] Component: `Escape` discards the in-progress row and leaves staged rows

- [ ] Component: a scanned token and a typed asset tag resolve to the same device

## 4.6d Conflicts · 1.5 d

### Work items
- [ ] Live `/backfill/preview` call as rows change, debounced, so conflicts
      surface while the paper page is still in the admin's hand
- [ ] Conflict panel expanding inline, **side by side**: already recorded vs.
      your paper entry, each with holder, department, time range and origin
- [ ] The four resolutions from [08](../../08-admin-console.md): correct the
      existing record's end time, change the asset tag, discard the row, or
      record as disputed
- [ ] Disputed rows badged permanently and explained at the point of choosing
- [ ] The batch **cannot be saved** while an unresolved conflict remains, with the
      count stated next to the save button

### Tests
- [ ] Integration + component **E17**: a row conflicting with existing custody is
      flagged before save and the batch cannot be saved until resolved
- [ ] Component: each of the four resolutions produces the expected staged state
- [ ] Component: resolving a conflict does not re-run preview into a loop (the
      debounce and the resolution must not fight each other)

## Risks

| Risk | Mitigation |
|---|---|
| Built as a generic "create loan" form and too slow to use daily | Its own sub-phase, its own timed criterion, and a real admin runs the test |
| Admins resolve conflicts by inventing tidy answers | The disputed option exists precisely so nobody is forced to fabricate certainty, and it is badged permanently |
| Staged work lost to a reload or a closed laptop | Local storage per page reference, with a remount test |
| The client reimplements borrow-vs-return "just for the radio button" | The server preview is the only source; a review rule, same as the kiosk's |
| The feature records history and issues no cards | 4.6e is a named unit, and E16 asserts the card is issued from the follow-up step |
| Live preview fires on every keystroke and the screen stutters | Debounced, and a test asserts resolution does not retrigger a preview loop |
