# 4.7 — Dashboard

**Parent:** [§4.2](../phase-4-admin-console.md) · **Depends on:** 4.5c, 4.6e,
4.2b · **Unblocks:** nothing — but it is the landing page, so it is what the
console *is* to the person using it
**Estimate:** 1.75 d · **Risk:** medium — the SSE reconnection path is the only
hard part, and it is the part that looks fine in development

## Goal

The one screen the administrator leaves open all day: what is out, what is late,
what just happened, and who was turned away.

## Design notes

**The dashboard is a work queue, not a status board.** Every panel exists because
it prompts an action. Overdue → chase. Unregistered card scanned → register that
person. Blank stock low → print more cards. Paper backlog → type yesterday's
page. A panel that shows a number nobody acts on is decoration and belongs in
[4.9](4.9-reports-and-audit.md).

**Unregistered-card scans are the most important line on the screen.** Each one
is a person who walked up to the kiosk, needed equipment, and was turned away —
and the only way they stop being turned away is if an administrator registers
them. It gets a register call-to-action, not just a count.

**Compose client-side before adding a dashboard field.** v1.1.0 added optional
`Dashboard` fields, and the temptation is to move everything into one endpoint.
Resist it per panel: the overdue list is a filtered `/loans` query the loans
screen already makes, and the unbound count is `/credentials/unbound-count`.
Reuse the query, get caching for free, and add a dashboard field only where a
composed call would be genuinely wasteful.

**The live feed reconnects, and reconnection is where SSE goes wrong.** A
dropped connection with no resume silently stops updating a screen that still
looks connected — the worst possible failure for a panel whose whole promise is
freshness. Backoff with jitter, `Last-Event-ID` resume, and a connection
indicator that tells the truth: connected, reconnecting, or stale-with-a-refresh.

**Duplicates are as bad as gaps.** A resume that replays events already rendered
produces a feed nobody trusts. De-duplicate by event id on the client, and test
the forced-disconnect path for both gaps and repeats.

## Risks

| Risk | Mitigation |
|---|---|
| SSE looks fine in development and silently stops in the ward | Backoff, resume, de-duplication, and an indicator with a real "stale" state, all tested against a forced disconnect |
| The dashboard grows into charts and configurable panels | Explicitly deferred in [08](../../08-admin-console.md); every panel must name the action it prompts |
| Everything is pushed into one dashboard endpoint and the screen becomes uncacheable | Compose from existing endpoints by default; add an optional field only where composition is genuinely wasteful |
| Turned-away people are shown as a statistic and nothing changes | Register call-to-action on the item itself, linking to the registration screen |
