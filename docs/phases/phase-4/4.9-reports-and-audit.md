# 4.9 — Reports and audit

**Parent:** [§4.8, §4.9](../phase-4-admin-console.md) · **Depends on:** 4.2a ·
**Unblocks:** 4.3b's bulk export, 4.11d's "export a report" exit step
**Estimate:** 3 d · **Risk:** medium — the streaming export is the only part that
fails at scale rather than in review

## Goal

The numbers that say whether the system is working, the export that lets anyone
analyse them in a spreadsheet, and the append-only record an auditor will ask
for.

## Design notes

**The headline number is transactions by origin over time (FR-78).** Everything
else here is useful; this one measures whether the project succeeded. If the
`paper` line is not falling and the `kiosk` line is not rising, the system has
added work rather than replaced it — and that is worth knowing monthly, not at
the end of the pilot.

**Operational health is an early-warning report, not a scorecard.** Rising
manual-entry counts mean labels are wearing out or a scanner is failing. Rising
camera-fallback counts mean the same. Rejection reasons tell you which. Each is a
maintenance signal that arrives before an outage, which is the only reason to
build it in v1.

**No charts beyond the availability bars.** Explicitly deferred in
[08](../../08-admin-console.md). Tables plus CSV export cover the analysis need
until somebody asks for more with a specific question. A charting library in this
pull request is scope creep with a nice appearance.

**Export streams and never buffers.** A multi-year export of 5 000+ rows must not
hold the result set in memory — write the header, then stream rows from a cursor
straight to the response, flushing periodically. The test asserts the memory
profile, not just the row count, because buffering passes every functional test
right up to the day it does not.

**Export reuses [4.2a](4.2-list-infrastructure.md)'s filter parser.** That is the
only way "export this view" keeps meaning what is on screen. A separate query
path drifts within one sprint.

**The audit log is append-only and is read as evidence.** Filters by actor,
action, subject and date; a row detail showing the JSON payload *and* a readable
diff, because a raw payload answers "what changed" only for someone who already
knows the schema. `ListAuditEvents` already exists in the audit store — this is
an API and a viewer over existing data, not new instrumentation.

## 4.9a Reports API · 1 d

Deletes the `4.9a` stubs.

### Work items
- [ ] `GET /reports/summary` — utilisation per device and per category, average
      loan duration, top borrowers, overdue rate over time
- [ ] `GET /reports/operational-health` — manual-entry count, camera-fallback
      count, rejection reasons, revoked-card scan attempts
- [ ] `GET /reports/by-origin` — **transactions by origin over time** (FR-78),
      bucketed by day/week/month
- [ ] `GET /reports/disputed` — implemented alongside [4.8a](4.8-loans.md)
- [ ] Each query index-backed and bounded by an explicit date range; an unbounded
      report is a 400, not a table scan
- [ ] Reports live in the module that owns the data; no cross-module "reporting"
      package reaching across every table

### Tests
- [ ] Integration: each report over a seeded dataset returns known values
- [ ] Integration: an unbounded date range is refused
- [ ] Integration: origin buckets sum to the total transaction count for the period
- [ ] Integration: `viewer` may read every report (this is the role's whole purpose)

## 4.9c Streaming CSV export · 0.75 d

Deletes the `4.9c` stubs.

### Work items
- [ ] `GET /reports/loans.csv`, `/reports/devices.csv`, `/reports/users.csv`,
      each parsing filters through [4.2a](4.2-list-infrastructure.md)'s parser
- [ ] Stream from a database cursor; write and flush incrementally; no full
      materialisation
- [ ] `Content-Disposition` filename carrying the resource and the date range
- [ ] Correct CSV escaping, a UTF-8 BOM for spreadsheet compatibility, and
      RFC 4180 quoting — a name containing a comma must not shift every column
- [ ] Client download without holding the file in browser memory

### Tests
- [ ] Integration: exporting 5 000+ rows does not buffer the whole result (assert
      on peak allocation or on first-byte latency, not only on the row count)
- [ ] Integration: the export's rows match the equivalent filtered list exactly
- [ ] Unit: quoting and escaping for commas, quotes, newlines and non-ASCII names

### Exit criteria
- [ ] Exporting 5 000+ rows does not buffer the whole result in memory
- [ ] An exported file opens in a spreadsheet with correct columns and no
      mojibake
- [ ] The export matches the on-screen view, because it shares the parser

## Risks

| Risk | Mitigation |
|---|---|
| Export buffers and dies on a real dataset | Cursor streaming with an explicit memory assertion in the test |
| Export drifts from the on-screen view | One filter parser, shared with 4.2a, by construction |
| Scope creep into charts and configurable dashboards | Deferred in [08](../../08-admin-console.md); one stacked bar is the entire allowance |
| Reports become unbounded table scans in the pilot | Mandatory date range, index-backed queries, and a 400 for unbounded requests |
| The audit viewer shows payloads only a developer can read | The readable diff is a work item, not an enhancement |
