# 5.0 — Preflight

**Parent:** — (new) · **Depends on:** Phase 4 · **Unblocks:** everything
**Estimate:** 1.5 d · **Risk:** medium — one unanswered question (Q6) blocks half
the phase

## Goal

Remove the three things that would otherwise be discovered halfway through: no
decided host, no safe place to rehearse, and a binary that will happily start in
production with development defaults.

## Design notes

**Q6 is the only genuinely blocking input in this phase, and it is blocking
today.** [01](../../01-requirements.md) marks it "Yes, before Phase 5". Nothing
in 5.3, 5.4, 5.5 or 5.6 can be finished without it, because each of them needs an
address, a disk and a backup target. It is answered here, in writing, as an ADR —
not settled verbally in the corridor and then reconstructed from memory during
the restore drill.

**Rehearsal never happens against production.** The restore drill (5.4c) writes a
database, the alert test (5.5c) deliberately breaks things, and the soak (5.6b)
runs for 24 hours. All three need a host that is not the one the counter depends
on. A staging stack running the same images from the same compose file is
cheaper than the incident that comes from skipping it.

**Production must refuse to start unsafely rather than warn.** The dev compose
sets `HDMS_RATE_LIMIT: "off"`, mounts source, and uses the example pepper — every
one of those is correct for `task dev` and catastrophic in the hospital. A
warning in a log nobody reads is not a control; a refusal to boot is.

**Clock discipline is a custody requirement, not an ops nicety.** Every loan row
is a timestamped claim about who had what. Once the kiosk queues transactions
offline (5.1) and replays them minutes later, "when did this happen" is answered
by two clocks that must agree. NTP on the host is listed here so it is configured
before it matters, not after a disputed loan.

## 5.0a Hosting decision and host specification · 0.5 d

### Work items
- [ ] Answer Q6 with the hospital: on-premise VM or cloud, who owns it, who can
      reboot it, and what the escalation path is out of hours
- [ ] Record it as **ADR-0009 — hosting and operational ownership**, including
      what was rejected and why
- [ ] Size the host from measured numbers, not guesses — Phase 2 measured p95
      18.4 ms and 780 scans/min at 50× peak
      ([load-test-results](../phase-2/load-test-results.md)); this is a small
      machine and the ADR should say so
- [ ] Nail down the operational surface: DNS name, the kiosk VLAN's network path
      to it, firewall rules, the certificate authority that will issue for
      `hdms.hospital.local`, the backup target's address and credentials, and NTP
- [ ] Confirm who at hospital IT receives alerts (5.5c has nowhere to route
      without this)

### Exit criteria
- [ ] Q6 answered in writing and ADR-0009 merged
- [ ] The host exists, is reachable from a kiosk iPad, and its owner is named

## 5.0b Environment matrix and fail-closed configuration · 0.5 d

### Work items
- [ ] One table of every `HDMS_*` variable × environment (dev, staging,
      production): value, whether it is a secret, and where the production value
      comes from
- [ ] `HDMS_ENV=production` **refuses to start** when any of these hold: the
      pepper equals the `.env.example` value, `HDMS_RATE_LIMIT` is off, TLS is
      disabled, CORS allows `*`, or `DEVICE_TOKEN_KEY` / `SESSION_KEY` are unset
- [ ] The refusal names the variable and what is wrong with it — an operator at
      22:00 should not need the source
- [ ] Startup logs the effective configuration with every secret redacted, so a
      misconfiguration is diagnosable without a debugger

### Tests
- [ ] A table-driven test with one case per refusal, asserting both the failure
      and the message naming the variable
- [ ] `productionConfigLogsNoSecretValues`

## 5.0c Staging stack · 0.5 d

### Work items
- [ ] Staging runs the same compose file and the same images as production, with
      its own secrets and its own database
- [ ] Seeded with synthetic data at pilot scale (a realistic roster, ~5 000 loan
      rows) so the restore drill and the soak measure something real
- [ ] Clearly marked in the UI so nobody registers a real borrower there
- [ ] Documented as the target for: restore drills, alert tests, the soak, and
      any deploy rehearsal

### Exit criteria
- [ ] Staging is reachable and serves the same build as production
- [ ] A drill run against staging cannot touch production data — verified by
      inspecting the connection strings, not assumed

## Risks

| Risk | Mitigation |
|---|---|
| Q6 stays unanswered and 5.3 slips into the pilot window | It is the first task in the phase and its own exit criterion; nothing after it can start |
| Production is deployed with a dev default nobody notices | Fail-closed startup with a test per refusal, rather than a warning |
| A drill is run against production because staging "wasn't ready yet" | Staging is built before the first drill exists, and every drill runbook names its target host explicitly |
| Host clocks drift and offline replays land at the wrong time | NTP is part of the host spec, checked in the deployment runbook |
