# 5.1 — Offline resilience ★

**Parent:** [§5.1](../phase-5-hardening-pilot.md) · **Depends on:** 5.0b ·
**Unblocks:** 5.8 (the pilot's headline claim)
**Estimate:** 4.25 d · **Risk:** high — the only Phase 5 work that can create a
wrong custody record

## Goal

The counter keeps working when the network does not, and nothing is lost or
duplicated when it comes back. Client-only: the API is not touched.

## Design notes

**This is a store and a replayer, not a new transport.** The API has been
idempotent since [2.5](../phase-2/2.5-idempotency.md) and
[3.8](../phase-3/3.8-resilience.md) deliberately left exactly one mutation path
with keys derived in one place (`deriveIdempotencyKey`,
`apps/kiosk/src/lib/api.ts:29`). If this sub-phase finds itself adding a second
way to send a scan, it has gone wrong.

**Exactly-once is proved by the key, not by the queue.** The queue is allowed to
replay an item twice — after a crash mid-flight, it cannot know whether the
server saw it. The server collapses the duplicate because the key is the same
one the original attempt used. The test that matters therefore asserts row counts
in the database, not queue-internal bookkeeping.

**Queue what the server can still adjudicate; refuse what would let the kiosk lie
now.** This is the whole classification rule, and it splits the two actions:

- A **return** is safe to queue. The device is physically on the counter, the
  fact is unambiguous, and the server applies its normal rules at replay. The
  only thing delayed is the confirmation.
- A **borrow** is not, unless the cached device state is *fresh* and says
  available. Offline, the kiosk cannot know whether someone else took the device
  five minutes ago, and telling a borrower "yours" when it is not is exactly the
  failure the temporal custody constraint exists to prevent.

**A refusal is not a dead end, because paper is the designed overflow lane.**
When a borrow cannot be queued, the screen says so in one sentence and points at
the register — the same lane used for an unregistered card, already understood by
the attendants, and typed in later through
[4.6](../phase-4/4.6-paper-backfill.md). Offline mode never leaves the counter
stuck; it degrades to the process the hospital ran last year.

**Nothing is ever silently dropped.** An item that fails permanently on replay
(a `4xx` that will fail again) moves to a visible quarantine in the attendant
diagnostics modal with the reason. Retrying it forever hides a problem; deleting
it destroys a custody record.

**The queue must survive what an iPad actually does**: a reload, a service-worker
update, being killed by iPadOS, and a power cycle. A service-worker update that
wipes IndexedDB would discard transactions — so that is a test, not an
assumption.

## 5.1a Durable queue store · 0.75 d

### Work items
- [ ] IndexedDB store via `idb`, one object store keyed by a monotonic local
      sequence, holding the request, its derived idempotency key, the enqueue
      timestamp and an attempt count
- [ ] Scoped to the paired kiosk id, so a re-paired iPad never replays another
      kiosk's work
- [ ] Bounded: a documented maximum (say 200 items) with a loud, distinct state
      when full — a full queue is an incident, not a silent truncation
- [ ] Survives reload, service-worker update and app restart

### Tests
- [ ] `queueSurvivesReload`, `queueSurvivesServiceWorkerUpdate`
- [ ] `enqueueOrderIsPreservedAcrossRestarts`
- [ ] `queueFullSurfacesItsOwnState`
- [ ] `itemsCarryTheDerivedIdempotencyKeyNotAFreshUuid`

## 5.1b Offline read cache and queueability policy · 1 d

### Work items
- [ ] Cache device and user lookups from successful online responses, with an
      explicit staleness bound, so the kiosk can still show a device name and a
      borrower name while offline
- [ ] `canQueue(action, cachedState)` — one pure function, the single place the
      borrow/return rule lives, returning either a queue decision or a refusal
      with its reason
- [ ] Refusal copy: what happened, that the register is the way through, and no
      status code — reusing the existing screen vocabulary from
      [3.3b](../phase-3/3.3b-outcome-and-failure-screens.md)
- [ ] Cached names are visibly marked as last-known, so an attendant is never
      misled about how current the screen is

### Tests
- [ ] Table-driven over the classification matrix: action × cached state ×
      freshness → queue or refuse, including "no cache at all"
- [ ] `borrowWithStaleCacheIsRefusedNotQueued`
- [ ] `returnIsQueuedEvenWhenCacheIsAbsent`
- [ ] `refusalMentionsThePaperRegister`

## 5.1c Replay engine · 1.25 d

### Work items
- [ ] Replay strictly in enqueue order — a borrow and a return of the same device
      replayed out of order produce nonsense
- [ ] Triggered on reconnect (reusing `useConnectivity`, not a second detector)
      and on app start with a non-empty queue
- [ ] Single-flight: two tabs or a backgrounded-then-foregrounded app cannot
      replay concurrently
- [ ] Retry policy inherited from 3.8 — network and `5xx` retried with backoff;
      other `4xx` quarantined immediately
- [ ] Conflict handling: a replayed item the server rejects (the device was taken
      meanwhile) records the server's outcome against the item so the attendant
      can see what happened to which transaction
- [ ] Items succeed, quarantine, or stay queued — no fourth outcome, and no path
      that deletes an item without recording why

### Tests
- [ ] `replayIsOrderedPerDevice`
- [ ] `crashMidFlightReplaysAndServerCollapsesTheDuplicate`
- [ ] `concurrentReplayIsPreventedBySingleFlight`
- [ ] `permanentFailureQuarantinesWithReason`
- [ ] `replayStopsWhenConnectivityDropsAgainAndResumesInOrder`

## 5.1d Offline UI · 0.75 d

### Work items
- [ ] Persistent, unmissable indicator: **"Working offline — N transactions
      pending"**, with N live
- [ ] The count clears itself as replay drains; the indicator disappears without
      a toast or an announcement, matching 3.8's quiet-recovery rule
- [ ] Pending list and quarantine list inside the attendant diagnostics modal —
      what, when, and for quarantined items, why
- [ ] Attendant-visible outcome per replayed transaction, so "did that borrow go
      through" has an answer at the counter
- [ ] Countdown behaviour while offline stays as 3.8 defined it — suspended, not
      running

### Tests
- [ ] Component: indicator renders the count, updates as items drain, and hides
      at zero
- [ ] Component: quarantined item shows its reason and cannot be dismissed
      accidentally
- [ ] axe clean at kiosk contrast levels

## Risks

| Risk | Mitigation |
|---|---|
| Offline mode creates a conflicting custody record | Borrows refuse unless custody is verifiable from a fresh cache; the classification lives in one tested function |
| A replay creates a second loan | Items carry the original derived key; the e2e asserts row counts, not client state |
| A service-worker update discards the queue | Explicit test; the queue is versioned independently of the app shell |
| The queue silently swallows a failure | Three outcomes only, quarantine is visible, and no code path deletes an item without recording why |
| Attendants do not notice they are offline | One persistent indicator with a live count, tested for contrast and visibility at kiosk distance |
