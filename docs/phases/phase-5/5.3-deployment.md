# 5.3 — Deployment

**Parent:** [§5.3](../phase-5-hardening-pilot.md) · **Depends on:** 5.0a, 5.2a ·
**Unblocks:** 5.4, 5.5, 5.6, 5.8
**Estimate:** 3.75 d · **Risk:** medium — the TLS trust chain is the one that
silently breaks the camera

## Goal

A production stack on the host Q6 named, with TLS the iPads trust, secrets that
are not in git, and a rollback somebody has actually performed.

## Design notes

**There is no production deployment artefact in the tree today.** `deploy/` holds
a `Caddyfile` and the k6 script; `docker-compose.yml` is unambiguously a
development file — `Dockerfile.dev`, bind-mounted source, a published database
port, no resource limits, and `HDMS_RATE_LIMIT: "off"`. Production is a separate
compose file, not a set of overrides applied by memory at the terminal.

**A self-signed certificate the iPad does not trust silently breaks the camera
fallback.** [09](../../09-security-privacy-ops.md) says it and it bears repeating
here: `getUserMedia` refuses to run without trusted TLS. The failure is not an
error dialog — it is a camera that never opens, on the one path used when the
scanner has failed. Distributing the CA root to the iPads is therefore part of
the deployment, verified on a real iPad, not a follow-up ticket.

**Losing `TOKEN_PEPPER` invalidates every credential in the system.** It must be
backed up somewhere that is not the database backup — if both live in the same
file, the pepper protects nothing; if it lives nowhere, a restore is useless. The
location goes in the runbook, and the runbook says which password-manager entry.

**Rollback is rehearsed or it does not exist.** The rehearsal is the deliverable.
And it has a sharp edge worth stating: rolling the *binary* back is easy, rolling
a *migration* back is not always possible. The rule for the pilot is that any
migration shipped during it must be backward-compatible with the previous
release, so a rollback never needs a down-migration under pressure.

## 5.3a Production compose stack · 1 d

### Work items
- [ ] `deploy/production/compose.yaml`: Caddy, API, Postgres 18 — images pinned
      by digest, built from the production Dockerfile, no bind-mounted source
- [ ] Resource limits and `restart: unless-stopped` on every service; healthchecks
      that actually gate startup order
- [ ] API runs as a non-root user; the database port is not published to the
      network
- [ ] Caddy serves the built frontends: `/` kiosk, `/admin` console, per
      [09](../../09-security-privacy-ops.md)
- [ ] Migrations run on startup from the embedded goose set under the advisory
      lock (already implemented — verified here under two concurrent starts)

### Tests
- [ ] Integration: two API containers starting simultaneously migrate exactly once
- [ ] A smoke check after `up`: `/v1/healthz`, `/v1/readyz`, a login, and a scan

## 5.3b TLS and the iPad trust chain · 0.75 d

### Work items
- [ ] Certificate for the internal hostname from the CA named in 5.0a
- [ ] **CA root distributed to every iPad** and trust explicitly enabled —
      installing a profile is not the same as trusting it on iPadOS
- [ ] Verified on a real iPad: the kiosk loads, and **the camera fallback opens**
- [ ] Certificate expiry date recorded with a renewal reminder owned by a named
      person; renewal steps in the runbook

### Exit criteria
- [ ] A real iPad opens the camera scanner over the production hostname

## 5.3c Secrets and configuration · 0.5 d

### Work items
- [ ] Secrets in a root-only file on the host, outside git, referenced by the
      compose file — never inlined
- [ ] `TOKEN_PEPPER` and `DEVICE_TOKEN_KEY` backed up to the hospital password
      manager; the entry name recorded in the runbook
- [ ] 5.0b's fail-closed startup verified against the real production values
- [ ] A documented rotation procedure for the kiosk tokens and the session key,
      with the pepper explicitly marked **not rotatable without reissuing every
      credential**

## 5.3e Deployment runbook and rehearsed rollback · 0.75 d

### Work items
- [ ] Release procedure: build, tag, deploy, smoke-check, and what "healthy" looks
      like in numbers
- [ ] Rollback procedure, **performed at least once on staging and timed**
- [ ] The backward-compatible-migration rule written down as a release rule for

      did not write them

## Risks

| Risk | Mitigation |
|---|---|
| The iPads do not trust the internal CA and the camera path dies silently | Trust verified on a real device by opening the camera, as an exit criterion |
| A secret reaches git or a compose file | Root-only secrets file, CI secret scan (5.2c), fail-closed startup |
| `TOKEN_PEPPER` is lost or backed up alongside the database | Stored in the password manager, location in the runbook, and its loss scenario documented in 5.4d |
| A rollback is needed during the pilot and blocked by a migration | Backward-compatible migrations for the pilot window, stated as a release rule |
| Dev compose settings reach production | Separate production compose plus 5.0b's refusal to boot on dev defaults |
