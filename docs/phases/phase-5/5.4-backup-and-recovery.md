# 5.4 — Backup and recovery ★

**Parent:** [§5.4](../phase-5-hardening-pilot.md) · **Depends on:** 5.3a, 5.0c ·
**Unblocks:** the go decision
**Estimate:** 3 d · **Risk:** high — the failure is invisible until the day it
matters

## Goal

A nightly backup that is encrypted, offsite and monitored, and a restore that
somebody has performed and timed.

## Design notes

**A backup that has never been restored is a hypothesis.** [09](../../09-security-privacy-ops.md)
says it and the parent makes the drill an exit criterion rather than a task. The
drill is therefore scripted, so it can be repeated, and timed, so the 4-hour RTO
is a measurement rather than a hope.

**Restoring the database is not the same as restoring the system.** The database
holds hashed credentials; resolving them requires `TOKEN_PEPPER`. A restore that
recovers every row and cannot authenticate a single card has restored nothing —
which is why the drill's verification includes *credential resolution* samples,
not just row counts, and why the pepper-loss scenario is written down as its own
recovery procedure.

**Jobs are CLI subcommands run by a timer, not goroutines inside the API.** Three
reasons: an operator under pressure must be able to run one by hand, each is
independently testable, and a job crashing must not take the counter down. This
is the same pattern 5.5e uses for reconciliation and retention.

**Every job reports success positively.** "No error was seen" is not evidence a
backup ran — a job that never starts produces no errors at all. Each run writes a
row and a metric, and the alert fires on the *absence* of a success.

## 5.4a Nightly backup job · 1 d

### Work items
- [ ] `hdms-cli backup` — `pg_dump -Fc`, gzipped, encrypted, written to the
      target named in 5.0a, invoked by a systemd timer at 02:00
- [ ] Retention: 30 daily, 12 monthly, with pruning that is itself logged
- [ ] `migrations/0020_job_runs.sql`: a `job_runs` table (job, started, finished,
      outcome, detail) shared by every scheduled job in this phase
- [ ] Idempotent and safe to run twice; safe to run by hand mid-day
- [ ] Encryption key stored and backed up separately from the backups themselves

### Tests
- [ ] Integration: a backup of the staging database restores into a scratch
      database and the row counts match
- [ ] `pruningKeepsExactlyThirtyDailyAndTwelveMonthly`
- [ ] `concurrentInvocationsDoNotCorruptTheOutput`

---

## 5.4b Backup monitoring · 0.5 d

### Work items
- [ ] Each run writes a `job_runs` row and a Prometheus textfile metric with a
      last-success timestamp
- [ ] Alert fires when the last success is older than 26 hours — on absence, not
      on error
- [ ] Alert verified by deliberately failing a run (5.5c's rule: an untriggered
      alert is unverified)
- [ ] Backup size is tracked; a sudden drop is as suspicious as a failure

---

## 5.4c Restore drill · 1 d

### Work items
- [ ] `hdms-cli restore --into <scratch-db>` with verification built in
- [ ] Verification: loan counts, open-loan count against INV-3, and a sample of
      **credential resolutions** proving the pepper and the data still agree
- [ ] Drill performed against staging by following the runbook, **timed**, and
      the elapsed time recorded
- [ ] The runbook is written such that a hospital IT staffer who has never seen
      the codebase can follow it

### Exit criteria
- [ ] Restore drill completed and timed within the 4-hour RTO
- [ ] The drill was run by following the written runbook, not from memory
- [ ] A sample of credentials resolves correctly after restore

## 5.4d WAL archiving and the pepper-loss scenario · 0.5 d

### Work items
- [ ] Decide whether the RPO must beat 24 hours; if yes, continuous WAL archiving
      with 7-day retention, and the point-in-time recovery steps in the runbook
- [ ] If no, record the decision and the accepted worst case — up to one day of
      transactions, recoverable from the paper register, which is exactly why the
      register stays at the counter
- [ ] **Pepper-loss recovery** documented: what is lost (every credential becomes
      unresolvable), what survives (loans, users, devices, audit), and the
      recovery path — reissue and reprint every card, from the admin console,
      with a realistic time estimate for the whole roster

## Risks

| Risk | Mitigation |
|---|---|
| Backups are configured and never verified | The drill is an exit criterion; the alert fires on absence of success |
| The database restores but no card works | The drill verifies credential resolution, and the pepper is backed up separately |
| The backup job stops running and nobody notices | Last-success metric with a 26-hour alert, deliberately triggered once |
| Backups and their encryption key are lost together | Key stored separately from the backup target, both recorded in the runbook |
| The drill is only ever run by its author | The exit criterion requires it run from the runbook by someone else |
