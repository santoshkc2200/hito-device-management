# 5.5 — Observability in production

**Parent:** [§5.5](../phase-5-hardening-pilot.md) · **Depends on:** 5.3a ·
**Unblocks:** 5.6, 5.8a
**Estimate:** 5 d · **Risk:** medium — the largest genuinely new code in the
phase

## Goal

The system says what it is doing, tells somebody when it stops, and enforces its
own invariants nightly.

## Design notes

**The domain metrics do not exist yet.** `internal/platform/observability/metrics.go`
is thirteen lines that hand `/metrics` to `promhttp.Handler()` — the Go and
process collectors, and nothing about loans, scans or kiosks. All six metrics in
[09](../../09-security-privacy-ops.md) are new code, and the gauges among them
need a decision about how they are computed.

**Gauges over the database are collected, not incremented.** `hdms_loans_open`
and `hdms_devices_by_status` are properties of the data, not counts of events; an
in-memory counter drifts the first time a row changes outside the happy path. A
periodic collector that queries is boring, correct, and cheap at this volume.

**An alert that has never fired is an untested code path.** Every alert in this
sub-phase is deliberately triggered once, on staging, and the trigger is recorded.
This is a parent exit criterion and the reason 5.0c exists.

**Nightly reconciliation is a control, not a report.** INV-3 says `devices.status`
and the open loans must agree. A job asserts it every night and alerts on
mismatch, so a bug that corrupts custody is found by the system rather than by a
nurse holding a laptop the system says is available. Nothing in the tree runs on
a timer today — this is the first.

**Retention needs Q7 before it can delete anything.** [01](../../01-requirements.md)
leaves the data-protection rules unconfirmed. The job is built to the documented
default (closed loans anonymised at 3 years), but it ships in **report-only mode
until Q7 is answered** — it logs precisely what it *would* remove. A deletion
policy applied before it is confirmed is not recoverable.

**Do not stand up a tracing backend for this volume.** Tracing already exports to
stdout by default (`tracing.go`) and OTLP is configurable if the hospital happens
to run a collector. Structured, rotated, searchable logs plus a documented search
recipe is the honest answer here; the stack stays deliberately boring.

## 5.5a Domain metrics · 1.25 d

### Work items
- [ ] `hdms_transactions_total{action,source,outcome}`,
      `hdms_scan_rejections_total{reason}`, `hdms_session_expired_total` —
      counters at the point the event happens
- [ ] `hdms_http_request_duration_seconds{route,status}` — histogram in the
      middleware chain, with a bounded route label (the raw path would explode
      cardinality)
- [ ] `hdms_loans_open`, `hdms_devices_by_status`, `hdms_kiosk_last_seen_seconds{kiosk}`
      — a periodic collector querying the database, interval documented
- [ ] `/metrics` reachable only from the monitoring host, never from the kiosk VLAN
- [ ] Metric names and labels frozen once the dashboards exist — a renamed metric
      is a silently blank panel

### Tests
- [ ] A counter test per transaction outcome, asserting the label set
- [ ] `routeLabelIsBoundedNotTheRawPath`
- [ ] Integration: gauges match a database state constructed in the test

## 5.5c Alert rules and routing · 0.75 d

### Work items
- [ ] Every alert from [09](../../09-security-privacy-ops.md): API down, database
      unreachable, kiosk offline 30 min in working hours, backup failed, disk
      > 85 %, scan-rejection spike > 30 % over 15 min, reconciliation mismatch,
      paper backlog > 48 h on working days
- [ ] Routed to the channel named in 5.0a; if there is none, a shared mailbox —
      an alert nobody receives is not an alert
- [ ] Each alert's message says what to do, and links its runbook
- [ ] **Each alert deliberately triggered on staging and the trigger recorded**

### Exit criteria
- [ ] Every alert has been fired on purpose at least once and observed arriving
- [ ] Every alert links a runbook that exists

## 5.5e Scheduled jobs — reconciliation and retention · 1.5 d

### Work items
- [ ] `hdms-cli reconcile` — asserts INV-3 nightly, writes a `job_runs` row,
      alerts on mismatch, and reports *which* devices disagree rather than a count
- [ ] `hdms-cli retention` — the [09](../../09-security-privacy-ops.md) policy:
      closed loans anonymised at 3 years, archived users anonymised with the
      history that references them
- [ ] Retention runs **report-only until Q7 is confirmed**; the mode is explicit
      configuration, not a commented-out line
- [ ] Both log what they did, in numbers, to `job_runs` — retention that nobody
      can audit is a liability rather than a control
- [ ] Both are idempotent and safe to run by hand; both have runbook entries in
      the same commit

### Tests
- [ ] Integration: a deliberately desynchronised device is detected and named
- [ ] Integration: reconciliation on a healthy database reports zero and does not
      "fix" anything — it reports, it does not mutate custody
- [ ] Integration: retention in report-only mode changes no rows and reports the
      correct candidates
- [ ] Integration: anonymisation preserves loan counts and breaks no foreign key

## Risks

| Risk | Mitigation |
|---|---|
| Alerts are configured but never arrive | Each one deliberately triggered on staging before the phase closes |
| A metric label explodes cardinality | Route labels bounded to the pattern; label sets asserted in tests |
| Retention deletes something the hospital needed | Report-only until Q7 is answered in writing; every run logs what it did |
| Reconciliation silently "fixes" custody and hides a bug | It reports and alerts; it never mutates |
| Dashboards are lost on a container rebuild | Provisioned as code in the repository |
| Nobody looks at any of it | The monthly runbook item makes reviewing the trends a named task |
