# 5.6 — Performance

**Parent:** [§5.6](../phase-5-hardening-pilot.md) · **Depends on:** 5.3a, 5.5a ·
**Unblocks:** 5.8
**Estimate:** 3 d (plus 24 h elapsed for the soak) · **Risk:** low — the
measurements exist and are comfortable

## Goal

Confirm on the real host what Phase 2 measured on a laptop, and prove the system
survives being left running.

## Design notes

**This is verification, not optimisation.** Phase 2 measured p95 18.4 ms and 780
scans/min at 50× peak ([load-test-results](../phase-2/load-test-results.md)) —
roughly five times the required headroom. The interesting question is not whether
the API is fast; it is whether *the deployed stack on the hospital's VM* is, once
Caddy, TLS, resource limits and a shared host are in the path. Any tuning here is
a response to a measurement, never a precaution.

**The soak looks for growth, not speed.** A leak does not show up in a five-minute
k6 run. Twenty-four hours answers three questions: do connections leak, do
goroutines grow, and does any table grow without bound — `idempotency_keys`, the
outbox and sessions being the three that could.

**The kiosk's first paint is measured on hospital Wi-Fi, on an iPad.** A number
from a desktop on gigabit ethernet is not evidence about the corridor. This
measurement belongs with the hardware, alongside
[3.10](../phase-3/3.10-hardware-validation.md)'s checklist.

## 5.6a Load test on the deployed stack · 0.75 d

### Work items
- [ ] Run `deploy/loadtest/scan-load.js` at 50× peak against **staging**, with
      the production configuration — TLS, Caddy, resource limits and rate limits
      all on
- [ ] Compare against the Phase 2 baseline and explain any regression rather than
      accepting it
- [ ] Confirm the rate limits (5.2b) do not distort the result — a throttled load
      test measures the limiter, not the system
- [ ] Record the numbers alongside the Phase 2 baseline for comparison

---

## 5.6b 24-hour soak · 0.5 d work, 24 h elapsed

### Work items
- [ ] Continuous light load for 24 hours on staging, with the 5.5b dashboards
      recording
- [ ] Assert at the end: database connections flat, goroutine count flat, memory
      flat
- [ ] Table growth reviewed — `idempotency_keys`, the outbox, sessions and audit
      — and a pruning path exists for anything unbounded that should not be
- [ ] Include an offline/replay cycle in the soak so 5.1's queue is exercised over
      a long window, not only in a unit test

### Exit criteria
- [ ] No connection leak, no goroutine growth, no unbounded table

---

## 5.6c Query review on the scan path · 1 d

### Work items
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` over every query the scan path executes, at
      pilot data volume (5.0c's seeded staging)
- [ ] Any sequential scan on a hot path is justified in writing or indexed
- [ ] Re-check the list queries Phase 4 added — the 5 000-row overdue list has an
      exit criterion of its own and now has production-shaped data to prove it
- [ ] Index changes land as a migration with measurements in the commit message

---

## 5.6d Frontend budgets · 0.75 d

### Work items
- [ ] Bundle size budgets for kiosk and admin, enforced in CI so a regression
      fails the build rather than being noticed in the corridor
- [ ] **Kiosk first paint under 2 s on hospital Wi-Fi, measured on the iPad**
- [ ] Verify the service worker's precache serves the shell instantly on a warm
      start — the kiosk should paint before the network answers
- [ ] Check the admin console's heaviest screens (backfill, the large tables)
      against the same budgets

### Exit criteria
- [ ] Measured borrow < 8 s and return < 6 s p95 on the deployed stack — the
      parent's criterion, though the final judgement is made on real use in 5.8
- [ ] Kiosk first paint < 2 s, measured on an iPad on hospital Wi-Fi
- [ ] Bundle budgets enforced in CI

---

## Risks

| Risk | Mitigation |
|---|---|
| The hospital VM is slower than the development machine and nobody checks | The load test runs on staging with the production configuration, not locally |
| A slow leak surfaces during the pilot | 24-hour soak with connection, goroutine and table-growth assertions |
| A query fast on 200 rows is slow on 20 000 | Staging is seeded at pilot scale before the review |
| The kiosk feels slow on the corridor Wi-Fi despite good API numbers | First paint measured on the device, on the real network |
