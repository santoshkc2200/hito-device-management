# 6.0 — Intake gate and extension rules

**Parent:** — (new) · **Depends on:** Phase 5 go decision · **Unblocks:** every
other Phase 6 item
**Estimate:** 1 d · **Risk:** low to do, high to skip

## Goal

Write down, once, the rules that let a feature be added to a system people are
using this morning — so that each later sub-phase is a feature and not also an
argument about flags, migrations and contract versioning.

## Design notes

**Phase 6's defining constraint is that there is no more pilot.** Phases 0–5 could
break things between deploys because nobody depended on them yet. From the go
decision onward, a bad Monday morning at the counter is a real hospital problem,
and the paper register — the designed overflow lane — is the fallback for a defect
this phase shipped. That is the standard every rule here is set to.

**"Nothing here is required for go-live" is a scope statement, not a process.**
It is the parent's most important sentence and it is also the reason Phase 6
attracts speculative work: with no deadline, everything looks affordable. The
intake gate exists so that "someone mentioned it" and "someone needs it" are
distinguishable in writing.

**The contract is frozen, which means additive, not untouchable.** Phase 5
deliberately added no endpoints so that the pilot ran against exactly what Phase 2
specified. Phase 6 must add some — 6.1 needs one field, 6.4 needs several
endpoints. Additive change under a version discipline is a normal thing to do;
doing it without written rules is how a kiosk that has not reloaded since Friday
starts returning `422`.

**A feature nobody uses is a liability with a good origin story.** Each sub-phase
carries a four-week usage check and a removal path. It is far easier to delete
something with a documented off switch than to discover in year three that nobody
knows whether the reservations code is load-bearing.

## 6.0b Additive-change rules for a frozen contract · 0.5 d

### Work items
- [ ] Write the rules into `docs/06-api-contract.md`: new endpoints and optional
      request fields are additive; new response fields are additive; **removing a
      field, narrowing an enum, changing a status code or tightening validation
      is not**, and needs a deprecation window at least as long as the longest
      interval between kiosk reloads
- [ ] Enum values are the sharp edge and get their own rule: a client compiled
      against `enum: [qr, code128, nfc, rfid, manual]` must tolerate an unknown
      value rather than fail parsing — verify what the generated TypeScript client
      actually does with one before relying on it
- [ ] Schema rules: new tables, and new columns nullable or defaulted. No
      `NOT NULL` without a default on a populated table, no destructive `ALTER`,
      no `DROP`. A migration must work against the previous release's binary — the
      Phase 5.8 pilot rule, made permanent
- [ ] Migration numbering: next free from `0019`, claimed at scheduling time and
      recorded in the [ledger](README.md#migration-ledger)
- [ ] New modules get their depguard entry in the same commit — leading `**/` on
      `files` patterns, trailing `$` on an exact `pkg:` match, or the rule denies
      more or less than intended

### Tests
- [ ] A spec-compatibility check in CI: the merged `api/openapi.yaml` against the
      previous release's, failing on any removal or narrowing
- [ ] `unknownEnumValueDoesNotBreakTheGeneratedClient`
- [ ] `task generate` produces no diff, as always

## 6.0c Feature-flag pattern and staged enablement · 0.25 d

### Work items
- [ ] One mechanism, reusing the Phase 4 settings row (`migrations/0016_settings.sql`)
      rather than inventing a second configuration system: a typed flag, default
      off, readable by the API and exposed to the admin console
- [ ] Kiosk-scoped enablement where the feature is a counter behaviour, reusing
      `enabled_sources` and the kiosk config the kiosk already fetches
- [ ] The rollout ritual, written down: dark deploy → one kiosk or one
      administrator → one working day → widen → remove the flag after four weeks
      of clean operation, because a permanent flag is a permanent branch
- [ ] Freeze windows: no Phase 6 deploy on a Friday, during a ward's known peak,
      or while an incident is open. Record who can waive it

### Tests
- [ ] `featureDefaultsToOffOnAFreshDatabase`
- [ ] `flagOffMeansTheEndpointIsAbsentOrRefuses` — not merely a hidden button

## Risks

| Risk | Mitigation |
|---|---|
| Features get built because they were mentioned once | Intake gate requires a named requester and an observed frequency |
| A contract change breaks a kiosk that has not reloaded | Additive-only rules with a CI compatibility check against the previous spec |
| A migration cannot be rolled back under pressure | Additive-only schema, working `-- +goose Down`, must run against the previous binary |
| Flags accumulate until nobody knows what is on | Removal is part of the rollout ritual, four weeks after enablement |
| A new module quietly leaks its internals | depguard rule committed with the module, with the two known pattern gotchas called out |
