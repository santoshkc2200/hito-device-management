# 6.1 — Adopt the hospital's RFID/NFC staff ID cards ★

**Parent:** [§6.1](../phase-6-extensibility.md) · **Depends on:** 6.0, Q9 ·
**Unblocks:** retiring the second card
**Estimate:** 3.75 d of work plus reader procurement lead time ·
**Risk:** medium — one external gate (6.1a) can end the sub-phase outright

## Goal

Staff carry one card again. The ID card already in their pocket becomes the
borrowing credential, and the separate QR card issued in v1 stops being something
to leave at a desk.

## Design notes

**6.1a is a gate, not a task.** Some card families — DESFire in random-UID mode
is the common one — emit a fresh UID on every read. If these cards do that, no
amount of code makes them a credential, and the correct outcome of this sub-phase
is a one-page finding and a closed request. One reader, one hour, before any
procurement or any promise.

**"Expected code change: none" is not true, and this plan assumes about a day of
it.** Three specific things in the tree reject an RFID card today:

- `mintToken` (`internal/modules/credentials/module.go:155`) returns
  `ErrKindNotIssuableInV1` for `rfid` and `nfc`; only `qr`/`code128` are generated
  and only `manual` accepts a supplied value.
- `canonicalToken` (`module.go:219`) parses an HDMS token or trims whitespace. It
  never calls `NormalizeUID`
  (`internal/modules/credentials/internal/domain/credential.go:82`), so a reader
  that types `04:A2:B3:C4` cannot match an enrolled `04A2B3C4`. The failure mode is
  the worst kind: a silent "unknown card" at the counter.
- The contract has no field for a token the caller supplies for a non-manual kind
  (`api/openapi.yaml:2331`).

None of this is hard. The Phase 1 and Phase 4 groundwork is real — the
`credential_kind` enum already carries `rfid` (`migrations/0004_credentials.sql:7`),
`NormalizeUID` is written and tested including byte-order reversal, the reader-test
screen is [4.5d](../phase-4/4.5-credentials.md), and `HidWedgeSource` needs nothing.
The honest estimate is a day of code, not zero, and saying so now is cheaper than
discovering it during an enrolment session with twenty staff queued.

**Normalisation must happen on both sides, from the same function.** Enrolment
normalises before hashing; resolve normalises before hashing. If those ever
diverge the system says "unknown card" to a valid card, and there is no way to
debug it from the outside because only hashes are stored.

**Byte order is a per-reader property, and mixed readers are the trap.** The
enrolment reader on the admin PC and the reader on each kiosk may not be the same
model. Pin one reader model for the whole estate if procurement allows; where it
does not, the normalisation profile belongs to the reader, and 6.1b stores it
accordingly rather than as one global setting.

**Migration is additive and reversible, which is the reason to be relaxed about
it.** An RFID credential is another `credentials` row (FR-16 allows several active
per user). Identity, loans and history are untouched, both cards work during the
overlap, and if the readers turn out to be wrong the credentials are revoked and
the QR cards are still in service.

**We never need the access-control system's database.** The UID is broadcast to
any reader in range; protected sectors would need their keys and we do not read
them. That keeps the Q9 conversation narrow, and 6.1a's report should say so in
those words.

## 6.1a Viability test — the gate ★ · 0.5 d plus procurement of one reader

### Work items
- [ ] **Q9:** who owns the access-control system, are they content for us to read
      card UIDs, and who signs that off
- [ ] Identify the card technology: 13.56 MHz (MIFARE Classic / DESFire / NTAG) or
      125 kHz proximity. This determines which reader to buy
- [ ] Buy **one** HID-keyboard-mode reader for that technology
- [ ] **Stability:** read the same card ten times; the UID must be byte-identical
      every time
- [ ] **Uniqueness:** read ten different cards; all ten UIDs must differ
- [ ] **Format:** record exactly what the reader types — case, separators,
      length, byte order, and whether it appends Enter
- [ ] Test across card generations: hospitals reissue cards, and an older batch
      may behave differently from this year's

### Exit criteria
- [ ] A one-page finding recorded against the request in
      [`requests.md`](6.0-intake-and-extension-rules.md), with the raw reads pasted in
- [ ] **Stop condition:** if UIDs are unstable, the sub-phase ends here and the
      QR cards stay. Record the finding and close the request — do not attempt a
      workaround, because a card that changes identity has no stable identity to store

## 6.1b UID resolve path and reader profiles · 1 d

### Work items
- [ ] `canonicalToken` normalises RFID/NFC UIDs through `NormalizeUID` before
      hashing — same function, same options, as enrolment
- [ ] Decide and document how a scanned string is classified: an HDMS token parses
      as one; otherwise a hex-shaped string of expected length is treated as a UID.
      Ambiguity is resolved in favour of the HDMS token, and the rule is a test
- [ ] Reader normalisation profile (byte order, expected length) stored per reader
      rather than globally, defaulting to `ByteOrderAsIs`, in the Phase 4 settings
      row — no new table
- [ ] Verify the profile end to end on the [4.5d](../phase-4/4.5-credentials.md)
      reader-test screen: raw next to normalised, against a real card
- [ ] A revoked or unknown UID produces the same counter-facing message as a
      revoked or unknown QR card — Phase 3's outcome screens are not re-designed here

### Tests
- [ ] `normalizedUidResolvesRegardlessOfSeparatorsAndCase`
- [ ] `reversedByteOrderReaderResolvesAgainstAnAsIsEnrolment` — with the profile set
- [ ] `hdmsTokenIsNeverMisclassifiedAsAUid`
- [ ] `enrolmentAndResolveProduceTheSameHashForTheSameCard` — the property that
      matters, asserted directly

## 6.1c Enrolment: contract, service and admin flow · 1.5 d

### Work items
- [ ] Additive contract change under [6.0b](6.0-intake-and-extension-rules.md):
      a caller-supplied token value accepted for `rfid`/`nfc`, alongside the
      existing `manualToken`. Prefer widening the documented meaning of one field
      over adding a near-duplicate — decide it once and write the decision in the
      spec, not in a commit message
- [ ] `mintToken` accepts a supplied, normalised UID for `rfid`/`nfc`;
      `ErrKindNotIssuableInV1` survives for any kind still not issuable
- [ ] A tapped card already bound to another user is rejected with a message that
      names the conflict — the same shape as a duplicate QR token
- [ ] Admin flow: open a user → *add credential → RFID* → tap → confirm the
      normalised value → save. Administrator-only, consistent with registration
- [ ] **Bulk enrolment mode** — tap, pick the user, tap, pick the user, without
      leaving the screen. Enrolling a few hundred staff one navigation at a time is
      the real cost in this sub-phase and it is worth half a day to remove
- [ ] Audit: enrolment writes an audit event naming the actor, as every credential
      operation does
- [ ] **ADR-0010 — RFID UID as a credential token**: why the UID alone is
      sufficient, why the access-control database is not needed, what random-UID
      cards would have meant, and how normalisation is kept identical on both paths

### Tests
- [ ] `rfidCredentialCanBeIssuedWithASuppliedUid`
- [ ] `issuingADuplicateUidIsRejected`
- [ ] `uidIsStoredNormalizedAndNeverInPlaintext`
- [ ] `enrolmentIsRefusedForANonAdministrator`
- [ ] Contract: the spec-compatibility check passes, i.e. the change is additive

## 6.1d Kiosk enablement and staged rollout · 0.5 d

### Work items
- [ ] Attach a reader to each kiosk and confirm it presents as an HID keyboard
      alongside the barcode scanner — two wedge devices on one iPad is the thing to
      verify physically, not theoretically
- [ ] Add `rfid` to `enabled_sources` for one kiosk first
- [ ] Validate `enabled_sources` values against a known set on write — it is an
      unvalidated `text[]` today (`migrations/0001_init.sql:48`), so `RFID` or
      `rfid ` silently does nothing
- [ ] Confirm the scan router treats the reader as another wedge source and that
      the `source` recorded on the scan distinguishes it, so adoption is measurable
- [ ] Offline: an RFID scan queues on exactly the same terms as a QR scan
      ([5.1b](../phase-5/5.1-offline-resilience.md)) — no new queueability rules
- [ ] One working day on one kiosk before the second, per
      [6.0c](6.0-intake-and-extension-rules.md)

### Tests
- [ ] `unknownEnabledSourceValueIsRejectedOnWrite`
- [ ] Kiosk: a UID typed by a wedge reader drives the same state transition as a
      scanned QR token

## 6.1e Dual-card period and QR retirement · 0.25 d

### Work items
- [ ] Both credentials stay active during the overlap — a user holding two working
      cards is the designed state (FR-16), not a defect to clean up
- [ ] Report: proportion of scans by source, to see adoption rather than assume it
- [ ] Decide with the hospital whether to retire the QR cards or keep them as the
      backup for a forgotten ID card. **Recommendation: keep them.** The card is
      already issued and the failure it covers — a staff member without their ID —
      otherwise falls to the paper register
- [ ] If retiring: revoke in batches, with the counter told in advance, and the
      first batch small

### Exit criteria
- [ ] Adoption measured over at least two weeks, by source
- [ ] The retirement decision is recorded with its reason, whichever way it goes

## Exit criteria for 6.1

- [ ] UIDs proven stable and unique on real hospital cards, with the reads recorded
- [ ] A staff member borrows and returns a device using only their existing ID card
- [ ] The same card resolves from both the enrolment reader and every kiosk reader
- [ ] Enrolment is administrator-only and audited
- [ ] Four weeks after rollout: RFID is a measured majority of scans, or the reason
      it is not is understood

## Risks

| Risk | Mitigation |
|---|---|
| Cards emit random UIDs | 6.1a is a gate with an explicit stop condition, run before any spend |
| Enrolment and resolve normalise differently, producing silent "unknown card" | One shared function, asserted by a same-hash test rather than by inspection |
| Mixed reader models disagree on byte order | Profile stored per reader, verified on the 4.5d screen against a real card before rollout |
| A typo in `enabled_sources` disables the feature silently | Values validated on write |
| Enrolling hundreds of staff becomes a week of clicking | Bulk enrolment mode is a planned slice, not an afterthought |
| The access-control owner reads this as a request for their data | It is not, and 6.1a's finding says so explicitly: only the UID the card already broadcasts |
| QR cards are retired too early and a forgotten ID card falls to paper | Default recommendation is to keep both; retirement in small batches if chosen |
