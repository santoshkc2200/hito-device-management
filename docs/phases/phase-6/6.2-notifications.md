# 6.2 — Notifications

**Parent:** [§6.2](../phase-6-extensibility.md) · **Depends on:** 6.0, and the
Phase 5 job runner ([5.5e](../phase-5/5.5-observability.md)) ·
**Unblocks:** the dashboard's `[Remind]` button
**Estimate:** 6 d · **Risk:** medium — the risk is reputational, not technical

## Goal

Stop administrators chasing overdue loans by hand, without ever sending a
reminder that is wrong.

## Design notes

**The parent's exclusion reason still stands and should be re-read before
starting: an unreliable reminder email is worse than none.** A staff member who
receives "you have not returned the projector" about a projector they returned on
Friday stops reading every message this system sends, permanently. That single
sentence sets every design decision below: send late rather than wrong, send from
committed state, and make silence auditable.

**Nothing publishes `loan.overdue` today.** The topic is declared
(`internal/platform/events/events.go:32`), the hub routes it (`hub.go:41`) and
audit already subscribes (`internal/modules/audit/subscriptions.go:16`) — there is
no producer anywhere in the tree. So the first slice is the scan job, not the
email, and every other slice depends on it.

**The `notification` module is a boundary with nothing behind it.** `module.go`
and `notificationapi/notification.go` are comment-only files from Phase 0. The
boundary is proven; the service is new code. That is a feature: the module's
public surface can be designed now with the outbox already in place.

**Delivery is an outbox consumer, so at-least-once is the guarantee and
deduplication is ours.** A reminder must be sent once per loan per escalation
step, not once per delivery attempt. Dedupe on (loan, step), recorded before the
send is attempted, not after it succeeds.

**Getting SMTP relay access inside a hospital is a multi-week conversation.**
Start it on day one of this sub-phase; build against a local catcher meanwhile.
The relay is an infrastructure request with an owner, not a config line.

**Quiet hours are a clinical courtesy, not a nicety.** Night staff should not get
a 03:00 pager-adjacent email about a laptop. Queue and send at the window's open;
never drop.

## 6.2a Overdue detection job and the `loan.overdue` producer · 1 d

### Work items
- [ ] `hdms-cli overdue-scan` as a systemd timer, on the Phase 5 job pattern:
      idempotent, writes a `job_runs` row, exposes a last-success metric, runbook
      page in the same commit
- [ ] Publishes `loan.overdue` to the outbox with the loan, the borrower and how
      overdue it is; the `loans_overdue_idx` partial index
      (`migrations/0007_lending.sql:71`) is already the right one
- [ ] Publishes once per loan per escalation step, never once per scan — a job that
      runs hourly must not emit hourly events for the same loan
- [ ] Disputed loans are excluded, consistent with the custody constraint's
      predicate: a disputed row is a recorded claim, not a fact to email about

- [ ] `aLoanReturnedBetweenScansProducesNoEvent`
- [ ] `disputedLoansAreNeverNotified`

## 6.2c SMTP transport and templates · 1.25 d

### Work items
- [ ] Hospital SMTP relay: address, auth, envelope sender, and who owns it —
      requested at the start of the sub-phase, not the end
- [ ] Three templates: overdue reminder to the borrower, weekly digest to
      administrators, return confirmation
- [ ] Plain text first, minimal HTML second. What matters is the device, when it
      was borrowed, how overdue it is, and where to return it
- [ ] No credential tokens, no PII beyond what the recipient already knows about
      themselves, and a subject line that is meaningful in a notification preview
- [ ] Every message names a human contact; a no-reply address that ends the
      conversation is how the counter gets phoned instead

### Tests
- [ ] Golden-file rendering per template
- [ ] `renderedMessageContainsNoTokenAndNoOtherBorrowersData`

## 6.2d Preferences, quiet hours and opt-out · 1 d

### Work items
- [ ] Per-user channel preference and opt-out, editable by the user's
      administrator (there is no staff-facing login and this phase does not add one)
- [ ] A global quiet-hours window: queue, then send at the window's open
- [ ] Digest instead of per-event for administrators, so a bad morning does not

      message sat in the queue — re-check state at send time, not at enqueue time

## 6.2e Wire up `[Remind]`, and SMS if a gateway exists · 1.25 d

### Work items
- [ ] The Phase 4 dashboard's `[Remind]` button sends through the same pipeline —
      one send path, so preferences, quiet hours and the delivery log all apply
- [ ] Feedback at the button: sent, queued for quiet hours, or refused with the
      reason. A button that silently does nothing is worse than no button
- [ ] Rate-limit manual reminders per loan so a frustrated administrator cannot
      send six
- [ ] SMS only if a local gateway already exists — as a second channel behind the
      same interface, never as a second pipeline

### Exit criteria
- [ ] A real overdue loan produces exactly one reminder, verified end to end on
      staging
- [ ] Four weeks after ship: manual chasing measurably reduced, and no reminder
      sent about a returned device

## Risks

| Risk | Mitigation |
|---|---|
| A wrong reminder destroys trust in every future message | State re-checked at send time; disputed loans excluded; suppression is a test |
| Duplicate reminders from an at-least-once outbox | Dedupe key on (loan, step), recorded before the attempt |
| The SMTP relay conversation blocks the sub-phase for weeks | Requested at the start; built against a local catcher |
| A relay outage stalls the shared outbox | Module-level retry and quarantine, not outbox backpressure |
| Night staff are emailed at 03:00 | Quiet hours queue rather than drop, with a test on both halves |
| Administrators drown in per-event mail | Digest by default for admin recipients |
