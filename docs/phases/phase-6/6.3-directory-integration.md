# 6.3 — Directory integration

**Parent:** [§6.3](../phase-6-extensibility.md) · **Depends on:** 6.0; do
[6.1](6.1-rfid-staff-cards.md) first if both are planned ·
**Unblocks:** the end of manual roster maintenance
**Estimate:** 8 d · **Risk:** medium-high — this is where an external system's
availability becomes ours

## Goal

Stop maintaining a staff roster by hand, and stop a departed employee from
keeping a working credential.

## Design notes

**`identity`'s public interface does not change — only its internals.** This is
the extraction scenario ADR-0001 was written for and the best available test of
whether the module boundaries were real. If `checkout` or `lending` needs a single
edit to accommodate a directory-backed identity, the boundary leaked, and that is
worth knowing and recording either way.

**A directory is a source of people, not a source of custody.** The loan history,
credentials and audit trail stay ours. A user who leaves is suspended, never
deleted: their loans happened, and an outstanding device is exactly the case where
the record matters most.

**Admin login and roster sync are independent, and 6.3a is worth doing alone.**
OIDC for administrators removes a password store from a hospital system and is
about two days. Roster sync is the larger, riskier half. Ship the first, then
decide.

**The directory must never become a hard dependency of the counter.** If Active
Directory is down, borrowing and returning continue: kiosk scans resolve against
our `credentials` table and never call the directory. Only the admin console
degrades, and it needs a documented break-glass local login — an OIDC outage that
locks every administrator out is a foreseeable incident, so it gets a runbook page
before it happens.

**Sync is one-way in, always.** We read; we never write back. A hospital's HR
system is not ours to modify, and the moment sync is bidirectional every conflict
becomes a data-loss question.

**Auto-registration relaxes the administrator-only constraint without reopening
the hole it was closed for.** The parent is right: the authorising decision moves
to HR, which is a stronger source than a kiosk. It stays optional, off by default,
and gets an ADR — this is the one place Phase 6 touches a founding constraint of
the product, and a future reader must find the reasoning.

## 6.3a OIDC login for administrators · 2 d

### Work items
- [ ] Authorization-code flow with PKCE against hospital AD/Entra, discovery
      document rather than hand-copied endpoints
- [ ] Directory identity mapped to an existing admin account by a stable claim
      (`sub`/`oid`), never by email address, which gets reused after a leaver
- [ ] Roles: map directory groups to the Phase 4 roles where the hospital can
      supply groups; otherwise keep roles local and use OIDC for authentication only
- [ ] Sessions, CSRF and the Phase 5 security-header work all still apply; session
      identifier regenerated on login, as [5.2a](../phase-5/5.2-security-review.md)
      requires
- [ ] **Break-glass local login**, documented, audited loudly, and tested by
      someone who did not write it
- [ ] **ADR-0011 — the directory as the authentication authority for administrators**

### Tests
- [ ] `oidcLoginBindsToTheStableClaimNotTheEmailAddress`
- [ ] `directoryOutageStillAllowsBreakGlassLogin`
- [ ] `directoryOutageDoesNotAffectKioskScanResolution` — the property that protects
      the counter

## 6.3b Roster sync · 2.5 d

### Work items
- [ ] `hdms-cli directory-sync` on the Phase 5 job pattern: scheduled, idempotent,
      `job_runs` row, last-success metric, runbook page
- [ ] LDAP or SCIM, whichever the hospital actually operates — do not build both
- [ ] Migration (next free from `0019`): external identity link (issuer, stable
      subject, last-seen-in-directory) and per-user sync state
- [ ] Field mapping decided once and written down: which system owns name,
      department and contact. Ours must lose on the fields the directory owns, or
      every sync becomes a merge argument
- [ ] **Dry-run mode reporting what would change, and it is the default for the
      first two weeks** — the same discipline Phase 5 applied to retention
- [ ] A safety limit: a sync proposing to change more than a set fraction of the
      roster stops and asks, because that shape of diff is usually a filter mistake

### Tests
- [ ] `syncIsIdempotentAcrossRuns`
- [ ] `syncNeverWritesToTheDirectory`
- [ ] `aMassChangeIsRefusedAndReported`
- [ ] `localOnlyUsersAreNeverTouchedBySync` — contractors and volunteers exist

## 6.3c Leaver suspension · 1.5 d

### Work items
- [ ] Disappearing from the directory suspends the user and their credentials;
      it never deletes, and never touches loan history
- [ ] **An outstanding loan blocks nothing but must be escalated:** the suspension
      happens, and the open loan appears on an administrator's list with the
      leaver's last known department. This is the single most valuable thing in the
      sub-phase — a device leaving the building with someone who has left the
      organisation is what it prevents
- [ ] Reinstatement path for a leaver who returns, without re-registering them
- [ ] Grace period before suspension, because directories lag and secondments look
      like departures

### Tests
- [ ] `leaverIsSuspendedAndCredentialsRevoked`
- [ ] `leaverWithAnOpenLoanIsEscalatedNotSilentlyClosed`
- [ ] `historyIsUnchangedBySuspension`

## 6.3d Optional auto-registration · 2 d

### Work items
- [ ] Off by default, behind the [6.0c](6.0-intake-and-extension-rules.md) flag,
      and scoped to a defined directory group rather than "everyone"
- [ ] An auto-registered user has no credential until an administrator issues one
      — registration and card issuance stay separate acts
- [ ] Provenance recorded on the user: registered by directory sync, at a time,
      from a batch, and visible in the admin console
- [ ] **ADR-0012 — relaxing administrator-only registration for
      directory-sourced users**: why HR is a stronger authorising source than a
      kiosk, and what stays administrator-only regardless

### Exit criteria
- [ ] The roster is not maintained by hand for directory-sourced staff
- [ ] A leaver cannot borrow, and their outstanding devices are surfaced
- [ ] A directory outage leaves borrowing and returning entirely unaffected
- [ ] `identity`'s public interface is unchanged — or the leak is documented in the ADR

## Risks

| Risk | Mitigation |
|---|---|
| The directory becomes a dependency of the counter | Kiosk resolution never calls it; asserted by a test, not by intent |
| An OIDC outage locks every administrator out | Break-glass local login, audited, rehearsed by someone who did not build it |
| A filter mistake suspends half the hospital | Dry-run default for two weeks, plus a mass-change refusal |
| Email-based matching binds a new joiner to a leaver's account | Matching on the stable claim only |
| Contractors without directory accounts are wiped by sync | Local-only users are explicitly out of scope of sync, with a test |
| Auto-registration quietly reopens the self-registration hole | Off by default, group-scoped, no credential without an administrator, and an ADR |
