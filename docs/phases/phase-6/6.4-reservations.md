# 6.4 — Reservations

**Parent:** [§6.4](../phase-6-extensibility.md) · **Depends on:** 6.0; after
[6.6](6.6-multi-location.md) and [6.9a](6.9-second-language.md) if either is
planned · **Unblocks:** nothing — it is a leaf
**Estimate:** 10 d · **Risk:** high — it adds a genuine new state to a machine
that is currently correct

## Goal

Let a device be claimed for a future window, without making the present-tense
borrow-and-return path any less reliable than it is today.

## Design notes

**Treat this as a small project, not a feature flag — the parent says so and the
schema agrees.** `device_status` has no `reserved` value
(`migrations/0003_catalog.sql:12`), and the custody exclusion constraint
(`migrations/0007_lending.sql:64`) ranges over loans: `tstzrange(borrowed_at,
returned_at)` per device, excluding written-off and disputed rows. A reservation
is a claim on a *future* interval with no loan row to exclude against. Either
reservations get their own overlapping-interval constraint, or two administrators
double-book the same projector and the database does not care.

**The hard question is not the reservation. It is the interaction with a walk-up
borrower.** Someone stands at the kiosk at 13:50 holding a device reserved for
Dr. X at 14:00. Refusing is correct and infuriating; allowing it makes the
reservation worthless. Decide the policy — with the counter, in advance, in
writing — before writing any code: a pre-window during which a device stops being
walk-up borrowable, and what the screen says. The parent's "reserved for Dr. X
from 14:00" is already the right shape: name the reason and the time, never just
"unavailable".

**Every new state needs a row in the state-machine matrix and its own tests.**
[04](../../04-scanning-and-checkout-flows.md) documents the scan session machine
and ADR-0004 makes it explicit on purpose. Adding a state without adding matrix
rows is the fastest way to break Phase 2's correctness.

**No-show expiry must be automatic and forgiving.** A reservation nobody collects
holds a device hostage. Expire it on a timer, tell the reserver, and release the
device. Fifteen minutes is a guess; make it configurable and let the counter tune it.

**Reservations must not break offline.** [5.1](../phase-5/5.1-offline-resilience.md)
decided the kiosk queues what the server can still adjudicate correctly later. A
reservation conflict cannot be adjudicated offline without lying to someone
standing at the counter. **Recommendation: while offline, the kiosk does not
enforce reservations and says so** — the paper register and an administrator sort
out the collision, which is the designed overflow lane. Whatever is decided, it is
decided here and written down, not discovered.

**Measure contention before building this.** If the reports show devices sitting
idle most of the day, a reservation system solves a problem the hospital does not
have. Ten days is the most expensive item on the roadmap.

## 6.4a Model, constraint and ADR · 2 d

### Work items
- [ ] Migration (next free from `0019`): `reservations` — device, user, window,
      status, created-by, source — with a `gist` exclusion constraint on
      (device, window) so overlapping reservations are impossible at the database
      level, exactly as custody is
- [ ] Decide whether `reserved` becomes a `device_status` value or stays derived
      from an active reservation. **Recommendation: derived.** A status column that
      must be kept in step with a time window is a reconciliation job waiting to be
      written
- [ ] Define the interaction between a reservation window and an open loan that
      overruns it — the overrunning borrower is not at fault and must not be
      punished by the screen
- [ ] **ADR-0013 — reservations as an interval claim distinct from custody**:
      why a second constraint rather than an extension of the custody one, and what
      the walk-up policy is

### Tests
- [ ] Integration: overlapping reservations are rejected by the database
- [ ] `aReservationDoesNotBlockAnExistingOpenLoanFromBeingReturned`
- [ ] Reconciliation (Phase 5.5e) extended: no device is both reserved-active and
      on loan to someone else without an explanation

### Tests
- [ ] `creatingAConflictingReservationReturnsAClearConflictError`

Implementation note: the staff PWA supports self-service create and cancel through `POST /staff/me/reservations` and `POST /staff/me/reservations/{id}/cancel`. The server derives the reserver from the staff session, limits cancellation to that reserver, and uses the existing overlap constraint. Admins set the advance window, maximum duration, and return buffer under Settings → Policy; defaults are 90 days, 30 days, and 60 minutes. Devices without an expected return cannot be booked from the staff app. The staff reservation list is paginated so every active booking remains reachable.

## 6.4e No-show expiry and metrics · 1.5 d

### Work items
- [ ] `hdms-cli reservation-expiry` on the Phase 5 job pattern, with a configurable
      grace period and a runbook page
- [ ] Expiry notifies the reserver through [6.2](6.2-notifications.md) if it has
      shipped; otherwise it is visible in the admin console
- [ ] Metrics: reservations made, collected, expired, and conflicts refused at the
      kiosk — the four numbers that say whether this was worth ten days

### Exit criteria
- [ ] Double-booking is impossible at the database level, proven by an integration test
- [ ] A walk-up borrower is never surprised: every refusal names the reason and the time
- [ ] Four weeks after ship: collection rate is high and refused-conflict counts are
      low. A high expiry rate means the feature is being used as a hoarding tool and
      the grace period, or the feature, needs revisiting

## Risks

| Risk | Mitigation |
|---|---|
| Double-booking through a race | A database exclusion constraint, not application checks |
| The walk-up path regresses | Policy decided with the counter first; the unreserved path is a named regression test |
| A `reserved` status column drifts from reality | Status derived from the window, not stored |
| Reservations hold devices hostage | Automatic no-show expiry with a tunable grace period and an expiry metric |
| Offline reservations tell a borrower something false | Documented offline policy: do not enforce, say so, fall back to paper |
| Ten days spent on contention that does not exist | Measure utilisation from [6.8](6.8-analytics.md) or the Phase 4 reports before scheduling |
