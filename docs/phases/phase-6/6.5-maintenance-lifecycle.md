# 6.5 — Maintenance and lifecycle

**Parent:** [§6.5](../phase-6-extensibility.md) · **Depends on:** 6.0 ·
**Unblocks:** nothing — it is a leaf
**Estimate:** 6 d · **Risk:** low — additive throughout, and it touches custody
at exactly one point

## Goal

Know when a device is due for service, what has been done to it, and whether it is
getting worse — so that devices leave service on a schedule rather than by failing
in someone's hands.

## Design notes

**Most of this is record-keeping, and record-keeping is cheap to build and easy to
abandon.** The failure mode is not a bug; it is a service history nobody fills in.
Build the smallest thing that a busy administrator will actually maintain, and put
the due-date alert first — the alert is the part that changes behaviour, and the
history is only worth having because the alert makes people write it.

**`device_status` already has `maintenance` and `retired`**
(`migrations/0003_catalog.sql:12`), and `device_condition` already has
`good`/`fair`/`damaged` (`:15`). This sub-phase adds history and scheduling around
concepts that exist; it does not introduce them.

**The one custody-adjacent decision: a device with an open loan cannot be moved to
`maintenance` behind the borrower's back.** Either the transition waits for the
return, or it is flagged for return-and-service so the counter takes it out of
circulation when it comes back. The second is better, and it needs a screen at the
return path rather than only a status change.

**Damage capture at return is where condition data actually comes from.** An
administrator will not run a condition survey; an attendant handling a returned
projector will tap "damaged" if the tap is one tap. Design for that moment and the
history fills itself.

## 6.5c Condition tracking and damage at return · 1.5 d

### Work items
- [ ] Condition history rather than only the current `device_condition` value, so
      deterioration is visible as a trend
- [ ] Damage capture at return, on the kiosk **and** in the admin console. On the
      kiosk it must be one optional tap that never blocks the return — a return that
      cannot complete because a form is open is a device that goes back on the shelf
      unreturned
- [ ] Damage does not automatically accuse the last borrower. Record the
      observation; attribution is a human decision
- [ ] Optional photo attachment from the admin console only; the kiosk stays a
      single-purpose appliance

### Tests
- [ ] `damageCaptureNeverBlocksAReturn`
- [ ] `conditionHistoryIsAppendOnly`

## 6.5d Warranty, purchase records and retirement · 2 d

### Work items
- [ ] Purchase date, supplier, cost, warranty expiry, asset reference
- [ ] Warranty-expiry visibility alongside the service-due list — a repair quoted
      the week after a warranty lapses is the avoidable loss here
- [ ] Retirement workflow: reason, disposal record, data-wipe confirmation for
      anything that stored data, and the approving actor
- [ ] **A device with an open loan cannot be retired.** It can be marked for
      retirement on return, which is the flow that matches reality
- [ ] Retired devices keep their full history and never disappear from reports

### Tests
- [ ] `retirementIsRefusedWhileALoanIsOpen`
- [ ] `retiredDeviceHistoryRemainsQueryable`
- [ ] `dataBearingDeviceCannotBeRetiredWithoutAWipeRecord`

### Exit criteria
- [ ] A device due for service is visible before it fails, not after
- [ ] Retirement produces a disposal record an auditor would accept
- [ ] Four weeks after ship: service records are being written by someone other
      than the person who built the feature. If not, the alert is not landing where
      the work happens and the sub-phase has not delivered

## Risks

| Risk | Mitigation |
|---|---|
| The history is built and never filled in | Alerts first, damage capture at the return moment, next-due advanced automatically |
| A borrower's device vanishes into `maintenance` mid-loan | Transition is refused; mark-on-return instead |
| Damage capture slows the return path | One optional tap on the kiosk, never blocking, asserted by a test |
| A data-bearing device is disposed of without a wipe | Wipe record required by the retirement workflow |
| Condition becomes an accusation | The record is an observation; attribution stays a human decision |
