# 6.6 — Multi-location

**Parent:** [§6.6](../phase-6-extensibility.md) · **Depends on:** 6.0 ·
**Unblocks:** the location dimension that [6.4](6.4-reservations.md) and
[6.8](6.8-analytics.md) would otherwise be retrofitted with
**Estimate:** 5 d · **Risk:** medium — the risk is in the backfill and the
permission model, not the column

## Goal

Run the same system across more than one ward or site, so that a device belongs
somewhere, a kiosk knows where it is, and an administrator sees their own place
first.

## Design notes

**The parent is right that the schema absorbs this by adding a `location_id` —
and that is the smallest part of the work.** The column is an hour. The five days
are: backfilling every existing device and kiosk correctly, deciding what
"belongs to a location" means when a device is carried between wards daily, and
deciding whether an administrator of ward A may see ward B.

**Do this before [6.4](6.4-reservations.md) and [6.8](6.8-analytics.md) if any of
them are planned.** A reservation in a two-site world is location-scoped, and
utilisation questions are always asked per location. Retrofitting a dimension into
a state machine and a report set costs more than adding it once.

**Homing is a default, not a fence.** A device homed to ward A that is borrowed at
ward B's kiosk must still work — a refusal would make the system worse than the
paper register it replaced. The home location is where it should be returned to
and what the reports group by, and "away from home" is a visible condition rather
than an error.

**Permissions are the genuinely contentious decision.** Whether a ward
administrator can see another ward's borrowers is a hospital policy question with a
privacy dimension, not an engineering preference. Ask it explicitly, get the answer
in writing, and record it in the ADR. **Default: scoped read, with superadmins
unscoped** — the narrower default is the recoverable mistake.

## 6.6a Locations, homing and backfill · 2 d

### Work items
- [ ] Migration (next free from `0019`): `locations`, plus a nullable
      `location_id` on devices and kiosks — additive, per
      [6.0b](6.0-intake-and-extension-rules.md)
- [ ] Backfill every existing device and kiosk to a single default location so the
      column is never a partially-populated dimension in reports
- [ ] Location hierarchy only if the hospital actually has one; a flat list is
      correct until proven otherwise, and a self-referencing tree is easy to add
      later and hard to remove
- [ ] "Away from home" derived and visible, never enforced
- [ ] **ADR-0014 — location as a scoping dimension**: homing as a default rather
      than a fence, and the permission decision from 6.6c

### Tests
- [ ] `deviceBorrowedAtAnotherLocationsKioskSucceedsAndIsFlaggedAsAway`
- [ ] Migration up and down clean, with `migrations_test.go` green

## 6.6b Kiosk binding and counter behaviour · 1 d

### Work items
- [ ] Each kiosk is bound to a location; the binding flows through the existing
      kiosk config the kiosk already fetches — no new fetch path
- [ ] The location appears on the kiosk, quietly. An estate of identical iPads
      needs to be identifiable when someone phones about "the kiosk"
- [ ] Returns to a non-home location succeed and produce a "belongs at X" hint for
      the attendant rather than a refusal

## 6.6c Scoped views and permissions · 1.5 d

### Work items
- [ ] Get the visibility policy answered in writing before implementing it
- [ ] Location filter across the Phase 4 list infrastructure, defaulting to the
      administrator's own location
- [ ] Scoped dashboards; superadmins see everything
- [ ] Scope enforced server-side. A filter in the UI is a convenience; the
      authorisation must be in the query, and the negative test is the deliverable

### Tests
- [ ] `scopedAdministratorCannotReadAnotherLocationsData` — asserted at the API,
      not the screen
- [ ] `superadminSeesEverything`

## 6.6d Transfers · 0.5 d

### Work items
- [ ] An explicit transfer changes the home location, with actor, reason and
      timestamp, and appears in the device's history
- [ ] Bulk transfer, because moving a ward's equipment one device at a time is how
      the feature stops being used
- [ ] A transfer is refused, or queued until return, while a loan is open — the
      same rule as [6.5d](6.5-maintenance-lifecycle.md)'s retirement

### Exit criteria
- [ ] Every device and kiosk has a location; none are null
- [ ] Cross-location borrowing works and is visible as such
- [ ] The visibility policy is implemented as answered, and enforced server-side
- [ ] Four weeks after ship: reports are being read per location, which is the
      only reason to have built the dimension

## Risks

| Risk | Mitigation |
|---|---|
| A partially-populated dimension corrupts every report | Backfill in the same migration; a null `location_id` is treated as a defect |
| Homing becomes a fence and the counter is refused | Away-from-home is derived and visible, never enforced; asserted by a test |
| Ward A's administrator reads ward B's borrowers against policy | Policy answered in writing first; scoped by default; enforced in the query with a negative test |
| Retrofitting location into reservations and analytics later | Schedule 6.6 before 6.4 and 6.8 if those are planned |
| A premature hierarchy nobody uses | Flat list until the hospital demonstrates a tree |
