# 6.7 — Consumables

**Parent:** [§6.7](../phase-6-extensibility.md) · **Depends on:** 6.0 ·
**Unblocks:** nothing — it is a leaf, deliberately
**Estimate:** 8 d · **Risk:** medium — the risk is that it gets built inside
`lending` instead of beside it

## Goal

Track the things that are issued and never come back — cables, batteries, blank
media — without distorting the custody model that makes borrowing correct.

## Design notes

**This is a different domain wearing similar clothes, and the parent's
instruction is the whole design: a new `inventory` module beside `lending`, not a
mode inside it.** Lending is about *this* laptop, identified, in someone's hands,
with an interval of custody that a database constraint enforces. Consumables are
about *four* USB cables leaving a drawer. There is no identity, no return, no
overdue, and nothing to reconcile per item. Every invariant `lending` protects —
one open loan per device, no overlapping custody, temporal exclusion — is
meaningless here, and forcing both models into one table means weakening the
constraints that make the important half trustworthy.

**The modular design is what makes this cheap, and this is the test of it.**
`identity`, `credentials`, `audit` and the kiosk are reused unchanged. If building
`inventory` requires editing `lending`, ADR-0001's boundaries were aspirational,
and that finding is worth more than the feature.

**Stock levels are a new kind of wrongness.** A device is where the system says it
is, because custody is enforced. A count of cables in a drawer drifts from reality
every time someone takes one without scanning. Plan for reconciliation from the
start — a stock count workflow, and a visible "last counted" date so nobody trusts
a number from March.

**Kiosk issuance needs a quantity, which the scan machine has never needed.**
The kiosk is currently a two-scan appliance: device, badge, done
([04](../../04-scanning-and-checkout-flows.md)). Issuing three cables needs a
quantity step, and that step must not leak into the borrow path. **Recommendation:
ship 6.7a–c admin-only first and let the counter tell you whether kiosk issuance
is wanted at all** — half of this sub-phase's cost is in that last part.

## 6.7a Module, boundary and model · 2.5 d

### Work items
- [ ] `internal/modules/inventory` with an `inventoryapi` public surface, matching
      the existing module shape
- [ ] depguard rule in the same commit: internals unreachable from other modules.
      Both project quirks apply — leading `**/` on `files` patterns, trailing `$`
      to anchor an exact `pkg:` match — or the rule denies the wrong set
- [ ] Migration (next free from `0019`): item types, stock levels, and an
      append-only movement ledger (issue, restock, adjustment, write-off)
- [ ] **Stock level is derived from the ledger, not a column that is decremented.**
      A mutable counter and a movement history disagree eventually, and the ledger
      is the one that can be audited
- [ ] **ADR-0015 — consumables as a separate module**: the two models side by
      side, what was rejected, and why `lending`'s invariants do not apply

### Tests
- [ ] `stockLevelAlwaysEqualsTheLedgerSum`
- [ ] `issuingMoreThanStockIsRefused`
- [ ] depguard: an import of `inventory/internal` from another module fails lint

## 6.7b Issuing, restocking and low-stock alerts · 2 d

### Work items
- [ ] Issue to a user by the same credential resolution as lending — one identity
      model, reused, not reimplemented
- [ ] Restock and adjustment, both requiring a reason, both audited
- [ ] Low-stock thresholds per item with alerts through [6.2](6.2-notifications.md)
      if it has shipped, otherwise in the admin console
- [ ] Negative stock is impossible; an adjustment that would go negative is refused
      with the count that caused it

## 6.7c Admin screens and stock counts · 1.5 d

### Work items
- [ ] Item list, movement history and issue flow on the Phase 4 list infrastructure
- [ ] Stock count workflow: enter counted quantity, the difference is recorded as
      an explicit adjustment with a reason, never as a silent overwrite
- [ ] "Last counted" date visible everywhere a stock number is shown
- [ ] Consumption reporting by user and department — which is what finance will
      ask for and the reason this gets requested

## 6.7d Kiosk issuance — only if the counter asks · 2 d

### Work items
- [ ] Quantity selection as its own step, entirely separate from the borrow path;
      no shared state with the scan session machine
- [ ] The borrow-and-return journey is unchanged for anyone not issuing a
      consumable — this is the regression test that matters
- [ ] Offline: an issue is queueable (nothing to adjudicate but a count) but a
      stock refusal cannot be shown offline. Say so on screen rather than promising
      stock that may not exist
- [ ] Strings through [6.9a](6.9-second-language.md)'s catalogue if shipped

### Tests
- [ ] `theBorrowPathIsUnchangedWhenConsumablesAreEnabled`
- [ ] `offlineIssuanceFollowsTheDocumentedPolicy`

### Exit criteria
- [ ] `lending` was not modified — verified by reading the diff, not by assertion
- [ ] Stock reconciles to the ledger, provably
- [ ] Four weeks after ship: counts are being reconciled and the numbers are
      trusted. An untrusted stock number is worse than no stock number, because
      someone orders against it

## Risks

| Risk | Mitigation |
|---|---|
| Consumables get bolted into `lending` and weaken custody | Separate module, depguard-enforced, with an ADR and a no-diff check on `lending` |
| Stock drifts from reality until nobody trusts it | Ledger-derived levels, a stock count workflow, and a visible last-counted date |
| The kiosk borrow path gets slower for everyone | 6.7d is optional, separately staged, with an explicit no-regression test |
| A silent overwrite hides a discrepancy | Counts produce adjustments with reasons, never overwrites |
| Eight days for something used twice | 6.7a–c ship admin-only first; 6.7d waits for the counter to ask |
