> The original 6.9 scoped only the kiosk and estimated 4 days. The i18n spec ships all four surfaces — kiosk, admin console, printed material, and backend-emitted text where no browser exists — with collation, CSV BOM, IME, font, and line-break work that a string-extraction plan misses. Its estimate is ~11.5 days. That spec and the two plans above are the source of truth; this page no longer drives execution.

## Risks

| Risk | Mitigation |
|---|---|
| Extraction is assumed done and the estimate collapses | 6.9a is a costed slice; the assumption is corrected in this plan and in the README's gap list |
| Wording changes ride along with the refactor | Mechanical extraction only, tests updated in the same commit, wording separately |
| Long translations clip buttons on a 10.2-inch iPad | Phase 3.9's worst-case layout tests run per locale |
| The kiosk is left in the wrong language for the next person | Reset on the existing idle timeout, asserted by a test |
| A missing key renders as a raw key at the counter | Visible fallback to the default language, plus compile-time key checking from a typed catalogue |
| The same strings get extracted twice | 6.9a scheduled before any new kiosk screen in 6.4 or 6.7 |

## Four-week check (deferred — not yet due)

Four weeks after ship, check whether the second language is actually being selected — the kiosk toggle and the admin switcher both write somewhere observable (`kiosks.default_locale`, `admin_accounts.locale`). If it is not being used, the translation was not the barrier and the request behind it should be re-examined rather than extended. Tracked as a follow-up after this branch merges; see `docs/superpowers/plans/2026-08-31-i18n-admin-print-backend.md` Task 10 Step 7.
