# 6.9 — Second language

**Parent:** [§6.9](../phase-6-extensibility.md) · **Depends on:** 6.0 ·
**Unblocks:** any later kiosk screen that would otherwise hardcode its copy
**Estimate:** 4 d · **Risk:** low, once the parent's assumption is corrected

## Goal

Run the kiosk in a second language, without a second codebase and without a
translation step that has to be repeated by hand every release.

## Design notes

**The parent says "the strings are externalised from Phase 3, so this is
translation work plus a language toggle". They are not.** The kiosk's copy is
inline in JSX — `apps/kiosk/src/screens/awaiting-device-screen.tsx:141` is
`Scan a device to borrow or return`, and its test asserts that literal string.
There is no catalogue, no `i18n` dependency and no locale plumbing anywhere in the
frontend. The extraction is real work and it is [6.9a](#69a-string-extraction--15-d),
the first slice.

**Do 6.9a before any other new kiosk screen.** [6.4d](6.4-reservations.md) and
[6.7d](6.7-consumables.md) both add copy. Extracting once is cheap; extracting the
same strings twice is not.

**Extraction is a mechanical refactor and should be exactly that.** No wording
changes in the same commit as the move, or the Phase 3 screen tests fail for two
different reasons at once and the review becomes archaeology. Update the tests to
assert through the catalogue in the same commit, then change wording separately if
it needs changing.

**Layout resilience is the part that actually breaks.** German and Nepali run
long; Phase 3.9 already built worst-case layout tests
([3.9](../phase-3/3.9-visual-design.md)) for exactly this class of problem. Run
them per locale, with the longest string in each, or the second language ships
with clipped buttons on a 10.2-inch iPad.

**A language toggle on a shared kiosk must reset.** The next person to walk up
gets the default language, not whatever the last person chose. This belongs in the
idle timeout that already exists.

**Numbers, dates and names are not translation.** Dates already go through
`apps/kiosk/src/lib/date-format.ts`; locale-aware formatting belongs there rather
than in a second mechanism.

## 6.9a String extraction · 1.5 d

### Work items
- [ ] Choose the mechanism. **Recommendation: a plain typed catalogue module**, not
      a runtime i18n framework — the kiosk has perhaps 150 strings, an offline-first
      bundle should not grow a dependency for that, and a typed object gives
      compile-time detection of a missing key, which a framework's runtime fallback
      does not
- [ ] Extract every user-visible string from `apps/kiosk/src` — screens,
      components, error and outcome copy, and the strings in the shared `ui` package
- [ ] Keys named for meaning, not for the current English wording
- [ ] Update the Phase 3 screen tests to assert through the catalogue, in the same
      commit, with **no wording changes at all**
- [ ] Admin console strings are explicitly out of scope unless asked for: the
      counter is where language matters, and administrators are a small trained group

### Tests
- [ ] `noUserVisibleStringLiteralsRemainInKioskComponents` — a lint rule or a test,
      so the extraction cannot silently rot back
- [ ] The full Phase 3 kiosk suite green, unchanged in intent

## 6.9b Locale plumbing and the toggle · 1 d

### Work items
- [ ] Locale selection with a per-kiosk default in the existing kiosk config
- [ ] A visible toggle that is reachable without being easy to hit by accident
- [ ] **Resets to the kiosk default on idle timeout**, using the timeout that
      already exists
- [ ] Locale-aware date and number formatting through `date-format.ts`
- [ ] Locale is a client concern: the API returns codes and identifiers, and no
      translated string ever comes from the server. RFC 9457 error mapping
      ([3.8](../phase-3/3.8-resilience.md)) already works this way — keep it that way

### Tests
- [ ] `localeResetsToTheKioskDefaultAfterIdle`
- [ ] `serverErrorCodesRenderTranslatedOnTheClient`

## 6.9c Translation and layout verification · 1.5 d

### Work items
- [ ] Translate the catalogue, reviewed by a native speaker who works at the
      counter — not by whoever is available, because "return" and "give back" are
      different instructions to someone in a hurry
- [ ] Run [3.9](../phase-3/3.9-visual-design.md)'s worst-case layout tests per
      locale with the longest strings
- [ ] Re-run the axe accessibility audits per locale, including `lang` attributes,
      which a screen reader needs to pronounce anything correctly
- [ ] A missing key falls back to the default language visibly enough to be caught
      in review, and never renders a raw key at the counter
- [ ] Printed material and the [5.7b](../phase-5/5.7-documentation-and-training.md)
      counter card need the same treatment, or the kiosk speaks one language and the
      card beside it speaks another

### Exit criteria
- [ ] No user-visible string literal remains in kiosk components, enforced in CI
- [ ] Both locales pass the worst-case layout and axe suites
- [ ] A native speaker at the counter has reviewed the copy in place, on the iPad
- [ ] Four weeks after ship: the second language is being selected. If it is not,
      the translation was not the barrier and the request should be re-examined

## Risks

| Risk | Mitigation |
|---|---|
| Extraction is assumed done and the estimate collapses | 6.9a is a costed slice; the assumption is corrected in this plan and in the README's gap list |
| Wording changes ride along with the refactor | Mechanical extraction only, tests updated in the same commit, wording separately |
| Long translations clip buttons on a 10.2-inch iPad | Phase 3.9's worst-case layout tests run per locale |
| The kiosk is left in the wrong language for the next person | Reset on the existing idle timeout, asserted by a test |
| A missing key renders as a raw key at the counter | Visible fallback to the default language, plus compile-time key checking from a typed catalogue |
| The same strings get extracted twice | 6.9a scheduled before any new kiosk screen in 6.4 or 6.7 |
