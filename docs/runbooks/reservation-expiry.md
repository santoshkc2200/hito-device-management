# Runbook: Reservation Expiry and No-Show Reclamation Pipeline (6.4e)

**Target host:** staging first, production by timer. Verify any remediation on staging before production execution — see `docs/runbooks/staging-stack.md`.

## Purpose and operational guarantee

The reservation expiry job identifies uncollected reservations where the reserver did not show up within the configured grace period (`start_at + grace_minutes < now()`). It transitions their status from `active` to `expired`, freeing the device for general walk-up borrowing or subsequent reservations, and notifies the original reserver via email.

**Core invariant:** Silence is auditable; reservations are an interval claim distinct from custody ([ADR-0013](../adr/0013-reservations-as-interval-claim-distinct-from-custody.md)).
- Walk-up pre-window blocks unreserved borrowers `reservation_pre_window_minutes` before `start_at` (default 30 min).
- If the reserver fails to collect the equipment before `start_at + reservation_expiry_grace_minutes` (default 15 min), the reservation is expired automatically.
- Once expired, the GiST exclusion constraint condition `WHERE (status <> 'cancelled' AND status <> 'expired')` no longer includes this reservation, releasing the equipment immediately.
- Reserver notification is deduplicated on `reservation-expiry:<id>` to avoid duplicate emails.

## What runs automatically

Every 5 minutes, a systemd timer runs the expiry command on the host. On the Docker stack this job runs inside the `worker` container on the same schedule; the systemd timer is for non-Docker installs:

```bash
/opt/hdms/bin/hdms-cli reservation-expiry
```

Unit files:
- Service: `/etc/systemd/system/hdms-reservation-expiry.service`
- Timer: `/etc/systemd/system/hdms-reservation-expiry.timer`

## Run it by hand (safe any time, safe repeatedly)

The expiry job is strictly idempotent across runs. Running it manually will only expire active reservations past their grace threshold:

```bash
sudo -u hdms /opt/hdms/bin/hdms-cli reservation-expiry
```

Expected output:
```
Reservation expiry: 2 reservation(s) expired (grace: 15m), 2 notification(s) enqueued, 0 skipped dedupe
```

## Verify execution positively

Scheduled jobs record positive success in `job_runs`:

```sql
SELECT job, started_at, finished_at, outcome, detail
FROM job_runs
WHERE job = 'reservation-expiry'
ORDER BY started_at DESC
LIMIT 5;
```

Expected healthy output: `outcome = 'success'` with details on expired count and enqueued notifications.

Alerts trigger on the *absence* of a recent successful run or on metric anomalies:
- Metric: `hdms_job_last_success{job="reservation-expiry"}`
- Metric: `hdms_reservations_expired_total`
- Metric: `hdms_notification_deliveries_total`

## Configuration

The grace period is stored in system settings:
- Setting key: `settings.reservation_expiry_grace_minutes`
- Default value: 15 minutes
- Tunable via Admin Console Settings or database update.

## Notifications & delivery review

Review notifications generated by reservation expiries:

```sql
SELECT id, recipient, template, dedupe_key, status, attempt_count, last_error, created_at
FROM delivery_log
WHERE template = 'reservation_expired'
ORDER BY created_at DESC
LIMIT 10;
```

## Escalation path

1. **Timer not running:** Check `systemctl status hdms-reservation-expiry.timer`.
2. **Expiry failing:** Inspect `journalctl -u hdms-reservation-expiry -n 50` and the latest `job_runs` row with `outcome = 'failure'`.
3. **Devices incorrectly remaining blocked:** Check if any active reservations still exist for the device:
   ```sql
   SELECT id, device_id, user_id, status, start_at, end_at
   FROM reservations
   WHERE device_id = '<device-uuid>' AND status = 'active';
   ```
4. **Reservers reporting missed notifications:** Verify SMTP transport connectivity and check `delivery_log` for failed or quarantined delivery attempts.
