# Internationalization and localization — English and Japanese

**Date:** 2026-08-31 · **Status:** approved design, awaiting implementation plan
**Supersedes:** [`docs/phases/phase-6/6.9-second-language.md`](../../phases/phase-6/6.9-second-language.md)

## Goal

Run HDMS in Japanese and English — the kiosk, the admin console, printed
material, and anything the backend emits where no browser exists to render it —
from one codebase, with a translation workflow that does not have to be repeated
by hand every release.

Japanese is the default. English is the second language.

## Why this supersedes 6.9

The existing sub-phase plan is sound in its mechanics and wrong in three ways
that change its cost:

1. It scopes only the kiosk. Administrators are excluded on the grounds that
   they are "a small trained group". The decision here is that all four surfaces
   ship bilingual.
2. It treats the work as string extraction plus translation. For Japanese
   specifically it is not: font loading, line breaking, collation, CSV encoding,
   and input-method behaviour are all real work, and one of them is a
   correctness bug rather than a cosmetic one.
3. It estimates 4 days. The scope above is roughly 11.5.

Its core mechanical guidance is kept unchanged: extraction is a refactor, no
wording changes ride along with it, and the same strings must not be extracted
twice.

## Decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Surfaces | Kiosk, admin console, printed material, backend-emitted text | All four requested |
| Default locale | `ja`, with a per-kiosk and per-admin-account override | Japanese hospital, Japanese staff |
| Frontend mechanism | Typed catalogue module, no runtime i18n dependency | ~150 kiosk strings do not justify a framework in an offline-first PWA, and a typed object detects a missing key at compile time where a framework falls back silently at runtime |
| Backend mechanism | `golang.org/x/text`, used only where no client exists | See "Backend rule" below |
| Operator-entered data | Not translated — single value, stored as typed | A device named ノートPC 12 reads identically in both locales; translating free text would add a second field to every create and edit form and a translation obligation to every import path |

### Backend rule

API responses stay code-only. No endpoint reads `Accept-Language`, and no
response carries a translated string — RFC 9457 problems carry a `type` and a
code, and the client renders the copy. `apps/kiosk/src/lib/problem.ts` already
works this way; the change is that its mapping moves into the catalogue.

The backend translates only where there is no browser to do it: the CLI (via
`LANG` or an explicit `--locale`), and notification emails when 6.2 is built,
keyed on the recipient's stored locale. Nothing in this plan builds notification
templates, because 6.2 does not exist yet.

## Architecture

### `packages/i18n`

A new workspace package, consumed by both apps and by `packages/ui`:

```
packages/i18n/src/
  locale.ts        # type Locale = "ja" | "en";  DEFAULT_LOCALE = "ja"
  provider.tsx     # LocaleProvider + useLocale(); sets the html lang attribute
  translate.ts     # t(catalogue, key, params) — typed, no runtime dependency
  format.ts        # Intl wrappers: date, time, number, list, collator
  catalogue.ts     # type Catalogue<T>, defineCatalogue helper
```

Each app owns its own catalogue namespace; `packages/ui` owns the strings in
shared components, which is why the engine cannot live inside either app.

Completeness is enforced by the type system:

```ts
type Messages = typeof ja;   // ja is the reference catalogue
const en: Messages = { … };  // a missing key is a tsc error
```

The reference catalogue is Japanese because Japanese is the default. A key added
in English that nobody translated then fails the build rather than the counter.
`task build` already runs `tsc -b`, so this costs no new CI step.

Keys are named for meaning (`kiosk.awaitingDevice.prompt`), never for the
current English wording. Parameters are typed: `t("loan.dueBy", { time })` does
not compile without `time`.

Plurals are a small helper over `Intl.PluralRules` — Japanese has one form,
English has two, and that is the entire requirement.

### Locale resolution

| Surface | Source | Reset behaviour |
|---|---|---|
| Kiosk | `kiosks.default_locale`, exposed on the existing kiosk config payload | A visible toggle, reset to the kiosk default on the idle timeout that already exists |
| Admin | `admin_accounts.locale`, with a switcher in settings | Sticky per account |
| CLI | `LANG`, or an explicit `--locale` flag | n/a |
| Notifications (6.2, later) | The recipient's stored locale | n/a |

Both columns are additive migrations, `NOT NULL DEFAULT 'ja'`, per the 6.0
additive-change rules. Exposing them on the existing config and session payloads
is an additive contract change, not a breaking one.

A language toggle on a shared kiosk must reset. The next person to walk up gets
the kiosk's default language, not whatever the previous person selected.

## Localization beyond translation

This is the part that a "translate the strings" plan usually misses.

**Input methods and the barcode scanner.** The HID wedge injects keystrokes. If
a Japanese IME is composing in a focused text field, those keystrokes are
swallowed into the composition buffer and the scan is lost. The scan abstraction
must ignore events where `isComposing` is set or `keyCode` is 229. This is a
correctness bug, not a cosmetic one, and it is the highest risk in this plan —
it is scheduled first, as a spike, because if the fix is not local to
`packages/scan` the cost of everything downstream changes.

**Fonts.** The kiosk is an offline-first PWA, so a CDN webfont is not available
to it. The iPadOS system fallback (Hiragino) is acceptable, but Chrome on
Windows in the admin console is not. A subset Noto Sans JP ships in
`packages/ui/tokens.css` with a proper family stack, and the bundle delta is
budgeted rather than discovered.

**Line breaking.** Japanese has no spaces, so a browser will break a line
anywhere unless told otherwise. Per-locale `line-break: strict` and
`overflow-wrap` rules, with Phase 3.9's worst-case layout tests re-run per
locale using each locale's longest strings.

**Collation.** Sorting Japanese names in admin tables requires
`Intl.Collator("ja")` rather than `<`.

**CSV export.** Excel on Japanese Windows mis-renders UTF-8 without a byte-order
mark. Exports carry one.

**Dates and numbers.** `apps/kiosk/src/lib/date-format.ts` currently returns
whole English sentences ("Please return by today, 17:00"). It is rewritten to
return parts, and the catalogue owns the sentence. Gregorian calendar,
`Asia/Tokyo`, 24-hour clock.

## Extraction mechanics

Extraction is a mechanical refactor and should be exactly that. No wording
changes in the same commit as a move — otherwise the Phase 3 screen tests fail
for two different reasons at once and the review becomes archaeology. Tests are
updated to assert through the catalogue in the same commit; wording changes ship
separately if they are needed at all.

Per file: lift the literal into a key in the `ja` catalogue (written new, in
Japanese) and the `en` catalogue (seeded from the existing code, verbatim), then
replace the JSX with `t()`. Note the direction — the English catalogue is
extracted, the Japanese catalogue is authored, and authoring it is the
translation work.

### Enforcement

- **`no-user-visible-literals`** — an oxlint rule, or a vitest source scan if
  oxlint cannot express it, over `apps/*/src` and `packages/ui/src`. Bare text
  nodes in JSX and string literals in `aria-label`, `title`, `placeholder`, and
  `alt` fail. Exceptions are allowlisted by comment at the site, not by
  accumulating configuration.
- **Completeness** comes free from `const en: Messages` and the existing
  `tsc -b`.
- **Unused keys** — a test walks the catalogue and greps for each key, so dead
  copy is deleted rather than accumulated.
- **No raw key ever renders.** On a miss, `t()` returns the `ja` value, never
  the key string. This is unreachable past `tsc` for the checked catalogues, but
  it protects anything loaded or edited outside the type system.

### Ordering

`6.9a` gates the schedule — run it before committing to dates. `6.9b` and
`6.9c` are independent of each other and both precede `6.9d`. Everything from
`6.9d` onward is sequential within its app, and the admin track (`6.9g`, `6.9h`)
is independent of the kiosk track once the engine exists.

`6.9d` must land before any new kiosk screen — 6.4d reservations and 6.7
consumables both add copy, and extracting the same strings twice is the one
avoidable cost here.

## Testing

- `missingEnglishKeyFailsTypeCheck` — a compile-fail fixture, so the central
  guarantee is proven rather than assumed
- `noUserVisibleStringLiteralsRemainInKioskComponents` and the admin equivalent,
  in CI
- `localeResetsToKioskDefaultAfterIdle` — the shared-kiosk invariant
- `serverErrorCodesRenderTranslatedOnTheClient` — proves the contract rule holds
  in both directions
- `scannerDeliversFullPayloadWhileImeActive` — the 6.9a regression test
- Phase 3.9's worst-case layout suite, parameterized by locale
- The axe suite per locale, asserting `lang` is set correctly
- Playwright: one full borrow-and-return in `ja`, one in `en`

## Exit criteria

- No user-visible string literal remains in kiosk or admin components, enforced
  in CI
- Both locales pass the worst-case layout and axe suites
- A native speaker who works at the counter has reviewed the copy in place, on
  the iPad
- A scan succeeds with the IME active, on the hardware
- Four weeks after ship: the second language is being selected. If it is not,
  the translation was not the barrier and the request should be re-examined

## Risks

| Risk | Mitigation |
|---|---|
| An active IME swallows wedge keystrokes and the scanner stops working | 6.9a is a costed spike scheduled before anything else, with a regression test |
| Wording changes ride along with the extraction refactor | Mechanical extraction only; tests updated in the same commit, wording changed separately |
| Long strings clip controls on a 10.2-inch iPad | Phase 3.9's worst-case layout tests run per locale with each locale's longest strings |
| Japanese text renders in a fallback font on the admin console | Subset Noto Sans JP shipped in `tokens.css`, with the bundle delta budgeted |
| The kiosk is left in the wrong language for the next person | Reset on the existing idle timeout, asserted by a test |
| A missing key renders as a raw key at the counter | Typed catalogue keyed against `ja`, plus a visible fallback that never returns the key string |
| The same strings get extracted twice | 6.9d scheduled before any new kiosk screen in 6.4 or 6.7 |
| The API grows translated strings by accident | Codified in 6.9j as a module-boundary guard, not as a convention |
